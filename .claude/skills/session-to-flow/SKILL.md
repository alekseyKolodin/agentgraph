# /session-to-flow — flow из сессии

Хелпер: `node <директория этого скилла>/digest.mjs <команда>` (обычно `~/.claude/skills/session-to-flow`, симлинк на `<корень agentgraph>/.claude/skills/session-to-flow`). Ниже `D` = эта команда, `$SCRATCH` — scratchpad-директория сессии.

- `D root` — корень проекта agentgraph (`ROOT`): там `flows/`, `src/` и CLI.
- `D list [--cwd DIR] [--limit N]` — последние сессии: id, время, директория, ветка, заголовок, первая реплика; текущая помечена `current`.
- `D digest [ID|путь.jsonl] --out FILE` — дайджест транскрипта. Без ID берётся текущая сессия (`$CLAUDE_CODE_SESSION_ID`). Хвост, начиная с последнего вызова `/session-to-flow`, и запущенные в нём сабагенты отрезаются.
- `D tool [ID] N [--tail L]` — вызов `#N` из дайджеста целиком: полная команда или вход и последние L строк результата (по умолчанию 80).

Аргументы пользователя: `$ARGUMENTS`

Цель — flow, который при запуске на похожей задаче сам пройдёт путь, найденный в сессии, без ошибок, тупиков и поправок пользователя. Пересказ хронологии сессии такой цели не служит.

## 1. Источник и дайджест

- По умолчанию источник — текущая сессия. Если в аргументах есть id или путь к `.jsonl`, бери его. Если пользователь описал прошлую сессию словами, выполни `D list --cwd <директория проекта>` и уточни через AskUserQuestion, какую взять.
- Дайджест строй **всегда**, даже для текущей сессии: контекст мог сжиматься, а ранние ошибки ценнее всего.
  ```bash
  D digest [ID] --out "$SCRATCH/session-digest.md"
  ```
  Прочитай файл целиком, большой — частями через Read с offset. Сырой `.jsonl` не читай и не разбирай своими скриптами. Если по дайджесту не ясно, что произошло (команда обрезана, нужен вывод), выполни `D tool [ID] N`. Проверенные команды во flow бери оттуда, а не из обрезанной строки дайджеста.
- В дайджесте:
  - 👤 реплики пользователя целиком, в том числе отправленные, пока ассистент работал;
  - 🤖 текст ассистента; последний ответ сессии идёт без обрезки, обычно это лучшая сводка итога;
  - → #N вызовы инструментов, ⤷ хвост вывода;
  - сбои и вмешательства: ✗ ошибки, ⚠ выводы, похожие на сбой при коде выхода 0 (`| head`, `|| true` и т. п. — частые ложно-зелёные), ⛔ отказы пользователя от действия, ⏹ прерывания;
  - ❓ ответы на вопросы, ↳ отчёты и сообщения агентов, 🔔 итоги фоновых задач;
  - 📝 записи в память, CLAUDE.md, правила и скиллы — уроки, уже сформулированные в сессии.

  В конце два раздела: «Повторы» (одна и та же команда или файл много раз) и «Сабагенты» (их собственные сбои).
- Секреты и IP в дайджесте замаскированы, но проверь сам. Во flow **не переносить** токены, пароли, ключи, OTP, IP, персональные данные, содержимое `.env` и `local.properties`. Хост сервиса (`gitlab.<компания>.com`) оставлять можно, если без него команда не работает.

## 2. Разбор сессии

Запиши разбор в `$SCRATCH/session-analysis.md` по пунктам ниже. Он нужен для шагов 3–5, пользователю его не показывай.

1. **Задача.** Что делали, в обобщённом виде. Отдельно — конкретика этого раза: тикет, ветка, экран, файлы, MR. Она станет `{{input}}` или её будет выяснять этап анализа.
2. **Проект.** Директория, стек. Соседние репозитории, куда ходили. Если без них не обойтись, они пойдут в `add_dirs`: только существующие пути, проверь через `ls`.
3. **Рабочий путь.** Последовательность шагов, которая в итоге сработала. Не хронология и не метания. Сгруппируй шаги в этапы. Если что-то делалось несколько раз (два прохода исправлений, два push), во flow это один шаг цикла, а не копии этапов.
4. **Проверенные команды.** Только те, что в итоге прошли и действительно проверили результат: сборка, тесты, линтер, запросы к API. Дословно, с флагами и env.
5. **Подводные камни.** По одному на строку в формате «симптом → причина → как правильно». Где искать:
   - ✗ ошибки: что ассистент поменял после каждой, чтобы пройти дальше;
   - ⛔ отказы и поправки пользователя («нет, не так», «не пушь», «используй X»). Это самый сильный сигнал, ни одной не пропусти;
   - «Повторы»: команда или файл много раз означает, что здесь застряли. Разберись почему;
   - ложно-зелёные проверки (команда прошла, но ничего не проверила) и ложно-красные;
   - ошибки сабагентов и случаи, когда их отчёт оказался неверным;
   - тупики: подходы, от которых отказались, и причина отказа;
   - ограничения среды: хуки, права, таймауты, сеть.
6. **Решения пользователя.** Для каждого определи: оно стабильное (тогда это правило в промпте) или каждый раз своё (тогда AskUserQuestion на этапе анализа или `pause_marker`).
7. **Критерий готовности.** Как в сессии поняли, что всё сделано. Детерминированная проверка → `until: command` или этап проверки с маркером. Качественная → `judge` или проверка внутри этапа.
8. **Действия с последствиями.** push, MR, комментарии, сообщения, удаление, force, миграции, релизы. Что пользователь разрешал, что запрещал, о чём просил спрашивать.
9. **Что уже записано.** Сверь камни с тем, что этап и так получит или что уже есть рядом: 📝 записи из дайджеста, память проекта (`~/.claude/projects/<проект>/memory/`), CLAUDE.md и AGENTS.md проекта, flow в целевой папке. Записанное в CLAUDE.md, правилах или памяти проекта этап прочитает сам, во flow хватит ссылки. Готовую формулировку из соседнего flow бери дословно.

Если в сессии было несколько разных задач, спроси, какую оформлять. Если сессия была запуском существующего flow (видно по `/agentgraph` и `AG start` в дайджесте) или похожий flow уже есть в `ROOT/flows`, предложи **доработать его**, а не плодить новый.

## 3. Уточнить у пользователя

Один AskUserQuestion, до 4 вопросов. Спрашивай только то, чего нельзя понять из сессии:

- что будет меняться от запуска к запуску (это пойдёт в `{{input}}`) — варианты возьми из п. 1;
- папка и имя flow — варианты из существующих папок (`ls ROOT/flows`) и предложенное имя в kebab-case;
- как поступать с действиями из п. 8: делать самому, спрашивать или не делать;
- новый flow или доработка существующего, если такой выбор есть.

## 4. Спроектировать flow

1. Прочитай правила генератора прямо из кода, они главнее этого файла: `ROOT/src/generate.ts` (`ORCHESTRATOR_RULES`, `DESIGN_RULES`) и схему `ROOT/src/schema.ts`. Если код и этот файл разошлись, прав код.
2. Открой 1–2 flow из целевой папки и возьми их конвенции: `model` и `effort` этапов, `defaults`, `max_budget_usd`, вызов сабагента `docs-librarian` на этапе анализа, запрет выводить `.env`, стиль `handoff`, язык. Новый flow должен выглядеть как соседи. Правило генератора «не задавай model и effort» здесь уступает конвенции папки: если соседи их задают, задавай так же; если не задают — не задавай.
3. Отличие от генератора. Его правило «не выдумывай факты о репозитории» здесь смягчено: факты не выдуманы, а проверены в сессии.
   - **Стабильное** встраивай дословно: команды, флаги, пути к конфигам, хосты, имена модулей и флейворов, порядок шагов.
   - **Нестабильное** (ветку, тикет, конкретные файлы задачи) поручай выяснить этапу анализа и не хардкодь.
4. Что из разбора куда идёт:

   | В сессии | Во flow |
   |---|---|
   | итоговый рабочий путь | этапы блока, 2–5 штук; несколько блоков — только если в сессии были отдельные стадии со своими критериями готовности |
   | проверенная команда | промпт этапа, который её выполняет, дословно |
   | камень с командой или флагом | тот же этап: «делай X, а не Y: Y <причина>» |
   | ложно-зелёная проверка | этап проверки: правильная команда и почему другая врёт |
   | тупик | этап, где возникает соблазн: «не пробуй X: <почему не работает>» |
   | стабильное решение пользователя | правило в промпте |
   | решение, которое каждый раз своё | AskUserQuestion на этапе анализа (и `AskUserQuestion` в `tools`); `loop.pause_marker` — только если вопрос возникает по итогам итерации (см. ниже) |
   | пути «этого раза» (worktree, временные папки) | не хардкодить; этап анализа находит или создаёт их и передаёт путь через `handoff`. Правки вне директории проекта и `add_dirs` не гарантированы (в headless запрос подтверждения = отказ), поэтому либо flow запускают с `--cwd` на нужный worktree (написать в `description`; форма запуска в UI умеет его готовить), либо команды идут через Bash с `git -C` |
   | действие с последствиями | отдельный последний блок без цикла; в промпте «только если согласие зафиксировано в плане»; без force |
   | детерминированная проверка готовности | `until: command`, если команда известна заранее; если она зависит от того, что найдёт запуск (список веток, модулей), — этап проверки и `until: marker` |
   | замечания, которые приходилось исправлять повторно | чек-лист на этапе реализации и пункт рубрики проверки |
   | нужный документ или скилл | ссылка по имени или пути, без пересказа |
   | долгая команда или фоновая задача | на переднем плане с `timeout`; процесс, который должен пережить этап, — через `nohup … &` |
   | Jira, Confluence, Slack из коннекторов claude.ai | перечисли в `tools` точные имена вызванных инструментов (`mcp__claude_ai_Atlassian_Rovo__getJiraIssue` и т. п.) или весь коннектор одной записью (`mcp__claude_ai_Atlassian_Rovo`, только если этап должен и писать туда): без них этап коннекторов не получит. В этапе имя всегда вида `mcp__claude_ai_<Коннектор>__<инструмент>`; имя `mcp__<uuid>__…` из desktop-сессии переименуй |
   | другие MCP-инструменты (Figma и т. п.) | выдача этапам не проверена; замени проверенным в сессии CLI или API (`glab`, `curl`) или вынеси данные в `{{input}}`, и скажи об этом пользователю |

5. `pause_marker`: маркер последней строкой может вывести любой этап итерации. Пауза ставится после итерации, если условие не выполнено. После «Продолжить» идёт следующая итерация. Ответ пользователя в промпты сам не попадает: `/agentgraph` запишет его туда, куда укажет этап. Поэтому этап, задающий вопрос, должен назвать файл решений, а первый этап — читать его.
6. Камень формулируй как инструкцию с причиной, без истории («в прошлый раз мы…»). Агент этапа — свежая сессия и о твоей сессии ничего не знает.
7. Не дублируй то, что этап получит и так. Сессии этапов грузят CLAUDE.md пользователя и проекта, правила, auto-memory проекта, скиллы и сабагентов, как обычная сессия Claude Code; что именно, видно на странице «Контекст» в UI. Если правило уже записано там, сошлись на скилл или документ по имени. Если камня там нет, а он касается проекта, а не этой задачи, предложи пользователю после flow дописать его в CLAUDE.md или память проекта.
8. `input`: задавай, только если у flow есть осмысленная задача по умолчанию, например «Исправление конфликтов текущей ветки». Иначе не задавай, а в `description` напиши, что передавать задачей. Старый тикет или ветка в `input` при повторном запуске повторят старую задачу.

## 5. Записать и проверить

1. Черновик пиши в `$SCRATCH/<имя>.yaml`.
2. Проверь схему и ссылки `{{phases.X}}`:
   ```bash
   npm --prefix ROOT run --silent agentgraph -- show "$SCRATCH/<имя>.yaml"
   ```
   Код выхода не 0 — исправь и повтори.
3. Сверь черновик с разбором:
   - каждый камень из п. 5 и каждая поправка пользователя попали в конкретный этап; составь таблицу «камень → этап», она понадобится для отчёта;
   - `{{input}}` есть в каждом этапе; в блоке с циклом `{{feedback}}` есть в первом этапе и в этапе реализации;
   - если промпт велит спрашивать пользователя, `AskUserQuestion` есть в `tools`; если велит запускать команды — есть `Bash`; права минимальны;
   - для `marker` в промпте сказано, что маркер — ровно последняя строка;
   - нет секретов и конкретики этого раза.
4. Имя должно быть уникально во всех папках: `find ROOT/flows -maxdepth 2 -name '<имя>.y*ml'` ничего не находит. Исключение — осознанная доработка существующего flow. Перед перезаписью покажи пользователю diff и получи согласие.
5. Скопируй файл в `ROOT/flows/<папка>/<имя>.yaml` (или в `ROOT/flows/<имя>.yaml` без папки) и ещё раз прогони `show` по итоговому пути. UI подхватит flow сразу.
6. В git не коммить. В `ROOT` часто лежат чужие незакоммиченные правки. Коммит — только по просьбе пользователя и только своим файлом.

## 6. Отчёт

Коротко:
- путь к файлу и план: блоки, этапы с инструментами, условие остановки и лимит итераций;
- таблица «подводный камень → куда встроен» и отдельно то, что сознательно не перенесено, с причиной;
- что передавать задачей при запуске;
- что проверено (`show`) и что нет. Сам flow не запускался: первый прогон лучше сделать под присмотром, через `/agentgraph <имя>` с `--max-budget`;
- как править: Конструктор в UI или `npm --prefix ROOT run agentgraph -- edit <имя> "<что поменять>"`.

Запуск flow не предлагай как само собой разумеющееся, если в нём есть push, MR или публикация. Скажи, на каком этапе это произойдёт.
