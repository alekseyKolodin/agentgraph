# Центр дел — спецификация разработки

Центр дел («Мои дела») — доска, на которой утром видно всё, что на тебе: ревью, задачи Jira и Teamwork, обещания со встреч,
забытые сессии и ветки. Доска наполняется и чистится сама. Эта спека задаёт порядок: сначала фундамент и починки, доска —
последней. Написана 18.11.2026 по итогам аудита.

- Аудит (20 сценариев месяца, пути к коду): [audit/](audit/) — A (утро, проекты), B (ревью, Jira), C (рутины, встречи),
  D (сессии, flow), E (месяц, Teamwork). Сводка: https://claude.ai/artifact/DT1nUMVBqau1nDDhRkY8rx.
- Макеты: [design/DeskPult.dc.html](design/DeskPult.dc.html) — доска, [design/RulePult.dc.html](design/RulePult.dc.html) —
  строка «Завести дело» в редакторе рутины. Холст: https://claude.ai/artifact/ShwmFDHcodf8v2KtYNJKu2, страница «В стиле приложения».
- Связанные спеки: [../routines/SPEC.md](../routines/SPEC.md), [../teamwork/spec.md](../teamwork/spec.md).
- Рамки: UX, логика продукта, пространства. Безопасность и производительность — отдельно.

## 1. Принципы

Каждое решение ниже проверяется этими восемью правилами. Если этап их нарушает, этап переделывается.

1. **Дело — это состояние настоящей вещи, а не событие.** MR открыт, автор ответил, смержен. Пять комментариев к одному MR —
   одно дело, а не пять.
2. **Три слоя: сигнал → вещь → наблюдатель.** Откуда ты узнал (сигнал), что это (вещь) и как оно меняется (наблюдатель) —
   три независимых вопроса. Ссылку на MR могли назначить в GitLab, кинуть в Slack или прислать письмом — вещь и её
   наблюдатель одни и те же.
3. **Одна операция записи для всех.** Рутина, этап flow, сессия Claude и командная строка заводят, обновляют и закрывают
   дело одним и тем же вызовом.
4. **Одна вещь — одно место.** Новая фича не добавляет ещё один список рядом. Существующие блоки (свои MR, «Не доделано»,
   «Мои задачи» Teamwork, ожидания рутин) становятся источниками и видами одного хранилища.
5. **Сверка не врёт.** «Проверено» значит: запрос ушёл, ответ пришёл, записей столько-то. Пустой ответ, протухший ключ и
   «не проверяли с перезапуска» — три разных состояния, и все видны.
6. **Ничего не теряется молча.** Всё, что отброшено по лимиту, фильтру или ошибке, оставляет строку в журнале.
7. **Настройка — как у рутины.** Отдельного мастера и отдельных «источников доски» нет. Что считать делом, куда класть и
   когда закрывать — поля правила.
8. **Привычки команды — это данные правила, а не код.** Где просят ревью, как называют ветки, что считается «готово» —
   настраивается; ни одна привычка не зашита.

Следствие для порядка работ: каждый этап полезен сам по себе, на текущей Главной, без доски. Старое поведение остаётся,
пока новое не заменило его полностью; блоки Главной убираются только на этапе доски.

## 2. Решения

Приняты вместе с аудитом 18.11.2026. Меняются только правкой этого раздела.

| Вопрос | Решение |
|---|---|
| Что такое «проект» | Пространство. К нему привязаны репозитории «Подключений» и проект Teamwork. Работа без пространства попадает в «Без проекта» |
| Где живёт доска | Доска заменяет Главную. Над ней остаются вопросы агентов и сверка |

| Кто двигает дело | Автоматика двигает только при *изменении* вещи. Ручной перенос держится до следующего изменения (как `prPatch` в `src/teamwork-status.ts`) |

## 3. Модель

### 3.1 Сигнал, вещь, наблюдатель

**Сигнал** — «я узнал об этом здесь»: событие любого источника рутины (`RoutineEvent`), вызов инструмента из flow или
сессии, ручное добавление. У сигнала есть источник, ссылка, автор, время и нить разговора (тред Slack, ветка письма).

**Вещь** — то, о чём дело. У вещи есть канонический ключ; по нему определяется «то же самое».

| Вещь | Ключ | Наблюдатель | Закрыта, когда |
|---|---|---|---|
| MR / PR | `mr:<host>/<путь проекта>/<номер>` | forge (glab / gh) | смержен или закрыт |
| Задача Jira | `jira:<host>/<KEY-123>` | Jira | статус из категории «Готово» или сняли с меня |
| Задача Teamwork | `tw:<команда>/<проект>/<id>` | репо команды | статус `done` |
| Ветка | `branch:<корень репо>#<ветка>` | локальный git | чисто и нет коммитов впереди без MR |
| Сессия | `session:<id>` | сервер сессий | продолжена или удалена |
| Запуск | `run:<id первого запуска цепочки>` | сервер запусков | цепочка закончилась успехом |
| Разговор | `thread:<источник>/<канал>/<нить>` | нет | вручную или по правилу |
| Своё | `own:<id>` | нет | вручную, из flow или сессии |

**Разбор ссылок.** Любой сигнал проходит разбор: из `link` и `text` достаются ссылки и ключи известных вещей (адрес MR/PR,
адрес или ключ задачи Jira). Ссылка на известную вещь делает сигнал сигналом об этой вещи, откуда бы он ни пришёл. Ссылок
несколько — вещей несколько. Ссылки нет — вещь «разговор»: ключ по нити, наблюдателя нет.

**Наблюдатель** — один на тип вещи. Раз в интервал снимает состояние только тех вещей, по которым есть открытые дела:

```ts
type ThingState = {
  exists: boolean;                      // false — вещь пропала или нет доступа (см. error)
  closed?: 'merged' | 'closed' | 'done';
  turn: 'me' | 'others' | 'none';       // чей ход
  why: string;                          // «автор ответил на 2 замечания», «CI упал», «3 файла не закоммичены»
  title: string;
  updatedAt: string;
  facts: Record<string, unknown>;       // ветка, автор, статус CI — для условий и карточки
  error?: string;                       // «нет доступа к gitlab.company.com: glab auth login»
};
```

Чей ход у MR считается по обсуждениям и коммитам, а не по полю «ревьюер»: мой ход, если есть коммиты или ответы автора
после моей последней реплики, либо ревью запрошено заново; ход других, если последняя реплика моя. Так работает и команда,
где ревьюера назначают в GitLab, и команда, где его не назначают вовсе. Логика «ждут ответа» уже есть в `src/attention.ts`
для своих MR, опрос состояния PR — в `src/teamwork-status.ts`; обе переезжают в общий наблюдатель.

Нет доступа к хосту или тип ссылки неизвестен — дело всё равно заводится, но без наблюдателя, с пометкой «состояние не
отслеживается» и причиной.

### 3.2 Дело

```ts
type DeskItem = {
  id: string;
  key: string;                 // ключ вещи
  thing?: { type: string; ref: Record<string, unknown> };
  kind: string;                // свободный текст: «Ревью», «Jira», «Встреча», «Забытое», «Своё»
  title: string;
  project?: string;            // слаг пространства
  column: 'new' | 'plan' | 'work' | 'waiting' | 'done';
  why: string;                 // почему сейчас твой ход
  signals: Array<{ source: string; link?: string; author?: string; at: string; text?: string; replyTo?: Record<string, unknown> }>;
  due?: string;
  links: { runs: string[]; sessions: string[]; branch?: string; mr?: string };
  createdAt: string;
  movedAt: string;             // возраст в колонке
  movedBy: 'me' | 'watcher' | 'routine' | 'flow' | 'session';
  closed?: { at: string; reason: string };
};
```

Хранилище личное: `<configDir()>/desk/items.json` и журнал движений `desk/log.jsonl` (обрезается при записи). Задачи
Teamwork в хранилище не копируются: их отдаёт поставщик, см. этап 4.

**Одна операция** `put(key, patch, by)`: дела с таким ключом нет — завести; есть — добавить сигнал и применить правила
ниже. Плюс `close(key, reason, by)` и `list(filter)`.

**Правила движения.** Срабатывают только на изменение, один раз на каждое.

| Что произошло | Что с делом |
|---|---|
| Сигнал о вещи, по которой дела нет | Новое дело в колонке правила (по умолчанию «Новое») |
| Ещё один сигнал о той же вещи | Тот же элемент, сигнал в список. Из «Ждёт других» и «Готово» — в «В плане» |
| Наблюдатель: ход стал моим | Из «Ждёт других» — в «В плане», `why` обновлён |
| Наблюдатель: ход стал чужим | Из «В плане» и «В работе» — в «Ждёт других» |
| Наблюдатель: вещь закрыта | В «Готово» |
| С карточки начат запуск или сессия | В «В работе», ссылка в `links` |
| Запуск по делу закончился | Колонка та же, `why`: «агент закончил: …» или «запуск упал: …» |
| Перенос руками | Держится до следующего изменения вещи |

### 3.3 Кто я

Профиль в настройках: имена и почты, логин GitLab и GitHub, id пользователя Slack, почта Jira. Нужен, чтобы отличать
«обращено ко мне» в Slack, «мои обещания» во встрече, «моя реплика» в MR. Что можно взять само (glab, gh, git config,
Jira из «Подключений») — берётся само; остальное одно поле.

### 3.4 Сверка

У каждого источника и наблюдателя на диске лежит итог последней проверки:

```ts
type CheckResult = { at: string; ok: boolean; total: number; fresh: number; error?: string; emptySince?: string };
```

Состояния для человека: «проверено 09:12, 14 записей, 2 новых», «проверено, пусто 6 дней — обычно 3 в день», «сломано:
ключ не принят», «не проверялось с запуска приложения». Строка «N из N» над доской собирается из этих записей и не
хранит ничего своего.

## 4. Команды работают по-разному

Фундамент не предполагает один способ работы. Таблица — проверочный список: каждый вариант должен работать без правки кода,
настройкой правила.

| Что различается | Варианты | Чем закрыто |
|---|---|---|
| Где просят ревью | назначают ревьюером в GitLab или GitHub; кидают ссылку в канал Slack; пишут в личку; отвечают в треде; упоминают в MR; приходит письмо; задача Jira переходит в «Review» | Сигнал из любого источника + разбор ссылок. Все варианты дают один ключ `mr:…` и одно дело |
| Попросили и там, и там | назначили в GitLab и продублировали в Slack | Второй сигнал ложится в то же дело; на карточке видно оба |
| Где автор отвечает | в обсуждениях MR; в треде Slack «поправил, глянь» | Ход считает наблюдатель MR; ответ в треде — сигнал с той же нитью, возвращает дело в план |
| Куда писать, что посмотрел | комментарий в MR; ответ в тред | `reply.to: source` отвечает туда, откуда пришёл сигнал (уже есть в рутинах) |
| Попросили без ссылки | «глянь мой MR по оплатам» | Дело-разговор без наблюдателя; flow или ты сам привязываешь вещь, дело получает ключ MR |
| Как связаны задача, ветка и MR | ключ задачи в имени ветки; в заголовке MR; никак; одна ветка на несколько задач | Связь ищется по ключу в ветке и заголовке и по запуску или сессии, начатым с карточки; не нашлась — привязка руками; дело работает и без неё |
| Как ведут ветки | MR на задачу; коммиты прямо в основную ветку; форки; цепочки MR | Наблюдатель ветки смотрит «грязно» и «впереди без MR» относительно upstream; MR не обязателен |
| Что значит «готово» | MR смержен; задача закрыта в Jira; выкатили; поставили ✅ в Slack | Поле `close` правила: по умолчанию — закрытие вещи, иначе условие или «только руками» |
| Хост без доступа | ссылка на GitLab, где не выполнен `glab auth login` | Дело без наблюдателя, причина на карточке и в сверке |

## 5. Что найдено после замечания про Slack

Эти проблемы в аудит не попали; все входят в этапы ниже.

1. Источник Slack читает только каналы (`types: public_channel,private_channel`, `src/routines/sources/slack.ts:121`).
   Лички и групповые лички не читаются.
2. Ссылка внутри сообщения не разбирается: событие Slack — просто текст. Его нельзя ни склеить с сигналом GitLab о том же
   MR, ни закрыть по мержу.
3. Виденное считается отдельно по каждому источнику (`engine.ts`, `ingest`). Один MR, пришедший из GitLab и из Slack,
   сегодня даёт два запуска и две карточки.
4. Ответ в треде под просьбой — отдельное событие без связи с просьбой. Понятия «продолжение того же разговора» нет.
5. Для Slack «я» — владелец токена. С токеном бота упоминание человека не распознаётся: нужен id пользователя из профиля.
6. Вид `review` у forge видит только MR, где я назначен ревьюером (`forge.ts:62`). В команде, где ревьюера не назначают,
   источник пуст, а статус у него «ок».
7. «Ждут ответа» считается только для своих MR (`src/attention.ts`). Для MR, который я ревьюил без назначения, «автор
   ответил» узнать нечем.

## 6. Этапы

Порядок жёсткий: каждый этап опирается на предыдущий. Внутри этапа пункты независимы и делаются параллельно.

### Этап 0. Починки, которые мешают уже сейчас

Не зависят от дел. После этапа рутины перестают молча ломаться.

### Этап 2. Вещи и наблюдатели

Новый модуль `src/things/`. После этапа приложение знает состояние вещей — ещё без дел.

| # | Что | Где |
|---|---|---|
| 2.1 | Контракт: ключи, `ThingState`, интерфейс наблюдателя | `src/things/types.ts` |
| 2.2 | Разбор ссылок: сигнал → вещи. У события рутины появляются поля `things` и `thread` | `src/things/resolve.ts`, `src/routines/types.ts`, `engine.ts` |

### Этап 3. Дело

Новый модуль `src/desk/`. После этапа дела существуют, заводятся отовсюду и ходят сами. Доски ещё нет: дела видны в
существующих блоках Главной.

| # | Что | Где |
|---|---|---|
| 3.1 | Хранилище, `put` / `close` / `list`, правила движения (3.2), журнал | `src/desk/` |
| 3.2 | Сверка: наблюдатели обходят вещи открытых дел и применяют правила; после простоя и отпуска — та же сверка, без клика и без запуска flow на каждое событие | `src/desk/reconcile.ts` |
| 3.3 | Блок `task` в правиле рутины (ниже); `run` становится необязательным — рутина может только заводить дела | `src/routines/types.ts`, `schema.ts`, `engine.ts`, редактор |
| 3.4 | Первый опрос источника у рутины с `task` заводит дела по текущему списку, а не только запоминает | `engine.ts` |
| 3.5 | Инструменты сессии `desk_put`, `desk_close`, `desk_list` в сервере `agentgraph` (образец — `team_task_update`); сессия, проект и ветка подставляются сами | `src/sessions-mcp.ts` |

| 3.7 | Командная строка: `agentgraph desk add`, `list`, `close` | `src/cli.ts` |
| 3.8 | Ожидание рутины с `task` — это дело в «Новом» с кнопкой «Запустить»; «Не сейчас» — перенос в план. Ожидания рутин без `task` работают как раньше | `engine.ts`, `web/src/screens/home/RoutineWaits.tsx` |
| 3.9 | «Проверка на истории» показывает строки «дело / в план / закрыто» | `engine.ts`, `RoutineEditor.tsx` |
| 3.10 | Блок своих MR и «Не доделано» на Главной читают дела; вид не меняется | `web/src/screens/home/Attention.tsx`, `Review.tsx` |

Блок правила:

```yaml
task:
  kind: Ревью            # свободный текст
  column: new            # куда класть новое
  from: event            # event — событие и есть дело; flow — дела заводит flow инструментом
  same: thing            # что считать тем же: thing | thread | event
  on_repeat: plan        # пришло новое по тому же: plan | keep
  close: thing           # thing — когда вещь закрыта; never — руками; или условие словами
```

По умолчанию `same: thing`, если в событии распознана вещь, иначе `thread`, иначе `event`.

Готово, когда: рутина «ревью из Slack» и рутина «ревью из GitLab» на один MR дают одно дело; автор ответил — дело
вернулось в план; MR смержен, пока приложение было закрыто, — после открытия дело в «Готово» без единого клика.

## 7. Чего не делаем

- Перевод статуса задачи в Jira. Дело подсказывает «MR смержен — закрой PROJ-12»; переход — позже.
- Вебхуки. Как и в рутинах: только опрос и живые соединения.
- Замечания к строкам кода от имени пользователя. Ответ рутины — один комментарий или ответ в тред.
- Закрытие по реакции в Slack. Проверочная таблица (раздел 4) оставляет для этого поле `close`; сам признак — после этапа 5.
- Общая доска на команду. Дела личные; командное — в Teamwork.

## 8. Как ведём разработку

- Общая ветка `desk`. Этап — своя ветка от неё; сливается после ревью и проверки критериев «Готово, когда».
- В начале этапа пишется его план: `docs/desk/plan-<N>.md` с таблицей владения файлами и контрактами между сессиями,
  по образцу [../teamwork/plan.md](../teamwork/plan.md). Контракт типов — первым коммитом этапа.
- Сессии одного этапа работают параллельно в своих worktree и правят только свои файлы.
- Каждая сессия: скиллы `agentgraph-core`, `agentgraph-web`, `agentgraph-tests`; `npm run typecheck && npm test`, для
  `web/` — `npm run build:web`; новое поведение — с тестом рядом с модулем.
- Этап закрывается, когда: критерии выполнены, e2e на главный сценарий этапа проходит, независимое ревью
  (`code-reviewer`) без серьёзных замечаний, поведение проверено в браузере.
- Контракты (`src/routines/types.ts`, `src/api-types.ts`) только дополняются. Изменение существующего поля — с правкой
  соответствующей спеки.
- После каждого этапа спека перечитывается: что узнали, что меняется в следующих этапах.
