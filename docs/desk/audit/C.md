# C. Рутины как двигатель центра дел

Смотрел текущее рабочее дерево, включая незакоммиченные правки (`ask` в engine/routes/types, «Спросить Claude» в LogWhy).

---

## 1. Сценарии

### 1.1 Встреча → дела (Fireflies → flow → дела на меня)

**Шаги пользователя (день 1):** подключить Fireflies → собрать рутину «новая встреча → flow meeting-to-tasks» → проверить на истории → включить → утром смотреть дела со сроками.

**Что уже есть**
- Два способа достать встречи:
  - готовый рецепт `templates/sources/fireflies.yaml`: `command` + curl GraphQL `transcripts(limit: 20) { id title date duration transcript_url organizer_email }`, ключ `FIREFLIES_API_KEY`. Текста, саммари и action items в запросе нет, поэтому `text` события пустой;
  - «Сервис через Claude» (`src/routines/sources/connector.ts`): модель один раз собирает скрипт из вызовов MCP, дальше проверка идёт без модели через `mcp_call` (`src/mcp-call.ts:20-36`). Каждая встреча становится событием, текст режется до 4000 знаков (`connector.ts:23`), записей за проверку не больше 50 (`connector.ts:22`).
- Шаблон пустого списка «Встреча закончилась → задачи и итог» (`web/src/screens/routines/RoutinesList.tsx:26`). Под него берётся *первый попавшийся* источник не из стандартных видов (`NewRoutine.tsx:36`), то есть это может оказаться Sentry или Linear. Flow `meeting-to-tasks` в репозитории нет (`flows/` — только example, Kai, micro-business). Имя встречается только в тестах (`web/src/lib/routines/routines.test.ts:138`).
- Flow получает событие, приписанное к задаче (`server.ts:305`, `engine.ts:1479`). Транскрипт целиком этап может дочитать сам, если перечислит инструменты коннектора Fireflies в `tools` (`src/connectors.ts:1-3`, `agent.ts:296-300`).
- Дедупликация по `id` события на источник (`engine.ts:417-425`, `store.ts:15` SEEN_MAX 2000). Самый первый опрос только запоминает виденное (`engine.ts:436`).
- Расписание (`when.schedule`) тоже есть, но событие расписания пустое (`scheduleEvent`), и всё делает flow. В «Проверке на истории» расписание ничего не показывает (`engine.ts:1122`).

**Что добавит центр дел:** этап flow «завести дело» (N дел из одной встречи) и «почему сейчас твой ход» = обещание со встречи.

**Где рвётся**
1. **Завести дело некуда.** В MCP сессий `agentgraph` нет такого инструмента (`src/sessions-mcp.ts:71-197`: знания, документы пространства, flow, сессии, Teamwork). Flow может только написать итог (`digest`), а он уходит в ответ наружу или в карточку (`engine.ts:726`, `server.ts:1435`).
2. **Одна встреча = много дел.** Модель рутины такая: одно событие → один запуск → одна строка журнала (`types.ts:223-241`). В журнале и в «Проверке на истории» видно «запустилось бы K из N» (`RoutineEditor.tsx:468`), но не видно, сколько дел из встречи получится. Строка правила «Завести дело: как [вид] в [колонку]» из RulePult исходит из того, что одно событие = одно дело. Для встречи это не так: дела рождает flow, а не правило.
3. **Срок из текста.** «До пятницы» считается от `event.at`. У рецепта это `date` встречи, и это правильно. Но у «Сервиса через Claude» без правила `at` время подставляет agentgraph (`connector.ts:233` `stampAt`). После «догнать» (возврат из отпуска) относительные сроки посчитаются от дня обработки, а не от дня встречи.
4. **Чьё дело.** Понятия «я» для встречи нет. `author` = `organizer_email` (рецепт), в настройках есть только Jira email (`src/settings.ts:20`). Чтобы отобрать «мои» action items, flow должен как-то знать имя или почту пользователя. Сейчас это только текст в `run.input`.
5. **Пропуск встреч из-за `{{since}}`.** Сборщик советует фильтровать по времени прошлой проверки (`connector.ts:401`). Курсор = начало опроса − 1 мин (`connector.ts:275`). Транскрипт Fireflies готов через десятки минут после встречи, а её дата — время начала. Если аргумент фильтрует по дате встречи, встреча, обработанная позже курсора, не попадёт ни в одну проверку. Ошибкой это не считается, источник остаётся «ok».
6. **Повторяющиеся встречи как «дубль».** Если у рутины есть «Если», haiku проверяет «тот же предмет, что недавние» (`check.ts:35`, 20 последних, `check.ts:13`). Еженедельный «Billing sync» с тем же названием легко уйдёт в `duplicate`. Без «Если» дубли не ищутся вообще.
7. **Лимит записей.** Рецепт берёт `limit: 20` без фильтра по времени. Если за отпуск прошло больше 20 встреч, старшие пропадут молча, а «догнать» покажет только то, что пришло (`engine.ts:805-827`).
8. Каждая встреча в режиме `suggest` (по умолчанию для источника, `NewRoutine.tsx:58`) даёт отдельную карточку на главной (`engine.ts:480-494`). Это ещё одна очередь рядом с доской.

**Оценка: не закрыто.** Встречи достаются, flow запускается, но дело из результата flow не заводится. Срок и «чьё» flow решает сам, без опоры в продукте.

### 1.2 Сборка новой рутины с нуля

**Шаги:** NewRoutine (4 шага) → «Другой сервис…» → ConnectSource (3 вкладки) → назад в NewRoutine → «Проверить и включить» (черновик) → RoutineEditor + «Проверка на истории» → «Включить» → «Срабатывания» (RoutineLog, LogWhy).

**Что есть**
- Источник подключается словами, из готовых или своей командой. Пробная проверка показывает «нашёл N» и 3 записи (`types.ts:132-141`, `engine.ts:1341-1365`). Для коннектора есть сборка с повтором и ловля «бессмысленных заголовков» (`connector.ts:488-498`, `542-581`).
- Шаг 2 показывает «последнее, что пришло» (`NewRoutine.tsx:227`) и честно пишет, что эти записи не запустятся (`:267`).
- В редакторе «Проверка на истории»: «Запустилось бы K из N», «≈ N запусков / $ в неделю», «Что получит flow» (`RoutineEditor.tsx:404-507`, `engine.ts:1114-1196`).
- «Срабатывания»: чипы по исходам, «за 7 дней · $» (`RoutineLog.tsx:44-55`). LogWhy объясняет условия, «Если», ответ проверки, «Проверить на этом событии» и «Сохранить “Если”», а в новых правках ещё «Спросить Claude» (`LogWhy.tsx:22-169`, `engine.ts:1260-1274`).

**Где непонятно или лишнее**
1. Поле «Задача для flow» в NewRoutine есть только у расписания (`NewRoutine.tsx:213-216`). У источника его нет в шаге 3 (`FlowStep`, `:272-315`), оно появляется только в редакторе (`RoutineEditor.tsx:275`). Для встречи как раз задача («вытащи мои обещания со сроками, я — …») главная.
2. «Проверить и включить» на самом деле не проверяет и не включает: сохраняет черновик (`NewRoutine.tsx:96`, `:177`). Включение — второй экран. После «Включить» редактор уводит на список (`RoutineEditor.tsx:86`), и «Срабатывания» новой рутины надо искать.
3. «Собрать новый flow…» нажимает кнопку в сайдбаре через DOM (`NewRoutine.tsx:41`, `:285`). Для «встреча → дела» flow почти всегда новый, а пути «собрать flow под эту рутину с этим событием как примером» нет.
4. «Проверка на истории» проверяет только отбор. Что flow сделает с событием, не видно без настоящего запуска («Запустить сейчас», `engine.ts:1095-1111`). Для расписания проверка пустая (`engine.ts:1122`).
5. Шаблон «meeting» сам выбирает чужой источник (см. 1.1).

**Чего не хватает для строки «Завести дело» (RulePult)**
- В `RoutineSpec` нет поля под дело (`types.ts:185-208`): только `run`, `mode`, `reply`, `limits`. Нужен блок вроде `task: { kind, column, key, onNew: 'back_to_plan', closeWhen }`.
- **Ключ «то же самое»:** `id` события уникален на каждое изменение (Jira `key@updated`, `jira.ts:86`; GitLab `comment:…:noteId`, `forge.ts:85`). Для «пришло новое по тому же MR → вернуть в план» нужен ключ сущности. В полях он есть (`fields.ref`, `project`, `number` в `forge.ts:32`), но движок им не пользуется.
- **«Закрыть, когда MR смержен»:** источник GitLab берёт только `state=opened` (`forge.ts:62`, `:78`). Смерженный MR просто пропадает из ответа, а у движка нет понятия «запись исчезла» (только `seen`, `engine.ts:417-425`). Закрывающего события нет.
- В «Проверке на истории» нет строк «дело / в план / закрыто» из макета: `HistoryCheck.events[].outcome` знает только started/waiting/filtered/check_no/duplicate (`types.ts:332-348`).
- Режимы «Ждать меня» (`suggest`) и колонка «Новое» на доске делают одно и то же. При строке «Завести дело» `suggest`-карточка на главной не нужна.

**«Источник проверен, нашёл N» — есть ли данные для сверки «N из N»**
- Есть: у источника `status` ok/error/idle/needs_secret, `error`, `lastCheckAt` (`types.ts:117-129`). Список показывает «проверен HH:MM» (`RoutinesList.tsx:214`).
- Нет: **сколько нашла проверка** (вернулось всего / новых). `pollSource` число не сохраняет (`engine.ts:342-346`), `total` есть только у пробной проверки (`engine.ts:1359`).
- Статус и ошибка живут в памяти (`engine.ts:113`, `:130`). После перезапуска до первого опроса упавший источник показан как `ok` (`engine.ts:977`). Персистентный `lastCheck` обновляется только при успехе (`engine.ts:346`).
- У расписания `lastCheck` двигается каждым тиком (`engine.ts:900`) и значит «движок жив», а не «рутина отработала».
- Отдельной строки «проверка прошла, 0 новых» в журнале нет (`LogOutcome`, `types.ts:212-221`), поэтому «молчит, потому что пусто» от «молчит, потому что сломано» не отличить.

**Оценка: частично.** Сборка и разбор срабатываний сильные. Строки «Завести дело» и данных для «N из N» нет.

## 2. Как это живёт через месяц (10+ рутин)

**Копится**
- Журнал: каждое отфильтрованное событие пишет строку (`engine.ts:465`). `appendLog` не обрезает файл (`store.ts:242-246`), обрезка до 2000 строк только в `updateLog` (`store.ts:249-257`). Файл больше 8 МБ (`store.ts:13`) `readRegular` отказывается читать (`safe-fs.ts:35`), и `logAll` молча возвращает `[]` (`store.ts:216-221`). Журнал «пуст», `per_day` считает 0 (`engine.ts:563`), а `updateLog` тоже больше не находит строк и не обрежет файл. Для шумного Slack с узким фильтром это реально за несколько недель.
- Карточки `suggest`/`pause`/`reply` на главной и в полосе ожиданий. «Не сейчас» прячет карточку, но хранит её бессрочно (`engine.ts:757-761`). Сроков жизни у ожиданий нет.
- История источника — 50 событий (`store.ts:17`). Через месяц LogWhy по старой строке пишет «текст события уже не хранится» (`LogWhy.tsx:83`).

**Шумит**
- OS-уведомление «запуск завершён» на *каждый* конец запуска, включая запуски рутин (`server.ts:1422`, `2187-2198`). На 10 рутинах это десятки уведомлений в день.
- Ложные срабатывания лечатся только через «Если» и «Зря запустилась». Без «Если» отметка ни на что не влияет (`LogWhy.tsx:159`).

**Молча не работает (самое опасное)**
- Источник отвечает, но пусто: протух токен, а сервис вернул текст без ошибки; фильтр `{{since}}` (см. 1.1-5); `limit`. Статус остаётся `ok`. Сигнала «N дней без событий» нет нигде.
- Ошибка источника видна только как «Источник молчит» в списке рутин (`view.ts:42`, `RoutinesList.tsx:132`). На главную она не выходит, OS-уведомления нет: уведомления шумят на успехе и молчат на поломке.
- Коннектор claude.ai отвалился (переавторизация) — ошибка `mcp_call`, тот же статус error. Подсказки «переподключи на claude.ai» нет.
- Расписание работает, только пока открыто приложение (`NewRoutine.tsx:217`). Пропуски уходят в «догнать» (`engine.ts:860-921`), но на главной это одна строка, без «N из N».

**Лимиты и стоимость в понимании пользователя**
- Видно: «сегодня N запусков · $» (`view.ts:194-201`), «за 7 дней · $» по рутине (`RoutineLog.tsx:54`), оценка в неделю в проверке на истории.
- Не видно:
  - стоимость опроса источника в режиме `model` (haiku раз в 30 мин, до $0.5 за опрос, `connector.ts:20`, `:302`). Она кладётся в `fields.costUsd` события (`connector.ts:326`) и нигде не суммируется;
  - стоимость проверки словами у *подошедших* событий: при запуске строку перезаписывает `costUsd` запуска (`engine.ts:720`);
  - общий расход «все рутины за неделю/месяц» и доля 5-часового лимита.

**Что чистить руками:** отложенные ожидания, «догнать» после отпуска (по строке на рутину), разросшиеся журналы, источники без рутин (`idle`).

## 4. Дубли и пересечения с центром дел

- **Карточки ожидания рутин (`suggest`, `pause`, `reply`) на главной** (`HomeScreen.tsx:73-100`, `RoutineWaits.tsx`) и колонка «Новое» на доске — одно и то же «ждёт твоего решения». При строке «Завести дело» `suggest` становится лишним: событие сразу становится делом в «Новое». Пауза перед блоком = дело «В работе / ждёт меня».
- **«Догнать»** (`engine.ts:805-853`) и сверка «N из N + вернулся после отпуска» должны слиться: пропущенное — это строка сверки по источнику, а не отдельная лента.
- **Полоса ожиданий и статусы источников в /routines** (`RoutinesList.tsx`) дублируют сверку над доской. Список рутин остаётся местом настройки, а «работает ли» переезжает в сверку.
- **«Ответить в источник» с черновиком** (`reply.draft`) пересекается с делом «Ждёт других» / «ответить автору». Это одна карточка, а не две.
- **Teamwork-задачи** (`server.ts:1438-1441` двигает задачу Teamwork по концу запуска) — вторая модель «задача ходит сама». Дело на доске и задача Teamwork должны быть одной ссылкой, а не двумя карточками.
- **«Сегодня N запусков · $» в шапке рутин** (`view.ts:194`) пересекается с недельным ритмом и стоимостью в центре дел. Лучше одна сводка расхода.
