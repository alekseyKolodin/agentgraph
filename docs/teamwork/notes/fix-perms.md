## Модель доверия к flow команды (S-1) и почему так

Flow команды — YAML в общем репо: его пишет любой с push, а выполняется он у каждого участника с его правами (`type: command` в
условиях — shell без всякого guard'а, инструменты этапа разрешены без вопроса). Поэтому граница — **содержимое**, а не автор и не имя:

- **Одобрение по хэшу.** Flow запускается, только если sha256 его текста (CRLF → LF, чтобы `core.autocrlf` не делал версию
  «другой») одобрен на этом компьютере. Без вопроса одобрены: (1) текст, совпадающий с любым flow из `templates/teamwork/flows/`
  самого agentgraph (под любым именем: это содержимое поставили мы); совпавшая версия запоминается в `trust.json` (`via: template`),
  чтобы новая версия шаблона после обновления agentgraph не сделала нетронутый flow команды «чужим» и люди не привыкали жать
  «Доверять» не глядя; (2) версия, которую пользователь сохранил на вкладке «Процесс» (одобряется текст, который он отправил, а не
  файл после записи — его мог переписать pull; если в редактор пришла неодобренная версия коллеги, «Сохранить» сначала показывает её
  дифф). Остальное — кнопкой «Доверять этой версии» в диалоге.
- **Где хранится.** `teams/<slug>/trust.json` рядом с `local.json`: `{ flows: { <имя>: { sha256, yaml, at, via } } }`. Ориентир брифа —
  поле в `local.json`; отдельный файл выбран сознательно: `readLocal` в `teamwork-repo.ts` (файл сессии данных) отбрасывает неизвестные
  поля, `local.json` переписывается каждой синхронизацией, а одобрение не должно зависеть от чужого рефакторинга. Безопасность та же:
  вне `repo/`, git туда писать не может (клон с `core.symlinks=false`), агентам запись в папку команд закрыта guard'ами. Текст
  одобренной версии хранится, чтобы дифф следующей шёл от неё. Одобрение — по имени flow: одобренный `a` с тем же текстом не
  одобряет `b`. Отключение команды удаляет файл вместе с папкой.
- **Одна точка проверки.** `TeamService.readTeamFlow` — единственный путь, которым YAML команды попадает в раннер: черновики
  документа и раздела, разбивка, повтор черновика (`TeamDrafts.start`) и «В работу ▸» (`POST /api/runs` с `teamFlow`). Схема → запреты
  (400 `flow_forbidden`) → доверие (409 `flow_untrusted`). Хэш и `spec` берутся из одного прочитанного текста — подменить файл между
  проверкой и запуском нельзя. Продолжение и повтор запуска берут снимок `flow.yaml` запуска — версию, одобренную на старте.
  Вкладка «Процесс» (`GET …/flows/:name`) показывает `trust`/`problems`, но сама ничего не запускает; `intake` читает только `input`.
- **409 и одобрение.** Тело — `{ error, code: 'flow_untrusted', flow: TeamFlowTrust }`: YAML, хэш, база диффа (одобренная здесь версия,
  иначе шаблон с тем же именем, иначе нет — «новый flow»), shell-команды условий (`until` и `next`) и инструменты с shell, записью и
  сетью. `POST /api/teams/:t/flows/:name/trust { hash }` одобряет **ровно увиденный хэш**: если pull успел принести другую версию —
  409 с ней, ничего не записано.
- **UI.** `useFlowTrust()` (`web/src/screens/teamwork/FlowTrust.tsx`): `guard(запуск)` ловит 409 `flow_untrusted`, показывает диалог,
  после «Доверять» повторяет запуск; «Отмена» — `undefined`, запуска нет, форма остаётся как была. Shell-команды — отдельным блоком над
  диффом, фокус по умолчанию — на «Отмена» (Enter не одобряет чужой flow не глядя). Пока смотрели, flow поменялся — диалог сам
  показывает новую версию. Подключено в «Черновик с агентом…»/«С агентом…» (`AgentAsk`), «Повторить» черновика (`DocTab`), «Разбить ТЗ»
  и «Повторить черновик» разбивки (`SplitStart`), «В работу ▸» (`ToWork`); на «Процессе» — строка «Эту версию на этом компьютере не
  одобряли» с «Посмотреть изменения…» и список запретов.

### Что flow команде нельзя вовсе (защита в глубину)

Одобрение — один барьер, и люди нажимают «Доверять» не читая. Поэтому то, что у общего flow не имеет законного применения, запрещено
независимо от одобрения (`teamFlowProblems`, 400 `flow_forbidden` и при запуске, и при сохранении на «Процессе»; одобрить нельзя):

| Возможность | Почему нельзя |
|---|---|
| `plugins` (блок, этап) | путь к плагину этого компьютера; плагин приносит хуки и MCP-серверы — исполнение мимо guard'ов |
| `add_dirs` | папки этого компьютера (`~`); из них грузятся `CLAUDE.md` и скиллы; папки проекта и репо agentgraph добавит сам |
| `knowledge` блока | теги знаний этого компьютера — чужой flow вытягивал бы мои заметки в промпт |
| блок-вызов `flow:` | зовёт мой локальный flow (с моими режимами и плагинами) с задачей, которую собрал чужой flow |
| `permission_mode` кроме `default`/`plan` | `bypassPermissions`, `acceptEdits`, `dontAsk`, `auto` снимают вопросы с чужого flow; проверено и в `defaults` |
| инструменты вне `KNOWN_TOOLS` (+ `Agent`, `Skill`) | `mcp__…` и коннекторы claude.ai (`mcp__claude_ai_Slack__…`) разрешились бы без вопроса — письма и сообщения от моего имени |
| невидимые и управляющие символы в тексте (`teamFlowTextProblems`) | bidi-переключатели, zero-width и одинокий `\r` показали бы в диалоге одно, а выполнили другое; табуляция, CRLF и BOM в начале — можно |

**Разрешены, но видны в диалоге:** `type: command` и инструменты Bash, Write, Edit, WebFetch, WebSearch. Без них не обходится flow
задачи (`teamwork-task` шаблона даёт Bash, а «пока тесты не пройдут» — главный приём agentgraph). При Bash в инструментах запрет
`command` ничего бы не дал: исполнить shell можно и промптом. Поэтому решающим остаётся одобрение содержимого, а диалог выносит
команды и опасные инструменты наверх. Шаблоны agentgraph ни одного запрета не нарушают (тест).
