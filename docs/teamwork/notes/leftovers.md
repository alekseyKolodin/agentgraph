### 2. D-14 в сессии: номер задачи у `team_task_update` и `team_doc_write`

- `TeamService.workTask(team, { kind, id })` — номер задачи, у которой в `local.json → work` записан запуск или сессия (тот же
  поиск, что был в адаптере `statusService`; адаптер теперь зовёт его).
- `sessionTeamwork` (`src/teamwork-work.ts`): `team_task_update` меняет задачу, у которой записана эта сессия, а не номер со
  старта. Номер ищет сам сервис **внутри очереди записей клона** (`TaskWriteOptions.work` у `updateTask`/`changeTask` и
  `addComment`): синхронизация, которая стоит в очереди в момент вызова и переименует задачу, не уведёт запись в чужую (это
  нашло ревью — первая версия искала номер до очереди). Записи нет нигде (задачу удалили, старт не записался) — 404 «задачи …
  больше нет среди работы этой сессии … измени задачу в agentgraph руками», а не запись в задачу со старым номером (как
  `ended()`, который в этом случае ничего не трогает).
- `TeamworkStatus.started` пишет работу в `local.json` сразу, а не в цепочке за прошлым стартом той же задачи (тот может ждать
  очередь клона): иначе инструменты второй сессии по задаче получали бы временный отказ.
- `team_doc_write` пишет документ проекта как раньше (номер задачи на него не влияет), номер в сообщении коммита — текущий, без
  записи — номер со старта. Подпись задачи в вопросе PreToolUse (`label`) — тоже по текущему номеру; без записи — номер без
  заголовка.
- Для этого `SessionTeamwork.updateTask` и `label` получили id сессии (`src/sessions-server.ts`, точечно: тип и два места
  вызова).
- Описание инструментов MCP («Изменить задачу Teamwork PAY-12 …», `sessions-mcp.ts`) по-прежнему с номером со старта: список
  инструментов Claude Code читает один раз на старте сессии, поменять его посреди сессии нечем. Модель видит новый номер в
  ответе инструмента («Задача PAY-14: …»).
- Тест: `teamwork-server.sync.test.ts` → «D-14: сессия по моей задаче после переименования совпавшего номера …» на клонах
  alice и bob с общим bare-репо: bob начинает сессию по своей неотправленной задаче, alice отправляет задачу с тем же
  номером в тот же проект, после синхронизации у bob задача переименована; `team_task_update` ставит статус и комментарий
  его задаче под новым номером, задача alice со старым номером не тронута, подпись вопроса — новый номер, коммит
  `team_doc_write` — с новым номером, неизвестная сессия — отказ. Инструмент вызывается, пока идёт синхронизация, которая
  переименует задачу. Тест падает и на коде до правки, и на варианте с поиском номера до очереди.
  `teamwork-status.test.ts` → «D-14: вторая сессия по задаче записывается в work сразу …».

### 5. `.claude` в папках проектов не выгружается в клон

- **Выбор — sparse-checkout без cone.** Правила `/*` и `!/[pP][rR][oO][jJ][eE][cC][tT][sS]/**/.[cC][lL][aA][uU][dD][eE]` (файл
  или папка, на любой глубине, в любом регистре — и `.claude`, и `projects`, не полагаясь на `core.ignorecase`). Файлы остаются в индексе
  (skip-worktree) и в репо команды, поэтому rebase, перепроигрывание (временный индекс, `read-tree`/`write-tree`), `reset
  --hard`, fast-forward и `add -A` их не удаляют и не выгружают — проверено руками на git 2.50 и тестами. Вариант «не принимать
  `projects/*/.claude/**` при синхронизации» отбросил: это переписывание чужих коммитов при replay и конфликт с
  перепроигрыванием.
- `TeamRepo.ensureSparse()`: пишет `info/sparse-checkout` и `core.sparseCheckout=true`, `core.sparseCheckoutCone=false` (в
  `config.worktree`, если в клоне включён `extensions.worktreeConfig` — так делает `git sparse-checkout`, запущенный руками),
  и применяет правила к рабочей копии `read-tree -mu HEAD` раз за процесс. Зовут запись и синхронизация после `recover()` и
  `commitManual()` (ошибку глотают и пробуют снова), а создание и подключение — сразу после клона.
- Клон делается с `--no-checkout` и выгружается уже по правилам: `.claude` на диск не попадает ни на миг.
- Клон старой версии сервис переводит на правила сразу при первом открытии (`needsSparse` → `prepareSparse` в очереди:
  `recover`, правки руками коммитом, затем `ensureSparse`; read-tree до коммита правок вернул бы их к HEAD), а не получилось —
  при первой записи или синхронизации.
- `.claude`, созданная в папке проекта клона руками, не коммитится: каждый `add -A` клона идёт с исключающим pathspec
  `:(exclude,glob,icase)projects/**/.claude[/**]` — не зависит от ignore-файлов, так что `.gitignore` команды с `!.claude` не
  делает её коммитом и не роняет запись; `info/exclude` получил ту же строку, чтобы она не мелькала в статусе. `commitManual`
  не коммитит, если после `add` в индексе пусто. Такая папка на диске остаётся, и `teamsAddDirProblem` (`teamwork-trust.ts`)
  по-прежнему не даёт её агенту — на старте и перед каждой сессией этапа; текст отказа называет оба случая: пришла из репо
  команды — синхронизируйте, agentgraph уберёт её сам; положили руками — удалите.
- «Взять моё» у конфликта по файлу в `.claude` папки проекта (бывает только у клона старой версии) — 400 с объяснением: запись
  мимо правил не закоммитилась бы, и моя версия пропала бы молча.
- **Человеку видно.** `TeamRepo.projectClaude(project)` (`git ls-files` по папке проекта) → `TeamProject.claudeSkipped`
  (`src/api-types.ts`); на «Обзоре» проекта блок «Не применяется из репо команды»: «В папке проекта есть .claude. agentgraph не
  выгружает это в клон: скиллы, сабагенты и плагины из репо команды агентам не достаются — их пишут участники мимо доверия к
  flow. Правила проекта для агентов задают в CLAUDE.md.»
- Тесты (`teamwork-repo.sync.test.ts`, раздел §14, по поведению на тест): коллега без agentgraph кладёт `.claude/skills`,
  `docs/deep/.Claude` и `Projects/p/.CLAUDE` (другой регистр, через `update-index`) — их нет на диске после перепроигрывания (и
