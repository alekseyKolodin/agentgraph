# agentgraph: справочник

> Обзор и демо — в [README](../README.md). Впервые здесь? Начни с [GETTING_STARTED.md](GETTING_STARTED.md): как это работает, установка, первый запуск, развёртывание и как поделиться проектом. Ниже полный справочник.

Задача → `flow.yaml` → цепочка сессий Claude Code, зацикленная до выполнения условия.

Идея:

1. Ты кидаешь описание задачи.
2. **Генератор** (сессия Claude без инструментов) превращает его в спецификацию flow: этапы (`phases`), промпты этапов, инструменты каждого этапа, условие остановки.
3. **Раннер** исполняет спецификацию: каждый этап = свежая сессия Claude Code со своим промптом, куда подставлен вывод предыдущего этапа. После прохода всех этапов проверяется условие; если оно не выполнено, идёт следующая итерация, а замечания условия попадают в промпты.
4. Flow может состоять из нескольких **блоков** подряд: цикл до условия, потом шаги в один проход, потом снова цикл со своим условием (см. «Несколько блоков подряд»).
5. Кроме текста выводов этапы могут вести общие **артефакты запуска**: именованные файлы (план, чек-лист, решения), которые переживают итерации и блоки, защищены правами этапов и правятся пользователем в UI между шагами (см. «Артефакты запуска»).

Под капотом `@anthropic-ai/claude-agent-sdk`: та же авторизация, что у твоего `claude`, те же инструменты (Read/Edit/Bash…), сессии видны в `claude --resume`.

## Установка

```bash
npm install
npm run build
```

Запуск в dev-режиме без сборки: `npm run agentgraph -- <аргументы>`. Чтобы команда `agentgraph` была доступна глобально: `npm link` (после `npm run build`).

## Веб-интерфейс

```bash
npm run ui            # http://127.0.0.1:4747
```

UI — React-приложение из `web/`: `npm run ui` сам собирает его в `dist/web`, если сборки нет или `web/` изменился, и сервер раздаёт его на `/`. Адреса экранов — обычные пути: `/flow/<имя>`, `/run/<id>`, `/tags`, `/tags/<slug>`, `/context`, `/draft`; на любой из них сервер отдаёт `index.html`, неизвестный путь ведёт на главную. Старые ссылки продолжают работать: `/#run/<id>`, `/#flow/<имя>`, `/#tags/<slug>`, `/#context` прежнего интерфейса UI сам переводит на пути, а `/next/…` (адрес UI во время перехода на React) сервер отправляет на `/…` ответом 308.

Слева пункты «Главная» и «Контекст», список flow и история запусков, справа выбранный flow. Клик по flow в списке, ссылка `/flow/<имя>` и «Открыть flow» со страницы запуска открывают вкладку «Запуск»; только что созданный flow открывается в конструкторе, flow с невалидной спецификацией — на YAML:

- **главная** (первый пункт слева «Главная», логотип «agentgraph» или адрес `/`): вопросы агентов со всех идущих запусков в одном списке, сначала те, что ждут дольше. Отвечать можно прямо там, не открывая запуск; недописанный ответ не сбрасывается, пока приходят события других запусков. Ниже идущие запуски: полоска блоков, текущий блок, итерация и этап, сколько идёт и сколько стоит, кнопки «Открыть», «Пауза»/«Возобновить», «Остановить». Число вопросов, ждущих ответа, видно в заголовке вкладки («(2) agentgraph», на странице запуска — «(2) <имя запуска> · agentgraph») и на пункте «Главная» слева, на любом экране. «Включить уведомления» включает уведомления браузера о новых вопросах и о конце запуска; кнопка есть, пока браузер не спросил разрешение, а если разрешение запрещено, вместо неё стоит пометка «Уведомления выключены» (почему — в подсказке). Уведомления приходят, когда вкладка не на виду; если вкладка на виду, но открыт другой запуск или flow, внизу справа всплывает подсказка, клик ведёт на главную. Если ни одна открытая вкладка сама уведомления не покажет (UI закрыт или уведомления браузера не включены), о вопросе и конце запуска сообщает сервер системным уведомлением — см. «Уведомления» ниже. В шапке главной — **лимиты подписки Claude**: доля 5-часового и недельного окна и время сброса, как в `/usage` Claude Code (`GET /api/limits`; сервер берёт их через Agent SDK без обращения к модели и кэширует на минуту, `?force=1` — без кэша). Полоска желтеет с 70%, краснеет с 90%; клик — обновить. С ключом API, Bedrock или Vertex лимитов подписки нет, и блок не показывается. Справа на главной — окно **«События»**: лента того же, о чём приходят уведомления (вопрос агента и ответ на него, пауза по просьбе агента и возобновление, конец запуска со статусом и стоимостью), от новых к старым, по последним 50 запускам и всем идущим; видны первые 20 событий, остальные открывает «Ещё N». Лента строится из `run.json` (`GET /api/feed`), поэтому переживает перезагрузку вкладки и перезапуск сервера и видит запуски из CLI; скрытые запуски в неё не попадают. Новые с прошлой отметки «Отметить прочитанным» события подсвечены, их число — у заголовка (отметка хранится в `localStorage` вкладки). Клик по событию открывает запуск, по вопросу, который ждёт ответа, — его карточку на главной. На узком экране лента идёт сразу после вопросов и идущих запусков. Главная живёт на общем потоке событий всех запусков сервера (`GET /api/events`, SSE) и забирает состояние из `GET /api/home`;
- **контекст** (пункт «Контекст» слева, `/context`): что получит сессия до первого сообщения. Выбираешь директорию проекта (подсказки — те же недавние директории, что в форме запуска: директория по умолчанию, проекты из «Подключений», `cwd` и `addDirs` запусков; проекты, убранные из «Подключений», не показываются), при желании flow, этап и модель. Страница показывает memory-файлы с токенами (`~/.claude/CLAUDE.md`, CLAUDE.md проекта и `CLAUDE.local.md`, `.claude/rules/*.md`, CLAUDE.md из `add_dirs` этапа, auto-memory), скиллы и сабагенты с источником и токенами, MCP-серверы, системный промпт (стандартный preset `claude_code` или `system` этапа текстом), инструменты (`tools` этапа плюс неявные Agent и Skill; без этапа — все) и токены по категориям. С этапом учитываются его `add_dirs`, `tools`, `system` и модель (этап → `defaults` flow → выбранная модель). Если директории из `add_dirs` нет на диске, страница предупреждает об этом и продолжает работать. С этапом есть раздел «Промпт этапа по источникам» (`prompt` в ответе: `parts` с `kind` prompt / handoff / dirs / knowledge-lines / knowledge-inline, знаки до подстановок; `vars` — переменные шаблона; `chars`): шаблон промпта, handoff, список доп. директорий, строки тегов знаний по запросу одной частью и каждый тег целиком своей; раздел артефактов и вложения известны только в запуске и не входят. Предупреждения: теги целиком занимают больше половины промпта (и не меньше 2000 знаков), промпт больше 16000 знаков до подстановок, инструкции из четырёх и более источников (файлы памяти, теги целиком, свой системный промпт). Считает сам Claude Code через Agent SDK (`getContextUsage` на сессии без промпта, к модели не обращается), а опции сессии строятся тем же кодом, что у раннера, поэтому показанное совпадает с настоящим запуском. Каждый листинг поднимает процесс Claude Code (около секунды), сервер кэширует его на минуту; «Обновить» спрашивает заново. «Открыть» у CLAUDE.md и правил открывает редактор с превью markdown; «Сохранить» пишет файл и пересчитывает листинг. Если файл за это время изменили снаружи, сохранение отклоняется (409), «Перечитать» подтягивает версию с диска. Редактируются только `.md` из листингов этого сервера (сверка по realpath); managed-политики и всё из `~/.claude/plugins` и `~/.claude/cache` только смотрятся; скиллы, `settings.json` и файлы не из листинга не пишутся и не читаются. CLAUDE.md — обычные файлы на диске, в них бывают токены и внутренние адреса: содержимое показывается только по «Открыть». API: `GET /api/context?cwd=&flow=&phase=&model=&force=1`, `GET /api/context/file?path=`, `PUT /api/context/file` с `{"path", "text", "mtimeMs"}` (ответ — новый `mtimeMs`; 403 — файл не из листинга или не редактируется, 404 — файл из листинга пропал с диска, 409 — изменён снаружи); у `GET /api/context` 400 — недопустимое имя flow или нет директории проекта, 404 — нет flow или этапа, листинг дольше 30 секунд обрывается с ошибкой;
- **задачи и код** (на главной): задачи Jira (пресеты «Мой спринт», «Все мои», своя JQL), открытые MR (через `glab`, фильтр «Мои») и локальные ветки проектов. В каждом списке видны первые 5 строк, остальные открывает «Ещё N». «Запустить…» собирает задачу (`{{input}}`) из тикета, MR или ветки и открывает вкладку «Запуск» выбранного flow; запуск не стартует сам. В форме запуска можно подготовить отдельный git worktree. Запуск хранит `source` и `worktree` в `run.json`, связанные запуски видны под строкой. Настройки и токен Jira лежат в `~/.agentgraph` (`AGENTGRAPH_CONFIG_DIR`). Подробнее — в [GETTING_STARTED.md](GETTING_STARTED.md#запуск-из-задачи-jira-mr-или-ветки). API: `GET /api/integrations`, `PUT|DELETE /api/integrations/jira`, `GET /api/jira/issues`, `POST|PUT|DELETE /api/projects`, `GET /api/projects/mrs|branches`, `POST /api/intake`, `POST /api/worktrees`;
- **мои MR: нужно внимание** (на главной, над «Задачами и кодом»): твои открытые MR из проектов «Подключений» (только GitLab, через `glab`), у которых есть хотя бы одна причина:
  - упал последний пайплайн ветки (только `failed`; `canceled` и идущий не считаются);
  - есть неразрешённые обсуждения, где последнее несистемное сообщение не твоё (боты тоже считаются);
  - есть конфликты (`has_conflicts` или `detailed_merge_status: conflict`).

  У каждой причины есть ссылка: «CI упал» ведёт на пайплайн, остальные на MR. Ошибка одного проекта (например, `glab` не авторизован на хосте) видна под списком и не прячет остальные. «Запустить…» работает как в «Задачах и коде», но во вход flow добавляется строка «Требует внимания: …» с причинами на момент запуска. После загрузки списка сервер в фоне один раз спрашивает haiku (`claude-haiku-4-5-20251001`, сессия без инструментов), какой flow подходит каждому MR. Если подходящий есть, в строке появляется чип «→ <flow>» (почему — в подсказке), клик открывает «Запуск» этого flow с заполненным входом. Если подходящего нет или модель назвала flow не из списка, подсказки нет. Запуск никогда не стартует сам. Список кэшируется на минуту (↻ — без кэша), на главной обновляется, если ему больше 5 минут. Подсказки кэшируются по MR, причинам, времени обновления MR и списку flow, поэтому модель спрашивается только о новом. На каждый MR уходит один-два запроса `glab` (обсуждения — только если в MR есть комментарии), не больше 4 одновременно; больше 100 обсуждений в одном MR не читаются. API: `GET /api/attention[?force=1]` → `{ items, errors, at }`, `POST /api/attention/suggest` с `{"refs": [...]}` → `{ suggestions: { <ref>: { flow, why } } }` (подбор только по MR из последней выдачи `GET /api/attention`), `POST /api/intake` с `"attention": true` для `type: "mr"`;
- **шапка flow**: описание занимает две строки, остальное открывает «ещё» (целиком оно на вкладке YAML);
- вкладка **Конструктор**: граф flow слева направо. Узлы — «Задача» и этапы (номер, название, id этапа, переопределённые модель и effort, число инструментов, что этап получает; «ничего не получает» подсвечено ошибкой). Рёбра подписаны тем, что этап передаёт дальше (`handoff`, после группы — «выводы группы (склейка)»). Параллельная группа — рамка `∥ имя` с участниками столбиком: рёбра входят в каждого и выходят из каждого. Ромб — условие блока, пунктирная дуга от него к первому шагу — «не выполнено ↺ до N» (у `none` — «↺ ровно N итераций»). У многоблочного flow блоки идут полосами сверху вниз, каждый в рамке с заголовком, «↺ до N итераций» или «один проход» и чипами тегов знаний (`knowledge`); рамка не уже своей шапки, заголовок не обрезается; ребро к следующему блоку подписано «выполнено →», при `on_fail: continue` — «выполнено или лимит →». Одиночный блок получает рамку, только если у него есть `title` или теги знаний. У flow с `artifacts` справа от блоков колонка артефактов: сплошные рёбра — запись (`writes`), пунктир — чтение (`reads` и `{{artifacts.KEY}}`), наведение на артефакт подсвечивает его рёбра. Ребро идёт из правого бока этапа по каналу под его блоком к шине справа и не пересекает другие блоки. Клик по этапу открывает его целиком в «Крупном редакторе» справа: название, чипы «Переменные», промпт крупно, «Что передать следующему этапу», строка артефактов, инструменты, id, модель, effort, лимит ходов, права, лимит стоимости, параллельная группа, дополнительные директории, системный промпт, схема вывода и кнопки ↑ ↓ ⧉ ✕. Левая колонка при этом не прокручивается, выбранный узел остаётся выделенным, карточка этапа слева подсвечена. Справа и в карточке слева — одни и те же поля: правка с одной стороны сразу видна на другой и на графе. Туда же ведут «+» на графе, «Добавить этап», «⧉», строки «Что изменилось» у «Правки с ИИ», ошибка сохранения в поле этапа и клик в любое поле карточки слева. На узком экране (не шире 1100 px), где редактора справа нет, клик по этапу раскрывает его карточку и ставит фокус в промпт. Клик по шапке блока или ромбу ведёт к настройкам цикла. «+» на узле (при наведении) добавляет этап после шага (у участника группы — после всей группы), «+» на рамке группы — ещё одного участника. Граф перерисовывается на каждую правку, подсветка «Правки с ИИ» видна и на узлах. Панель «− 100% + Вписать» (строка над холстом, граф не перекрывает) и ⌘/Ctrl+колесо масштабируют граф (масштаб запоминается отдельно для конструктора, вкладки «Запуск» и страницы запуска; пока его не меняли руками, широкий граф вписывается по ширине, но не мельче 70%), перетаскивание фона прокручивает. Ниже карточки этапов: название, промпт, поле «Что передать следующему этапу», чипы инструментов и свёрнутое «Дополнительно» (там «Дополнительные директории» и id этапа: на его вывод ссылаются как `{{phases.id}}`). Чипы «Переменные» (клик вставляет `{{переменную}}` в промпт, использованные подсвечены) на широком экране лежат в редакторе этапа справа, над промптом. На карточке этапа слева они есть только на узком экране. Поля flow и блока («Описание flow», «Задача по умолчанию», рубрика судьи, команда условия) по фокусу открываются справа по-старому: зеркалом одного поля. Этапы можно добавлять, дублировать, переставлять и удалять; настройки цикла и условия тут же. Кнопка **Добавить блок** добавляет следующую стадию: у каждого блока свой режим (цикл до условия или один проход), условие и выбор, что делать, если условие так и не выполнено. Граф рисует блоки друг под другом, а ↑/↓ на крайнем этапе блока переносят его в соседний блок. id блока (ключ в YAML) у многоблочного flow правится в настройках блока. Кнопка «Сохранить» внизу появляется, когда есть несохранённые правки; сохранение валидирует и пишет YAML; flow из одного блока сохраняется в короткой форме (`loop` + `phases`);
- **Коннекторы claude.ai** в карточке этапа, под инструментами: какие инструменты Jira, Confluence и Slack этапу выданы и что это значит. «+ Jira, Confluence, Slack…» показывает список инструментов подключённых коннекторов аккаунта; первые пункты каждого коннектора — «весь коннектор» (одна запись в `tools`) и «всё на чтение» (все его инструменты, которые ничего не меняют) (сервер спрашивает его у Claude Code, несколько секунд; неподключённые перечислены отдельно) и поле для имени вручную. Пишущий инструмент подсвечен: этап выполнит его без подтверждения. Имя, которого нет у подключённых коннекторов, подсвечено ошибкой; имя вида `mcp__<uuid>__…` из desktop-сессии не принимается. Если промпт этапа зовёт Jira, Confluence или Slack (имя инструмента, «Atlassian MCP», ссылка, «открой … в Jira»), а коннекторов у этапа нет, строка предупреждает. Форма запуска предупреждает, если во входе ссылка на Jira или Slack, а коннекторы не получит ни один этап flow.
- **Правка с ИИ** (над графом в конструкторе): описываешь словами, что поменять, — агент правит flow инструментом Edit, как код: то, что к правке не относится, остаётся байт в байт, а зависимые места (ссылки `{{phases.X}}`, соседние промпты, рубрику судьи) ИИ подправляет и перечисляет в ответе. За основу берётся то, что сейчас в конструкторе, вместе с несохранёнными правками; сломанный flow ИИ заодно починит. Результат ложится в конструктор несохранённым: ответ ИИ с перечнем правок, список изменённых полей (клик ведёт к этапу), изменённые этапы и блоки подсвечены, «Отменить правку» возвращает как было, «Прервать» останавливает ИИ, пока он правит. В файл попадает только по «Сохранить»;
- вкладка **Запуск**: сворачиваемая «Схема» (по умолчанию свёрнута, чтобы «Запустить» была видна без прокрутки; развёрнутая — не выше 60% окна, дальше прокрутка) — тот же граф только для чтения, по сохранённой версии flow (без несохранённых правок конструктора); клик по узлу открывает конструктор на этом этапе (этап сразу открыт в редакторе справа) или блоке. Под ней план этапов, свёрнутый в сводку («2 блока, 5 этапов» или «3 этапа, до 4 итераций, …»; раскрывается кликом, так что «Запустить» видна без прокрутки), задача (уходит в `{{input}}`), директория проекта, лимит итераций (у многоблочного flow — лимит каждого цикла, пусто = как в блоках), лимит стоимости, модель. Кроме того:
  - **вложения** к задаче: «Добавить файлы…», перетаскивание файлов на форму или вставка скриншота в поле задачи; чип «имя · размер ×» убирает файл. Можно картинки (`png jpg jpeg gif webp`), PDF и текст (`txt md csv json log yaml yml xml`): до 10 файлов, до 10 МБ каждый и до 25 МБ вместе. `.docx` нет: Read его не разбирает. `CLAUDE.md` и `CLAUDE.local.md` (в любом регистре) сохраняются как `attached-…`: папка вложений уходит агентам в `additionalDirectories`, и под исходным именем Claude Code загрузил бы файл как инструкции агента. Файлы ложатся в `runs/<id>/attachments/`, их абсолютные пути дописываются в конец промпта каждого этапа («Вложения к задаче (открой инструментом Read)»), а папка `attachments/` добавляется всем этапам в `additionalDirectories`. Агент открывает их сам через Read, поэтому этапы без Read вложений не увидят; форма предупреждает об этом списком таких этапов. Судья (`until.type: judge`) тоже получает список вложений и их папку: это часть задачи. На странице запуска вложения видны ссылками в шапке, картинки и PDF открываются в браузере. При продолжении запуска вложения копируются в новый;
  - **дополнительные директории** на весь запуск, по пути на строку (кнопка «Выбрать…» дописывает строку): как `add_dirs`, но для всех этапов сразу (см. «Дополнительные директории этапа»). Нет директории — запуск отклоняется с ошибкой 400 ещё до создания папки запуска. Список пишется в `run.json` (`addDirs`) и переносится в продолжение. Если одной из директорий к продолжению уже нет, «Продолжить» отвечает 400, а убрать её из продолжения нельзя: верни директорию на место или начни новый запуск;
  - **недавние директории**: чипы под директорией проекта и под дополнительными директориями. Клик подставляет путь в директорию проекта или дописывает его строкой в дополнительные. Пути собираются из `cwd` и `addDirs` прошлых запусков (свежие сверху, без worktree), проектов из «Подключений» и директории по умолчанию; видно не больше 8, отсутствующие на диске не показываются. «×» на чипе (виден при наведении) убирает путь из недавних в обоих рядах и в подсказках страницы «Контекст»; путь вернётся после нового запуска с ним. Проект в «Подключениях» при этом остаётся, убрать его — там. Закрепить путь руками нельзя.

  API: `POST /api/runs` принимает, кроме `flow`, `input`, `cwd` и лимитов, поля `attachments: [{ "name", "data" }]` (`data` — содержимое в base64; тело запроса до 40 МБ) и `addDirs: string[]` (`~` раскрывается, относительные пути — от `cwd`). Ошибка в вложениях или директориях — 400. `GET /api/dirs/recent[?limit=N]` отдаёт недавние директории `[{ path, label, lastUsed?, exists }]`. `DELETE /api/dirs/recent?path=<абсолютный путь>` убирает путь из недавних: 200 и новый список, 400 при пустом или относительном пути. Скрытые пути и время скрытия лежат в `~/.agentgraph/settings.json`, поле `hiddenDirs`; путь снова показывается, если с ним был запуск позже скрытия. `GET /api/runs/:id/file?path=attachments/<имя>` отдаёт вложение с типом по расширению;

  API разового запуска: `POST /api/runs` вместо `flow` принимает `spec` (объект из конструктора) или `yaml` (строка): ровно одно из трёх, черновик проверяется до создания папки запуска, такой запуск помечается `adhoc`. `POST /api/flows/generate` с `save: false` возвращает `{ name, spec, yaml, summary, costUsd }` и ничего не пишет. `POST /api/flows/check` с `{ spec }` или `{ yaml }` проверяет черновик: `{ name, spec, yaml, summary }` или 400. `POST /api/runs/:id/save-flow` с `{ name?, folder? }` кладёт снимок запуска в `flows/` (поле `name` в YAML меняется на выбранное), ответ `{ name, folder }`; занятое `name` — 409. Фича в `GET /api/config`: `adhoc-runs`.
- вкладка **YAML**: та же спецификация текстом, для тонкой правки;
- кнопка **Удалить** в шапке flow: убирает файл из `flows/` после подтверждения, прошлые запуски остаются;
- **разовый запуск** («Новый flow» → «Разовый запуск (не сохранять flow)»): flow генерируется из описания и открывается в конструкторе черновиком (адрес `/draft`, у заголовка пометка «разовый»). Правка руками, «Правка с ИИ» и вкладка YAML работают как обычно, только «Сохранить» превращается в «Применить»: сервер проверяет черновик и ничего не пишет. Папки и «Удалить» у черновика нет. «Запустить» стартует запуск тем, что сейчас в конструкторе; в `flows/` файл не появляется, единственная копия flow — снимок `runs/<id>/flow.yaml`, а в `run.json` стоит `adhoc: true`. Черновик живёт только во вкладке: уход с него и закрытие вкладки спрашивают подтверждение. У разового запуска в списке и в шапке пометка «разовый», вместо «К flow» — **«Сохранить как flow»**: имя (пусто — свободное от имени запуска, `<имя>-2`, если занято) и папка; занятое имя — отказ, существующий flow не перезаписывается. Сам запуск после этого остаётся разовым. «Продолжить с места остановки» у разового запуска (и у продолжения продолжения) идёт по снимку, даже если в `flows/` есть flow с тем же именем.
- кнопка **Новый flow**: сгенерировать flow из описания задачи или собрать руками из заготовки, сразу в нужную папку;
- **папки flow**: flow можно разложить по папкам (подкаталоги `flows/<папка>/`, один уровень) — поле «Папка» под названием flow (выбрать существующую или вписать новую, пусто — корень) или перетаскивание flow на папку в списке слева. Опустевшая папка удаляется. Имя flow остаётся уникальным через все папки, поэтому `run <имя>`, ссылки и запуски от папки не зависят;
- **запуски по проектам**: слева запуски сгруппированы по директории проекта (подпись — имя папки, полный путь в подсказке; проекты идут по свежести последнего запуска, у свёрнутого видно число идущих ●). Переключатель «по проектам» возвращает плоский список;
- **фильтр запусков по статусу**: над списком запусков чипы статусов, которые сейчас есть в списке, с числом запусков («ждёт ответа», «выполняется», «готово», «лимит итераций», «ошибка», «оборвался», «прервано»…). Клик добавляет статус в фильтр или убирает из него, выбрано несколько — показываются все выбранные, «все» сбрасывает. Фильтр работает до лимита «ещё N», открытый запуск остаётся в списке, выбор запоминается в браузере. Вместе с ним работает поиск (см. «поиск» ниже);
- **имя запуска**: у нового запуска (из UI, CLI или скилла) есть короткое имя, 3–7 слов на языке задачи. Его придумывает отдельная сессия haiku без инструментов по задаче, имени flow и источнику запуска. Сессия идёт параллельно этапам и не задерживает `POST /api/runs`. Имя появляется через несколько секунд после старта, без перезагрузки страницы. До этого, а также у старых запусков и при сбое подбора (ошибка, таймаут 30 с, пустая задача) заголовком остаётся имя flow, и запуск это не роняет. Имя чистится так же, как заголовок автотега: одна строка без управляющих символов и угловых скобок, до 60 знаков. Оно придумано по недоверенному тексту, поэтому UI выводит его только как текст. Где оно видно: заголовок в списке запусков (flow стоит мелко первым в подстроке), шапка страницы запуска (под ней строка «flow <имя>» ссылкой на flow, у разового запуска без ссылки), карточка идущего запуска на главной, заголовок вкладки, системные уведомления («имя (flow)»), итог в CLI и сводка скилла. «Продолжить с места остановки» берёт имя исходного запуска, модель заново не зовётся. Если у исходного запуска имени нет, у продолжения его тоже нет. Переименовать запуск руками нельзя. API: `title` в `GET /api/runs`, `GET /api/runs/:id` и `GET /api/home`; событие `title` (`title` или `error`, `totalCostUsd`) в потоке запуска и в общем потоке `GET /api/events`; фича `run-title` в `GET /api/config`;
- **поиск** в сайдбаре: поле «Найти flow…» над списком flow и «Найти запуск…» над списком запусков. Каждое слово запроса должно найтись хотя бы в одном поле, регистр не важен. Flow ищутся по имени, папке и описанию. Папки с совпадениями раскрываются на время поиска, папки без совпадений скрываются, запомненная свёртка папок не меняется. Запуски ищутся по имени, flow, задаче, тегам задачи и знаний, имени папки проекта, id и ключу источника (тикет, MR). Поиск работает вместе с фильтром по статусу (нужно оба условия) и до лимита «ещё N», поэтому находит и старые запуски. Пока поиск не пуст, числа на чипах статусов считают только найденные запуски; набор чипов не меняется, у статуса без совпадений — 0. Открытый запуск остаётся в списке. В режиме «по проектам» группы с совпадениями раскрыты, пустые скрыты. Нет совпадений — «Ничего не нашлось». Поиск идёт на клиенте по уже загруженному списку. Задачу `GET /api/runs` отдаёт только первые 200 знаков без блоков тегов, поэтому слова из хвоста длинной задачи не находятся. Текст и фокус в поле переживают обновление списка (события и раз в 10 с), Esc очищает поле. Запрос не запоминается: после перезагрузки поле пустое;
- **скрыть и удалить запуск**: у закончившегося запуска при наведении в списке слева есть кнопки «Скрыть» и «Удалить», те же — в шапке страницы запуска. Скрытый уходит из списка, но файлы остаются (флаг `hidden` в `run.json`); «показать скрытые: N» под списком возвращает их на экран, «Вернуть в список» снимает флаг. Удаление после подтверждения стирает папку `runs/<id>` целиком. Идущий запуск (и запуск из CLI, чей процесс ещё жив) не скрывается и не удаляется: сначала останови. API: `PUT /api/runs/:id/hidden` с `{"hidden": true|false}`, `DELETE /api/runs/:id`;
- сворачивание и прокрутка: у разделов «Flow» и «Запуски» своя прокрутка, поэтому длинный список flow не уводит запуски за экран; строка flow занимает одну строку, описание — в подсказке. Разделы, папки и проекты сворачиваются кликом по заголовку, кнопка рядом с заголовком раздела сворачивает или разворачивает все сразу. Папки flow по умолчанию свёрнуты, кроме папки открытого flow; раскрытые руками запоминаются. Остальное состояние тоже запоминается в браузере; при открытии flow или запуска по ссылке его папка или проект раскрываются;
- **схема запуска** (страница запуска, сворачиваемая секция «Схема» над блоками этапов): граф по снимку `runs/<id>/flow.yaml`, по которому идёт запуск. Статусы обновляются на каждое событие без перерисовки, поэтому прокрутка, масштаб и фокус остаются. Текущий узел подсвечен и пульсирует, у пройденных ✓ или ✗ и стоимость последней итерации, а у идущего и пройденного этапа ещё и занятость контекстного окна в бейдже (сразу после иконки или цены, чтобы не обрезалось в узле: «⏳ 45% · идёт · итер. 1», «✓ $0.01 · 45%»; без известного окна — «90k» вместо процента; полная подпись — в подсказке узла), будущие приглушены; у ромба — «↻ не выполнено (итер. N)» или ✓, в шапке блока — «итер. 3/5» (лимит берётся из отчёта и меняется на ходу вместе с подписью дуги), блоки, пропущенные продолжением, помечены «пропущен». Над графом строка «Сейчас: блок 2 «…» · итерация 3/5 · этап «…» (идёт 4 мин)» с пометками «ждёт ответа», «на паузе», «пауза после шага»; время этапа считается с момента, когда эта вкладка увидела его старт. На узле «Задача» — задача и теги запуска (`tags`, `knowledge`). Клик по этапу раскрывает блок и итерацию и подсвечивает карточку этапа последней итерации (не выполнялся — подсказка рядом с заголовком), клик по ромбу — карточку условия, по артефакту — окно артефакта; кнопка «Открыть flow в конструкторе» (у разового — «Сохранить как flow»). У запусков без снимка `flow.yaml` секции нет. API: `GET /api/runs/:id/flow` → `{ name, blocks, artifacts? }` (блоки в полной форме), 404 без снимка; фича `run-flow` — в `features` у `GET /api/config`;
- страница запуска: у завершённого запуска наверху карточка **«Итог»**: статус, статусы блоков (у многоблочного flow), итерации, стоимость, длительность, ошибка запуска, при неуспехе — замечания последнего условия, и вывод последнего шага отформатированным markdown (у параллельной группы в конце — вывод каждого участника, кнопка «вывод» открывает файл целиком). Последний шаг — этап последнего выполненного блока с наибольшими итерацией и номером, упавший тоже; у старых запусков итог считается по этапам при открытии. Ниже — карточки этапов по итерациям (у многоблочного flow — по блокам, со статусом каждого блока) с кнопками «промпт / транскрипт / вывод» (у идущего этапа «промпт» и «транскрипт» есть сразу после старта, транскрипт — на момент открытия; у идущей проверки судьёй — «промпт судьи»), результат условия с замечаниями, живой лог сессий (раскрыт только у идущего запуска, у завершённого раскрывается по клику; в окне последние 3000 строк, весь лог этапа — в его транскрипте), кнопки «Пауза» и «Остановить запуск». Шапка запуска в две строки: ход («блок 3/6 · итераций: 4 · ≈$26.05») и серым дата, директория проекта и, у продолжения, ссылка на исходный запуск. `claude --resume <id>` сессии этапа лежит в окне «транскрипт», а не на карточке. Блоки и итерации сворачиваются кликом по заголовку; по умолчанию открыт идущий (или последний начатый) блок и последняя итерация каждого блока, остальное свёрнуто, а в заголовке итерации видна сводка: сколько этапов, время, стоимость, выполнено ли условие. Новая итерация открывается сама, предыдущая сворачивается, если её не раскрывали руками. Окно файла показывает промпт, вывод этапа и промпт судьи отформатированным markdown (заголовки, списки, таблицы, код), замечания судьи — тоже (замечания команды-условия — это хвост её вывода, он моноширинный); кнопка «как текст» в шапке окна возвращает исходник для копирования, выбор запоминается в браузере. Транскрипт, лог команды условия и вывод в JSON остаются моноширинными, как и очень большой текст (больше 300 000 символов или со строкой длиннее 10 000 символов): его разбор подвесил бы вкладку. Сырой HTML в markdown не выполняется, ссылки — только http/https. Над карточками одна кнопка «Свернуть все» / «Развернуть все»: она разворачивает, если свёрнуто больше половины, и сворачивает в остальных случаях;
  - **модель и effort этапа**: на карточках этапов (✓ у законченных, ⏳ у идущих, в том числе у участников параллельной группы) чип «модель · effort»; в подсказке — полный текст, «не задан (по умолчанию модели)» для effort без значения. У идущего этапа без заданной модели чип с моделью появляется через секунду после старта сессии, когда придёт `system/init`; effort показывается сразу. У старых запусков и этапов без данных чипа нет. В потоке запуска (`/api/runs/:id/events`) у `phase_start` есть заданные `model` и `effort` (если заданы), а отдельное событие `phase_model` (`block`, `iteration`, `phase`, `model`) приходит один раз после init с фактической моделью. Те же поля — `phases[].model` и `phases[].effort` в `GET /api/runs/:id`.
  - **контекст этапа**: на тех же карточках чип `ctx 172k / 1M · 17%` — пик контекста этапа, окно модели главного цикла и процент от него (процент всегда от окна модели, а не от окна автокомпакта). В подсказке: старт, пик, число запросов к модели, input/output/кэш (по всем моделям сессии, включая сабагентов). Чип с 70% окна жёлтый, с 90% красный. У идущего этапа чип растёт по ходу сессии на месте, без перерисовки страницы (форма ответа на вопрос не сбрасывается); процента у него нет, пока окно модели неизвестно: окно приходит с результатом сессии и запоминается по модели на время жизни сервера, а до первого результата его даёт `getContextUsage` Agent SDK. У старых запусков без `contextWindow` — только `ctx 90k` без процента, без `tokens` чипа нет. В потоке запуска (`/api/runs/:id/events`) событие `phase_context` (`block`, `iteration`, `phase`, `contextPeak`, `requests`, `contextWindow` — если известно) приходит после каждого запроса главного цикла к модели; сервер хранит только последний снимок каждого идущего этапа: переигрывание при подключении отдаёт по одному на этап (до строк лога), в ленту событий и в общий поток `/api/events` (главная) оно не идёт. Готовые данные — `phases[].tokens` в `GET /api/runs/:id`.
- **артефакты запуска** (на странице запуска, только у flow с `artifacts`; у остальных панели нет, и UI не делает ни одного запроса артефактов): панель «Артефакты» между карточками паузы и вопросов и блоками этапов. Свёрнутая строка — число артефактов, какой изменён последним и кем, «✎ пишет этап X» (у параллельной группы — все пишущие), предупреждения и «не сохранено». Те же данные — на узлах колонки артефактов в «Схеме»: последний автор, «открыто N из M», «✎ пишет этап X»; развёрнутая — строка на артефакт: название, файл, размер, последний автор со временем, пометки. На паузе по просьбе агента и при вопросе агента панель подсвечивается, но не раскрывается сама. Клик по названию открывает окно артефакта: превью markdown (у `.md`, с «как текст») или текст, любая сохранённая версия, «Править». В правке — «Сохранить», «Сохранить и возобновить» (только на паузе) и «Отбросить». Закрытое окно оставляет черновик («не сохранено» в строке), и любая кнопка «Возобновить» или «Продолжить с места остановки», в том числе на главной, при черновике спрашивает: «Сохранить и возобновить», «Возобновить без правки» или «Отмена»; уход на другой запуск и перезагрузка страницы спрашивают подтверждение. Пока идёт шаг, который пишет артефакт, правка заблокирована с причиной («пишет этап X»; «этап X ждёт твоего ответа», если пишущий этап задал вопрос): текст редактора остаётся, после конца шага «Сохранить» снова доступна. Если файл изменился после открытия, сохранение отклоняется с тем, кто и когда его менял: «Перечитать», «Сохранить поверх», «Скопировать мой текст». Если запуск возобновили не отсюда (с другой вкладки, из чата или скилла), а черновик остался, панель и окно говорят, что текст не сохранён и идущий шаг его не увидит. У запуска из CLI — только чтение, «Обновить» и время данных; у завершённого (`done`) и у того, что продолжить нельзя, — только чтение с причиной; у остановленного, который можно продолжить, правка попадёт в продолжение, а рядом стоит «Продолжить с места остановки». Файл больше 1 МБ в UI только читается. Предупреждения (запись без права, посторонние файлы, исчезнувший артефакт) видны значком в заголовке итерации, на строке артефакта и в «Итоге»; на карточке этапа — «изменил: …» и «отказов записи: N». API: `GET /api/runs/:id/artifacts` (`items` — путь, автор, версии, `lockedBy`, `editable` и причина; `from`, `warnings`, `live`, `continuable`), `GET /api/runs/:id/artifacts/:key[?version=N]` (текст, `hash` — база для записи, версии, `editable`), `PUT /api/runs/:id/artifacts/:key` с `{"text", "base", "resume"?}` → `{ hash, author, readers, resumed }` (`readers` — идущие этапы, которые уже получили прежнюю версию). Ошибки с полем `code`: 400 `bad_request`, 403 `readonly` (+ `reason`), 404 `unknown_key` или `missing`, 409 `conflict` (+ `hash`, `author`, `at`) или `not_paused` (`resume: true` не на паузе; ничего не записано), 413 `too_big`, 423 `locked` (+ `reason`: `writing` | `asking`, `phases`). Ключ — только имя из flow: путь вместо ключа (`..%2Frun.json`) даёт 404. Событие `artifacts` в потоке запуска (`/api/runs/:id/events`) несёт снимок списка и итог шага; в общий поток главной оно не идёт. Фича `artifacts` — в `features` у `GET /api/config`;
- **чат запуска** (вверху страницы запуска; по умолчанию свёрнут, раскрывается кликом по заголовку, выбор запоминается в браузере): разговор с агентом про этот запуск — спросить, что происходит, почему упало, что агент уже поменял в коде, или попросить поставить на паузу, возобновить, остановить запуск, поменять лимит итераций, ответить на вопрос агента, продолжить завершённый запуск. Агент — сессия Claude Code в директории проекта запуска: читает папку запуска и репозиторий (Read, Grep, Glob, Bash), по прямой просьбе правит файлы в директории проекта (Edit, Write; в папку запуска писать не может), а запуском управляет теми же функциями сервера, что и кнопки. Свежее состояние он берёт инструментами `run_status` и `run_log` (хвост живого лога), а в начало каждого сообщения сервер подставляет строку состояния. Разговор продолжается между сообщениями (`resume` сессии), «Очистить контекст» или `/clear` в поле ввода начинают новый — как `/clear` в Claude Code. Ответ идёт на сервере: можно уйти на другой запуск и вернуться — ход ответа и итог подтянутся; «Прервать» останавливает ответ. Модель выбирается в шапке чата. История лежит в `runs/<id>/chat.json`. API: `GET|POST|DELETE /api/runs/:id/chat` (POST `{"message", "model"?}` отвечает потоком NDJSON: `saved`, `log`, `done` или `error`), `POST /api/runs/:id/chat/stop`.

### Вопросы от агента

**Пауза** мягкая: идущая сессия (этап или проверка условия) доработает, а следующий шаг не начнётся, пока не нажмёшь «Возобновить». Запуск получает статус «на паузе» и держит контекст в памяти UI-сервера; если сервер перезапустить, запуск на паузе пропадёт, как и любой живой запуск. Такой запуск (в `run.json` остался `running`, а процесса раннера из поля `pid` уже нет) показывается со статусом «оборвался»: возобновить его нельзя, но можно продолжить с первого незавершённого блока (см. «Продолжение завершённого запуска»). **Остановить запуск** прерывает текущую сессию сразу, в том числе запуск на паузе и команду проверки условия: её процессы убиваются всей группой. API: `POST /api/runs/:id/pause`, `/resume`, `/abort`.

Если у этапа включён инструмент `AskUserQuestion`, агент может остановиться и спросить пользователя. В UI запуск получает статус «ждёт ответа», на странице запуска появляется карточка с вариантами и полем «Свой ответ». Если агент перед вопросом что-то написал (таблицу замечаний, список вариантов), этот текст стоит на карточке над вопросом, а в истории — свёрнутым: в счёт идёт то, что главный агент написал последним (подряд идущие текстовые блоки, без сабагентов) (поле `preface` вопроса в `run.json`; его же получают скилл `/agentgraph` и чат о запуске). Текст вопроса и описания вариантов показываются как markdown (списки, код, ссылки), заголовок вопроса — плашкой над ним; сам ответ уходит агенту как есть, ключ — исходный текст вопроса; после ответа сессия продолжается, а вопрос с ответом остаётся в истории запуска: вопрос блоком, ответ под ним. В CLI вопрос печатается в терминал, ответ вводится номером варианта или текстом. Пример: `flows/example/example-ask.yaml`.

Flow, где вопросы внутри сессии запрещены (агент работает сам и записывает решения в файлы), всё равно может упереться в то, что закрыть может только пользователь: стенд, доступ, внешний ответ. Для этого у цикла есть `loop.pause_marker`. Этап пишет вопросы и заканчивает вывод строкой-маркером. Маркер засчитывается, только если это последняя непустая строка вывода: цитата в середине текста паузу не ставит. Если условие цикла не выполнено, запуск после итерации встаёт на паузу: итерации вхолостую не тратятся, причина видна на странице запуска (текст агента над маркером — markdown), в `pauseReason` у `GET /api/runs/:id`, в системном уведомлении и в ленте «События» на главной (все паузы запуска с временем просьбы и возобновления лежат в `pauses` в `run.json`). После ответа и «Возобновить» запуск идёт со следующей итерации того же блока. В CLI паузы нет, и блок завершается ошибкой с текстом вопросов. Пример: `flows/example/example-pause.yaml`.

**Ответ на паузу в артефакт.** Если во flow есть артефакт с `decisions: true` (см. «Артефакты запуска»), под карточкой паузы по просьбе агента есть поле «Ответ», а кнопка «Возобновить» в шапке называется «Возобновить с ответом», когда в поле есть текст. Ответ дописывается в конец этого артефакта записью: время, блок, итерация, этап, вопросы этапа цитатой и ответ. Тот же ответ ложится в `run.json` в `pauses[].answer` (`text`, `via`: `ui` | `skill`, `at`): это авторитетный список ответов, ведь этапы тоже могут писать в артефакт решений. Запуск возобновляется только после успешной записи; при ошибке он остаётся на паузе, причина видна, текст остаётся в поле. Пустое поле — обычное «Возобновить» без записи. Если в окне артефакта есть правка, «Сохранить и возобновить» сначала сохраняет её, потом возобновляет с ответом. Поле ответа есть только на странице запуска: на главной у такого запуска кнопка «Ответить на странице запуска». Если артефакта `decisions` нет, но артефакты есть, карточка паузы вместо «запиши туда, куда просит агент» даёт «Открыть артефакты»; у flow без артефактов карточка прежняя. Скилл `/agentgraph` отвечает так же: `resume <id> --answer-file F`. API: `POST /api/runs/:id/resume` с `{"answer"}`. Пустой `answer` или тело без него — прежнее возобновление. Ошибки: 409 `not_paused` (запуск не на паузе), 400 `no_decisions` (ответ некуда записать), 413 (ответ больше 64 КБ).

**Продолжение завершённого запуска.** Запуск, который кончился не `done` (`max_iterations`, ошибка, остановка, «оборвался»), можно продолжить текущей версией flow: кнопкой «Продолжить с места остановки» на странице запуска, `POST /api/runs/:id/continue` или `agentgraph.mjs continue <id>` из скилла. Новый запуск пропускает сплошное начало блоков, которые в старом завершились `done`, и подставляет их последние выводы в `{{phases.*}}`, `{{prev}}` и `{{history}}`. Блок, на котором старый запуск остановился, идёт с первой итерации и без своих старых выводов: в них могут быть устаревшие указания. Продолжение продолжения берёт выводы из того запуска, где блок выполнялся. Лимит итераций при продолжении берётся из flow: `--max-iterations` переопределил бы все циклы, поэтому не принимается. Нет вывода пропускаемого этапа — продолжение отклоняется, а не идёт с пустым `{{phases.*}}`. Продолжать нечего, если первый блок не завершён, поэтому flow из одного блока продолжить нельзя. Можно ли продолжить запуск, сервер отдаёт в `GET /api/runs/:id` полями `continuable` и `continueReason`; кнопка «Продолжить с места остановки» берёт их оттуда.

У flow с артефактами продолжение получает копию текущих файлов артефактов прошлого запуска, включая правки после его остановки, но без истории версий. Последний автор переносится с пометкой «из запуска X», поэтому первый этап знает, что последнюю правку сделал пользователь. Страница нового запуска и его `run.json` (`artifacts.from`) показывают, откуда взяты артефакты. Если flow изменился: новый артефакт создаётся из `initial`, убранный не копируется, при смене `file` у того же ключа содержимое переносится, а переименованный ключ считается убранным и новым. Остановленный блок идёт с первой итерации без своих старых выводов, но с артефактами: артефакт и есть состояние, которое пользователь мог исправить.

Сервер слушает только `127.0.0.1`, авторизации нет. Чтобы чужая страница в браузере не управляла им (CSRF, DNS rebinding), он принимает только `Host` 127.0.0.1, localhost или [::1] с любым портом (иначе 421), у запросов кроме GET и HEAD — `Origin` того же адреса или без `Origin` (иначе 403), а тело — только `Content-Type: application/json` (иначе 415). UI, хелпер скилла и curl под это подходят. `--cwd` у команды `ui` задаёт директорию проекта по умолчанию для формы запуска, `--port` меняет порт, `--no-notify` выключает системные уведомления.

### Уведомления

Когда агент задаёт вопрос или запуск заканчивается (кроме остановки руками), сервер показывает системное уведомление — если ни одна открытая вкладка UI не покажет своё: UI закрыт или в нём не нажато «Включить уведомления». Вкладка с включёнными уведомлениями браузера сообщает об этом серверу при подключении к `/api/events` (`?notify=1`), и тогда сервер молчит, чтобы не дублировать. Сервер, поднятый скиллом `/agentgraph` (`AG ensure`), тоже шлёт уведомления.

- macOS: если установлен `terminal-notifier` (`brew install terminal-notifier`), клик по уведомлению открывает главную или страницу запуска; без него уведомление идёт через `osascript`, и клик открывает Script Editor. Если уведомлений не видно, разреши их в «Системные настройки → Уведомления» для Script Editor (или terminal-notifier).
- Linux: `notify-send`.
- `--no-notify` у команды `ui` выключает их совсем; `AGENTGRAPH_NOTIFY=log` вместо уведомления пишет строку в лог сервера (для проверок), `AGENTGRAPH_NOTIFY=off` — молчит.

## Быстрый старт

```bash
# сгенерировать flow и сразу запустить его в указанном репозитории
npm run agentgraph -- "Почини падающие тесты в проекте, не трогая сами тесты" --cwd ~/code/my-repo

# разовый запуск: сгенерировать и запустить, flow в flows/ не сохранять
npm run agentgraph -- "Переименуй модуль utils в shared и поправь импорты" --cwd ~/code/my-repo --once

# только сгенерировать, посмотреть и при желании поправить руками
npm run agentgraph -- gen "Добавь эндпоинт /health и покрой его тестами" --cwd ~/code/my-repo
npm run agentgraph -- show flows/add-health-endpoint.yaml

# поправить готовый flow по описанию (ИИ правит файл на месте, комментарии сохраняются)
npm run agentgraph -- edit add-health-endpoint "после реализации добавь этап ревью с судьёй"

# запустить готовый flow
npm run agentgraph -- run flows/add-health-endpoint.yaml --cwd ~/code/my-repo -v

# продолжить работу над фичей: саммари, заметки и пути тегов уйдут в задачу, после done саммари обновятся
npm run agentgraph -- run add-feature --cwd ~/code/my-repo --tag loyalty-card --tag frontend-rules --input "Добавь карту лояльности на экран профиля"
npm run agentgraph -- tags
```

Опции CLI: `--cwd` (директория проекта), `--max-iterations` (у каждого блока с циклом), `--max-budget` (лимит стоимости, USD, суммарно на запуск), `--model`, `--input` (подменить задачу у готового flow), `--once` (разовый запуск: только с формой `agentgraph "<задача>"`, без `-o`; flow не пишется в `flows/`, его копия — `runs/<id>/flow.yaml`), `--tag <slug>` (тег задачи, можно несколько раз), `--no-save-tag` и `--auto-tag` (новый тег задачи по тексту задачи; см. «Теги»), `-v` (стримить ход сессий в консоль). `agentgraph tags` — список тегов.

## Примеры в `flows/example/`

- `example-blocks.yaml` — три блока: слоган до одобрения судьи → перевод и короткая версия в один проход → сверка с маркером. Без инструментов, стоит центы; удобен как smoke-тест: `npm run agentgraph -- run example-blocks`.
- `example-ask.yaml` — этап с `AskUserQuestion`: агент задаёт вопрос пользователю, ответ в UI или в терминале.
- `example-pause.yaml` — `loop.pause_marker`: этап просит решения пользователя, запуск встаёт на паузу (только в UI).
- `example-parallel.yaml` — параллельная группа (`group`): три этапа смотрят на идею одновременно, четвёртый сводит их выводы из `{{prev}}`. Без инструментов, стоит центы: `npm run agentgraph -- run example-parallel -v`.
- `example-artifacts.yaml` — артефакты запуска (`artifacts`, `reads`, `writes`, `{{artifacts.KEY}}`): файл идей переживает итерации, этап `brainstorm` дописывает в него две идеи без инструментов проекта (`writes` даёт правку только своего артефакта), `pick` только читает. В UI нажми «Пауза», пока идёт `pick` первой итерации, открой «Идеи» в панели «Артефакты», допиши строку и нажми «Сохранить и возобновить»: вторая итерация получит правку с пометкой «последнюю правку сделал пользователь». CLI в конце печатает путь к папке артефактов. Модель `claude-haiku-5-5`; замер 2026-10-15 через UI с паузой и правкой — $1.40 за прогон (четыре сессии: `brainstorm` ≈ $0.36–0.37, `pick` ≈ $0.33–0.34), первый прогон за час дороже примерно на $0.15 из-за записи кэша: `npm run agentgraph -- run example-artifacts`.

## Формат flow.yaml

Этапы лежат в поле `phases`, условие остановки блока — в `loop.until` (типы: команда `command`, судья `judge`, маркер `marker`, `none` — без условия, ровно `max_iterations` итераций). Пример ниже показывает все поля сразу и поэтому многоэтапный; обычный flow — один этап со всеми нужными инструментами и условие приёмки. Каждый этап — свежая сессия, которая видит только переданный ей текст, поэтому лишняя граница между этапами — потеря контекста. Отдельный этап оправдан, когда контексты и правда не должны смешиваться: ревью только на чтение после пишущего этапа, параллельная группа независимых работ, шаг с огромным контекстом, который нужно сжать перед следующим. Генератор и «Правка с ИИ» следуют этому правилу; кнопка «Анализ flow» на странице запуска проверяет его по фактам (см. «Анализ flow»).

```yaml
name: fix-tests                 # slug
description: ...
input: "текст задачи"           # доступен как {{input}}
defaults:                       # необязательно, применяется ко всем этапам
  model: claude-opus-5-5
  effort: high
  max_turns: 40
  max_budget_usd: 5
loop:
  max_iterations: 4
  until:                        # одно из:
    type: command               #   shell-команда, exit 0 = готово; вывод -> {{feedback}}
    run: npm test
    # type: judge               #   судья по рубрике (Read/Grep/Glob + сабагенты)
    # prompt: "..."
    # type: marker              #   последняя строка вывода этапа — ровно этот литерал
    # marker: "<DONE>"
    # phase: verify
    # type: none                #   ровно max_iterations итераций
  pause_marker: "<NEEDS_USER>"  # необязательно: этап закончил вывод этой строкой -> запуск на паузе до решения пользователя
phases:
  - name: analyze
    title: Анализ
    tools: [Read, Grep, Glob]   # обязательное поле; [] = без инструментов; Agent (сабагенты) и Skill (скиллы) добавляются всегда; AskUserQuestion = может спросить пользователя
    prompt: |
      Задача: {{input}}
      Замечания с прошлой итерации: {{feedback}}
      ...
    handoff: 'раздел "## Результат": что нашёл, файлы и строки, план правок'   # чем закончить ответ; дописывается к промпту
  - name: implement
    tools: [Read, Edit, Write, Grep, Glob, Bash]
    prompt: |
      Задача: {{input}}
      План: {{prev}}
  - name: qa
    tools: [Read, Grep, Glob, Bash]
    add_dirs: [~/projects/qa-rules]   # куда этапу можно ходить кроме директории проекта (как --add-dir)
# у блока (полная форма, blocks[]) может быть knowledge: [qa] — теги области знаний со страницы «Теги»: их заметки, пути и вложения получают все этапы блока
    group: checks               # соседние этапы с одинаковым group идут одновременно (см. «Параллельные этапы»)
    prompt: |
      Проверь изменения по правилам QA.
  - name: security
    tools: [Read, Grep, Glob]
    group: checks
    prompt: |
      Проверь изменения на уязвимости. Изменения: {{prev}}
    # model, effort, max_turns, permission_mode, max_budget_usd, system, output_schema — по желанию
```

### Переменные шаблона

| Переменная | Что подставляется |
|---|---|
| `{{input}}` | исходная задача |
| `{{prev}}` | вывод предыдущего этапа (для первого этапа на итерации 2+ это вывод последнего этапа прошлой итерации, для первого этапа следующего блока — вывод последнего этапа предыдущего блока). Участники параллельной группы получают вывод до группы, этап после группы — склейку выводов участников |
| `{{phases.NAME}}` | последний вывод этапа `NAME` |
| `{{feedback}}` | замечания условия после прошлой итерации (вывод упавшей команды, замечания судьи); пусто на первой итерации каждого блока |
| `{{iteration}}`, `{{max_iterations}}` | номер итерации и лимит текущего блока |
| `{{outputs}}` | все выводы текущей итерации блока в порядке объявления этапов, каждый под заголовком `### имя` (в основном для промпта судьи) |
| `{{history}}` | все предыдущие выводы, каждая запись обрезана до 6000 символов |
| `{{artifacts.KEY}}` | содержимое артефакта `KEY` на старте шага: до 32 КБ целиком, больше — карта его разделов (см. «Артефакты запуска»), пустой файл — пустая строка. Работает в промпте, `handoff` и рубрике судьи; подстановка даёт этапу право чтения артефакта |
| `{{artifacts.KEY.path}}` | абсолютный путь к файлу артефакта; тоже даёт право чтения |

В `system`, `initial` артефакта и командах условия переменные не подставляются.

### Несколько блоков подряд

Форма выше — это один блок. Когда задача состоит из частей, каждую из которых надо довести до конца, прежде чем идти дальше, вместо `loop` + `phases` пиши `blocks`:

```yaml
name: spec-and-implement
input: "..."
blocks:
  - name: spec                  # цикл: пока судья не примет ТЗ
    title: ТЗ
    loop:
      max_iterations: 3
      until: { type: judge, prompt: "..." }
    phases: [...]
  - name: split                 # без loop = один проход, условие не проверяется
    phases: [...]
  - name: implement             # снова цикл: пока тесты не зелёные
    loop:
      max_iterations: 5
      until: { type: command, run: npm test }
    on_fail: continue           # по умолчанию stop
    phases: [...]
```

- Блоки идут строго по очереди: параллельно можно запускать только этапы внутри блока (см. «Параллельные этапы»). Если цикл блока исчерпал `max_iterations`, а условие не выполнено, запуск останавливается со статусом `max_iterations` (в `error` — на каком блоке). С `on_fail: continue` раннер идёт к следующему блоку.
- Маркер `until.marker` засчитывается, только если этап закончил им вывод: последняя непустая строка — ровно маркер, как у `pause_marker`. Фраза «маркер <DONE> не вывожу» цикл не завершает.
- Этап, чья сессия кончилась ошибкой (API, сон компьютера, лимит ходов или стоимости), останавливает запуск со статусом `failed`: текст ошибки не уходит следующему этапу под видом результата. Продолжить — «Продолжить с места остановки».
- `{{prev}}`, `{{phases.NAME}}` и `{{history}}` переходят из блока в блок: первый этап блока получает в `{{prev}}` вывод последнего этапа предыдущего блока. `{{feedback}}`, `{{outputs}}`, `{{iteration}}` и `{{max_iterations}}` у каждого блока свои и в начале блока обнуляются.
- Артефакты запуска общие для всех блоков: следующий блок видит их в том виде, в каком их оставил последний шаг предыдущего.
- Имена этапов уникальны во всём flow. `{{phases.NAME}}` может ссылаться на этап этого или более раннего блока, но не следующего: тот ещё не выполнялся. `marker.phase` — этап того же блока, по умолчанию последний.
- `--max-iterations` переопределяет лимит каждого блока с циклом; блок без цикла всегда проходит один раз.

### Параллельные этапы (group)

Соседние этапы одного блока с одинаковым полем `group` раннер запускает одновременно, а следующий этап и условие блока ждут, пока закончат все участники. Подходят независимые работы: ревью с разных сторон, исследование отдельных вопросов, в основном чтение. Пример: `flows/example/example-parallel.yaml`.

- Все участники видят один контекст, снятый до старта группы: общий `{{prev}}` (вывод до группы) и `{{phases.*}}`. Ссылаться на соседа по группе через `{{phases.<сосед>}}` нельзя: это ошибка валидации, иначе на итерации 2+ туда молча подставился бы вывод соседа с прошлой итерации.
- Этап после группы получает в `{{prev}}` склейку выводов участников в порядке объявления: `### имя` и вывод, как в `{{outputs}}`. Вывод каждого участника отдельно лежит в `{{phases.<имя>}}`.
- В группе не меньше двух этапов, имя группы не повторяется в другом месте flow, а этап с `Edit` или `Write` в группе не больше одного. `Bash` пишущим не считается, но параллельные сборки или тесты в одной директории могут мешать друг другу, например через общий build-кэш: такие этапы в группу лучше не ставить.
- Один артефакт в группе пишет не больше одного участника, и участник не читает (через `reads` или подстановку) артефакт, который пишет сосед: они идут одновременно. Этап, который пишет только артефакты (`writes` без `Edit` и `Write` в `tools`), пишущим в смысле предыдущего пункта не считается. Подстановки артефактов все участники получают на момент старта группы.
- `AskUserQuestion` в группе запрещён: два вопроса одновременно UI, CLI и скилл пока не покажут.
- Пауза срабатывает на границе шагов: участники группы дорабатывают, следующий шаг не начинается до «Возобновить».
- «Остановить» прерывает сессии всех участников сразу.
- Если участник упал, раннер дожидается остальных и останавливает запуск со статусом `failed` и ошибкой первого упавшего по порядку объявления. Лимит стоимости (`--max-budget`) проверяется после группы, поэтому перерасход может достичь стоимости всей группы.
- Если блок с условием `marker` кончается группой, `until.phase` обязателен: «последний этап блока» у группы не определён.
- Группа из N этапов расходует 5-часовой лимит подписки в N раз быстрее.
- Файлы этапов нумеруются по месту в блоке, как обычно; в `run.json` у участников есть поле `group`, а отчёты идут в порядке завершения.

Если у этапа задана `output_schema`, её результат — JSON по этой схеме, и в `{{prev}}` попадает именно он. Поле `handoff` описывает, чем должен закончиться ответ, чтобы следующий этап мог его использовать: раннер дописывает его к промпту, а в конструкторе оно показано как подпись ребра между этапами.

### Дополнительные директории этапа

`add_dirs` открывает этапу директории кроме директории проекта, как `--add-dir` у Claude Code. Пути и вложения тегов знаний блока (`knowledge`, см. «Теги») добавляются этапам так же. Пример: отдельный проект с правилами QA подключён только к этапу тестирования. Пути абсолютные, от `~` или относительно директории проекта.

- Из этих директорий подхватываются `CLAUDE.md` и скиллы из `.claude/skills`.
- Что этап получит из `add_dirs`, видно на странице «Контекст»: выбери flow и этап.
- Раннер дописывает их список в конец промпта этапа, чтобы агент знал, куда смотреть.
- Если директории нет, запуск падает до первого этапа: молча работать без правил хуже.
- Судья (`until.type: judge`) их не получает. Если ему нужны те же правила, вынеси проверку в этап. Артефакты запуска судья при этом получает: раздел «Артефакты запуска», подстановки в рубрике и инструменты чтения.
- Папку артефактов раннер тоже передаёт сессии как дополнительную директорию, но только этапу с доступом к артефактам и не в этом списке: о своих артефактах этап узнаёт из раздела «Артефакты запуска».
- Директории уровня запуска (поле «Дополнительные директории» в форме запуска, `addDirs` в `POST /api/runs`) добавляются ко всем этапам вместе с их `add_dirs`, без дублей, и дописываются в тот же список в конце промпта. Судья их тоже не получает. Страница «Контекст» о них не знает и показывает только `add_dirs` этапа.

### Артефакты запуска

Артефакт — именованный текстовый файл запуска, объявленный во flow: план, чек-лист, решения. Раннер создаёт его до первого этапа в `runs/<id>/artifacts/`, и файл живёт весь запуск: переживает итерации и блоки, переносится при продолжении, а пользователь правит его в UI или скиллом `/agentgraph` между шагами. `{{prev}}` живёт до следующего этапа, и каждый этап пересказывает состояние заново; артефакт хранит одну текущую копию. Пример: `flows/example/example-artifacts.yaml`.

```yaml
artifacts:                      # на верхнем уровне, в обеих формах flow
  plan:                         # ключ: латиница, цифры, - и _
    title: План                 # по умолчанию ключ
    file: plan.md               # имя без каталогов: md, txt, json, yaml, yml; по умолчанию <ключ>.md
    initial: |                  # начальный текст как есть, без подстановок; без него файл пустой
      # План
  progress:
    title: Пункты проверки
  decisions:
    title: Решения
    decisions: true             # сюда дописываются ответы на паузу; не больше одного во flow
phases:
  - name: analyze
    tools: [Read, Grep, Glob]
    writes: [plan]              # правит только свои артефакты, Edit и Write в tools для этого не нужны
    prompt: ...
  - name: verify
    tools: [Read, Grep, Glob, Bash]   # Edit нет: код этап не правит
    reads: [decisions]
    writes: [progress]
    prompt: |
      План: {{artifacts.plan}}  # подстановка тоже даёт право чтения
      Отметь выполненные пункты в {{artifacts.progress.path}}.
```

- **Права.** Этап читает артефакты из `reads`, `writes` и подстановок `{{artifacts.KEY}}` / `{{artifacts.KEY.path}}` в промпте и `handoff`, а пишет только артефакты из `writes`. Недостающие `Read`, `Edit` и `Write` раннер разрешает этапу сам, но только для его артефактов: правка любого другого файла по-прежнему требует `Edit` или `Write` в `tools`. Этап с `Read` в `tools`, как и раньше, читает любые файлы, но узнаёт только о своих артефактах. Судья читает все артефакты.
- **Защита.** Правка чужого артефакта, создание необъявленного файла в папке артефактов и запись в папку `runs/` (кроме своих артефактов, в том числе инструментами из `tools`) отклоняются, а агент получает объяснение. То же действует в сабагентах этапа; сабагент с `isolation` этапу с неявными правами не запускается. Запись через `Bash` не предотвращается: после шага раннер помечает такое изменение и пишет предупреждение, но содержимое не откатывает. Перед каждым шагом всё постороннее в папке артефактов (каталоги, в том числе `.claude`, файлы на точку, симлинки, `CLAUDE.md`) переносится в `artifacts-quarantine/<время>/` с предупреждением: Claude Code грузит такие файлы как инструкции. Посторонний обычный файл с допустимым расширением остаётся с одним предупреждением, исчезнувший артефакт создаётся пустым. Имена `CLAUDE.md` и `CLAUDE.local.md` для артефактов запрещены.
- **Что видит этап.** В конце промпта (после `handoff` и списка дополнительных директорий, до вложений) стоит раздел «Артефакты запуска»: название, путь, доступ и последний автор каждого своего артефакта и два правила — «пиши только в артефакты с доступом „запись“» и «пути к артефактам — только отсюда». Артефакты, чей текст целиком подставлен в промпт, перечислены строкой «текст уже есть выше: читать файл ради содержимого не нужно» — иначе этапы перечитывают файл перед каждой правкой. Записываемые артефакты (кроме журнала решений `decisions`) перечислены строкой «текущее состояние, а не журнал»: обновлять так, чтобы файл описывал, как есть сейчас; списки пополнять и уточнять, но без истории попыток по итерациям. Если последнюю правку сделал пользователь через UI или скилл, строка говорит «учитывай её и не откатывай». Изменение файла между шагами не через UI помечено «изменён вне этапов, источник не установлен», без такого указания.
- **Большой артефакт.** Подстановка снимается на старте шага. Файл до 32 КБ уходит целиком, больше — картой до 8 КБ: разделы markdown по заголовкам вне блоков кода, ключи верхнего уровня JSON и YAML, иначе части по 200 строк. У каждого раздела — диапазон строк, размер и первая содержательная строка. Сам файл не меняется. Дочитать раздел этап может инструментами `artifact_read` (раздел по ключу из карты), `artifact_map` (полная карта) и `artifact_search` (поиск строк) или `Read` с `offset` и `limit`. Инструменты только читают и есть у каждого этапа и судьи с доступом к артефактам. Пишущему этапу, получившему карту, раздел велит перечитать файл после своих правок.
- **Авторство и версии.** После каждого шага раннер записывает, кто изменил артефакт: этап (с блоком и итерацией), пользователь (UI или скилл), «снаружи» (между шагами не через UI), «неизвестно» (во время этапа, который этот артефакт не пишет, например через `Bash`; с предупреждением) или условие (команда `until`). Каждое изменение — версия в `artifacts-history/<ключ>/`. Копию содержимого версия хранит у файла до 1 МБ, пока история запуска меньше 200 МБ; иначе версия записывается без копии, с предупреждением. Любую версию с копией можно открыть в окне артефакта.
- **Пункты чек-листа.** У markdown-артефакта (`.md`) сервер считает строки чек-листа вне блоков кода (``` и ~~~): `- [ ]` — открытые, `- [x]` и `- [X]` — закрытые; маркер `-`, `*` или `+`, отступ любой. Счёт обновляется с каждой новой версией и лежит в поле `tasks: { open, done }`: в списке артефактов (`GET /api/runs/<id>/artifacts`), в событии `artifacts`, в `run.json` (`artifacts.items[]`) и в чтении текущей версии артефакта. Чтение версии `?version=N` поля не несёт. Если файл изменён после последней записанной версии (`unrecorded`), чтение считает по текущему тексту, а список до следующей версии показывает прежнее число. Нет пунктов, файл не `.md` или больше 8 МБ — поля нет. В UI это бейдж «открыто N из M» в строке артефакта и в шапке его окна, например у артефакта `progress` («Пункты проверки»): сколько проблем осталось, видно без открытия файла.
- **Правка на ходу.** Пока идёт шаг, который пишет артефакт, правка в UI заблокирована. Правку подхватывает каждый шаг, начавшийся после сохранения: этап, группа или проверка условия. Этап, который уже идёт, получил прежнюю версию. Надёжнее править на паузе: «Пауза» → шаг доработает → правка → «Сохранить и возобновить».
- **Ссылайся на артефакт, а не на пересказ этапа.** Правка пользователя доходит до этапов, которые читают артефакт, но не до тех, кто берёт `{{phases.<этап>}}`: вывод этапа уже написан. Этапу реализации давай `{{artifacts.plan}}`, а не `{{phases.analyze}}`.
- **Состояние, а не журнал.** Артефакт описывает, как есть сейчас: открытый пункт — одна строка (`- [ ] … (открыт с итерации N)`), подтверждённое исправление — `- [x]` одной строкой. Не проси этапы дописывать «итерация N: снова не исправлено»: историю хранят версии в `artifacts-history/`, а журнал раздувает промпт каждого следующего этапа, которому артефакт подставлен текстом. Исключение — артефакт `decisions`: ответы на паузу в него дописываются.
- **Текст или путь.** `{{artifacts.KEY}}` давай этапу, которому артефакт нужен всегда; `{{artifacts.KEY.path}}` — тому, кто читает его изредка, и для того, что растёт: патчи, логи, длинные списки. Громоздкое (например, готовый патч для ручного применения) держи отдельным артефактом, чтобы этапы, которым нужна сводка, его не несли.
- **Когда нужен артефакт.** План, по которому реализация идёт несколько итераций; чек-лист сделанного и открытого; решения пользователя. Линейному flow и циклу, где этапу нужен только прошлый вывод, хватает `{{prev}}`. Этапу проверки, который отмечает пункты, дай `writes: [progress]` вместо `Edit`: код он править не сможет. В рубрике судьи проси проверять результат по файлам проекта и командам, а не по тому, что отмечено в артефакте. Не ставь `max_turns` 1–3 этапу с доступом к артефактам: даже с `tools: []` модель часто сначала открывает файл инструментом и упирается в лимит ходов.
- **Валидация** (блокирует сохранение в UI, `show` и запуск): имена ключей и файлов, дубли `file` без учёта регистра, ссылки `reads`, `writes` и `{{artifacts.KEY}}` на необъявленный артефакт (с местом), больше одного `decisions: true`, правила групп (см. «Параллельные этапы»). Объявленный, но никем не используемый артефакт — не ошибка: его читает судья или правит пользователь.
- **CLI.** `show` печатает артефакты flow, `run` в конце — путь к папке артефактов. Правки на ходу в CLI нет: шаги идут подряд, но файл, изменённый руками во время запуска, засчитывается по правилам авторства.
- Flow без `artifacts`, `reads` и `writes` работает байт в байт как раньше: ни раздела в промпте, ни папок, ни полей артефактов в `run.json`.

### Инструменты и права

Перечисленные в `tools` инструменты **разрешаются без подтверждений**: в headless-режиме любой запрос на подтверждение автоматически превращается в отказ, так что иначе агент просто не смог бы редактировать файлы или запускать команды. Отсюда принцип минимальных прав: `Bash` только тем этапам, которым он реально нужен. `permission_mode: bypassPermissions` снимает вообще все проверки, используй осознанно. Права на артефакты (`reads`, `writes`) доступ к файлам проекта не расширяют: они касаются только своих артефактов этапа.

**Коннекторы claude.ai** — Jira и Confluence (Atlassian), Slack, Docs, подключённые в аккаунте. Этап получает их, только если перечислил нужные инструменты в `tools` точными именами, например `mcp__claude_ai_Atlassian_Rovo__getJiraIssue`, или весь коннектор одной записью `mcp__claude_ai_Atlassian_Rovo`: тогда без подтверждения разрешены все его инструменты, в том числе меняющие данные, и новые инструменты коннектора этап получит сам. Остальным этапам и судье раннер коннекторы не подключает (`ENABLE_CLAUDEAI_MCP_SERVERS=false`). Вызвать инструмент не из списка этап всё равно не может, а подключённые коннекторы после первого вызова любого инструмента кладут в контекст определения всех своих инструментов — около 45K токенов на каждый следующий запрос. Исключение — `permission_mode: bypassPermissions` или `auto`: там коннекторы остаются. Локальных MCP-серверов (Figma desktop и т. п.) это не касается. Выдать коннекторы этапу проще всего в конструкторе — строка «Коннекторы claude.ai» (см. «Веб-интерфейс»).

Фоновых задач у этапов и судьи нет: `Bash` и сабагенты работают синхронно. Команда без `timeout` идёт до 30 минут, с `timeout` — до часа; не уложилась — её убивают. Сессия кончается вместе с ответом агента, и фоновая задача погибла бы с ней: агент написал бы «жду уведомления», а push или сабагент оборвались бы. Процесс, который должен пережить этап (эмулятор, dev-сервер), запускай отвязанным от сессии: `nohup <команда> > <лог> 2>&1 &`.

## Что остаётся после запуска

`runs/<время>-<name>/`:

- `flow.yaml` — спецификация, с которой шёл запуск; у разового запуска это единственная копия flow, по ней идёт и продолжение
- `run.json` — статус, стоимость, ходы, `sessionId` каждого этапа (можно открыть `claude --resume <id>`), `pid` процесса раннера, `final` — итог: этапы последнего шага (`block`, `iteration`, `phase`, `title`, `ok`, `output` — путь вывода от папки запуска). У запусков до появления поля его досчитывает `GET /api/runs/:id`
- в `run.json` у разового запуска: `adhoc: true` (у обычных запусков поля нет)
- в `run.json` у каждого этапа: `model` — фактическая модель из `system/init` Agent SDK, а если init не пришёл (сессия упала до старта) — заданная (этап → `defaults` → `--model` или поле «Модель» формы); `effort` — заданный (этап → `defaults`), потому что SDK фактический effort не отдаёт. Ключа нет, если значение неизвестно: так у запусков до этого изменения и у этапов, где модель и effort нигде не заданы, а init не пришёл;
- в `run.json` у каждого этапа: `tokens` — токены его сессии: `contextStart` и `contextPeak` — контекст первого и самого большого запроса главного цикла (input + чтение и запись кэша; сабагенты не входят), `requests` — число запросов к модели, `contextWindow` — окно модели главного цикла из `modelUsage` результата (нет, если окно неизвестно: SDK прислал 0 или запись главной модели не опознана среди нескольких), `input`, `output`, `cacheRead`, `cacheCreation` — итог по всем моделям сессии, включая сабагентов; если сессия оборвалась без результата, итогов и `contextWindow` нет, есть только контекст. Поля `tokens` нет, если SDK не прислал usage (сессия упала до первого запроса), и у запусков до этого изменения
- `iter-01/01-analyze.prompt.md` — отрендеренный промпт этапа
- `iter-01/01-analyze.transcript.md` — текст ответов и вызовы инструментов
- `iter-01/01-analyze.output.md` — итоговый вывод этапа (то, что ушло в `{{prev}}`)
- `iter-01/condition.json` (+ `.command.log` / `.judge.prompt.md`) — как проверялось условие
- `chat.json` — история чата запуска и id его сессии (появляется после первого сообщения в чат)
- `attachments/` — вложения к задаче из формы запуска (или скопированные из продолжаемого запуска); их пути относительно папки запуска лежат в `run.json` в поле `attachments`, а директории уровня запуска — в `addDirs`
- `artifacts/` — файлы артефактов запуска (только у flow с `artifacts`); открыты этапам с доступом и судье
- `artifacts-history/<ключ>/0001.md`, `0002.md`, … — версии артефакта после каждого изменения; лежат вне `artifacts/`, агентам не видны
- `artifacts-quarantine/<время>/` — что раннер убрал из папки артефактов перед шагом (появляется только при находках); `.tmp/` — временные файлы атомарной записи
- в `run.json` у flow с артефактами: `artifacts` — артефакты с последним автором и версиями, `from` (из какого запуска взяты при продолжении) и предупреждения уровня запуска; у этапа и условия — `artifacts.changed` и `artifacts.warnings`, у этапа ещё `denials` (отказы записи); у паузы — `answer`

У flow из нескольких блоков итерации лежат в папке блока: `01-spec/iter-01/…`, `02-split/iter-01/…`. В `run.json` есть `blocks` (статус и итерации каждого блока), а у этапов и условий — поле `block`.

У запуска с тегами в `run.json` есть `tags` (слаги), `saveTag` (галочка) и `tagSummaries` — итог сессии саммари по каждому тегу: `tag`, `ok`, `costUsd`, `tokens`, а если саммари не обновлено — `skipped` (почему сессии не было) или `error`. В папке запуска — `tag-summary.<slug>.prompt.md`, промпт сессии каждого тега. У запуска с галочкой автотега есть ещё `autoTag`: `slug` и `title` заведённого тега (он же в `tags`) или `error`, плюс `costUsd` и `tokens` сессии подбора. У запусков без тегов нет ни полей, ни файлов.

Имя запуска (см. «имя запуска» в разделе «Веб-интерфейс») лежит в `run.json` в поле `title`. Поле `titleSession` описывает сессию подбора: `costUsd`, `tokens` и `error`, если имя не получилось. Сессия подбора имени промпт в папку запуска не пишет. У продолжения с унаследованным именем есть `title`, но нет `titleSession`. У старых запусков нет ни одного из этих полей.

## Теги: задачи и области знаний

Тег бывает двух видов (`kind` в `tag.json`; старые теги без поля — теги задачи, вид после создания не меняется):

| Вид | Что это | Куда попадает |
|---|---|---|
| `task` — тег задачи | саммари фичи между запусками (реализация → фикс багов → ревью → конфликты), заметки, пути, вложения | блок `<!-- tag:<slug> -->…<!-- /tag -->` в начало задачи; после `done` — сессия саммари |
| `knowledge` — тег области знаний | что должны знать этапы (фронтенд, бэкенд, QA): описание «когда нужен», заметки как инструкции, пути, вложения; саммари нет | строка «- <slug> — <заголовок>: <описание>» под шапкой «Области знаний …» в конец промптов этапов блока с полем `knowledge: [qa]` в flow.yaml (или всех блоков, если тег выбран в форме запуска) плюс инструмент `knowledge_read`, которым этап читает тег целиком; тег с `inline` — старый полный раздел «Область знаний <slug>»; пути тега в доп. директории этапов и судьи в любом режиме |

Фичу часто дорабатывают несколькими запусками. Чтобы не описывать её каждый раз заново, запуску дают **тег задачи** — например, `loyalty-card`: краткое саммари, которое ведёт модель, плюс твои заметки, пути и вложения. Тегов на запуск может быть несколько (до 10): фича и, например, тег знаний с правилами платформы.

**Тег знаний** заводится на странице «Теги» с видом «область знаний» и вешается на блок полем `knowledge` (конструктор: поле «Теги знаний» у блока). Несуществующий тег или тег задачи в `knowledge` — ошибка до старта этапов (в UI — 400 с именем блока). Заметки тега ограничены 4000 знаками, описание — 200, тегов на блок — до 10. По умолчанию тег раскрывается постепенно: в промпте этапа одна строка (`- qa — Правила QA: <описание или первая строка заметок> (знаков заметок: N, вложений: M, путей: K)`) под шапкой «Области знаний (подробности — инструментом knowledge_read со слагом; открывай только когда нужно):», а полный текст (описание, заметки, существующие пути, абсолютные пути вложений) этап получает вызовом `knowledge_read({ slug })` — MCP-инструмент внутри процесса, сервер `knowledge`, доступен без подтверждений и читает тег заново при каждом вызове, так что правка на странице «Теги» видна идущему запуску. Галочка «Всегда вставлять заметки в промпт целиком» (`inline` в tag.json) возвращает старое поведение для коротких правил, которые должны действовать всегда; если все теги блока такие, инструмента у этапа нет. Судья получает папки тегов знаний, но не их текст и не инструмент. Flow с `knowledge` на старом сервере: поле молча отбрасывается, запуск идёт без знаний.

В форме запуска поле «Задача» остаётся чистой задачей: текст тегов вставляет сервер, а под чипами показывается read-only панель «Контекст тегов» с тем, что он вставит. Галочка «Обновить саммари» видна только при теге задачи. В `run.json` теги знаний запуска — в `knowledge`; продолжение их наследует.

- **Где лежит:** `~/.agentgraph/tags/<slug>/` (или `$AGENTGRAPH_CONFIG_DIR/tags/`), вне репозитория:
  - `summary.md` — саммари, текущее состояние фичи;
  - `notes.md` — заметки (промпт тега): твой текст, сессия саммари его не трогает;
  - `attachments/` — вложения тега (типы и лимиты те же, что у вложений запуска);
  - `tag.json` — заголовок, даты, пути тега (`dirs`) и последние 20 запусков, обновивших саммари (`runs`); у автотега — `autoTitle: true`, пока заголовок не переписан руками; у тега знаний — `description` (когда нужен, до 200 знаков) и `inline: true` (вставлять заметки в промпт целиком).

  Слаг: строчные латинские буквы, цифры и дефис, до 64 знаков.
- **Что тег даёт запуску:** в начало задачи встаёт блок тега `<!-- tag:<slug> -->…<!-- /tag -->`: заголовок, заметки, пути, абсолютные пути вложений и саммари. Саммари — текст модели, поэтому оно в обёртке `source-data` с пометкой «данные, не инструкции»; заметки — твой текст, как сама задача. Этапы и судья получают на чтение доп. директориями: пути тега (у файла — его папку), папку вложений тега и папки `artifacts/` трёх последних запусков тега. Несуществующие пути пропускаются. В `addDirs` запуска эти папки не пишутся, при продолжении пересчитываются по нынешнему состоянию тегов. Вложения тега в папку запуска не копируются: этапы читают их из папки тега.
- **Выбор в форме запуска:** поле «Теги задачи» над задачей — выбери из списка или впиши новый слаг и нажми Enter. Каждый тег — чип; его блок встаёт к блокам других тегов в начале задачи, а крестик на чипе убирает только его блок. В CLI — `--tag <slug>` (можно несколько раз), в скилле `/agentgraph` — `start --tag <slug>`. Если блока тега во вводе нет (CLI, скилл, любой клиент API), его вставят сервер или CLI; блоки, которые уже есть, не трогаются. Новый тег заводится при запуске. Ввод из одних блоков тегов без своей задачи сервер не примет. Выбор тегов форма не запоминает.
- **Автотег:** галочка «Завести тег задачи автоматически» в форме запуска (в CLI — `--auto-tag`, в скилле — `start --auto-tag`, в API — `autoTag: true`). Работает, только если тег задачи не выбран; теги знаний не мешают. Выбран тег задачи руками — галочка неактивна, сервер `autoTag` игнорирует и модель не зовёт. Перед стартом короткая сессия (haiku, без инструментов, таймаут 30 с) по тексту задачи, имени flow и источнику запуска придумывает слаг и заголовок, и заводится **новый** тег задачи. Заголовок модели чистится: одна строка без управляющих символов и угловых скобок, до 80 знаков. Он придуман по недоверенному тексту (тикет пишет кто угодно), поэтому помечается `autoTitle` и в блок тега для этапов не попадает — шапка блока только «Тег задачи: <slug>»; на странице «Теги» он виден как обычно, а переписанный руками заголовок становится твоим текстом и попадает в блок. Существующие теги модели не показываются и не переиспользуются: если слаг занят (тегом любого вида или просто папкой), заводится `<слаг>-2`, `-3`…, а чужой тег не меняется. Дальше — как с тегом, выбранным руками: блок в задаче, после `done` — саммари; «Обновить саммари» для автотега не действует, саммари обновляется всегда (поэтому `--auto-tag` с `--no-save-tag` — ошибка). Чтобы продолжить фичу, выбери её тег руками или нажми «Продолжить»: автотег для «поправь ревью по X» заведёт отдельный тег. Сбой подбора (ошибка, таймаут, невалидный слаг) — не ошибка запуска: он идёт без тега, причина — в ответе `POST /api/runs`, в уведомлении UI и в `run.json` → `autoTag.error`. Продолжение запуска наследует его тег, новый не заводит. Галочка запоминается в браузере, по умолчанию выключена. Тег заводится при старте, поэтому у упавшего запуска остаётся тег без саммари.
- **Страница «Теги»** (`/tags` в UI): список тегов, заведение нового, редактор — заголовок, саммари, заметки, пути (абсолютные, по одному на строку), вложения, запуски с тегом, удаление тега; у тега знаний ещё поле «Описание — когда этот тег нужен» и галочка «Всегда вставлять заметки в промпт целиком», а в списке вместо начала заметок показывается описание. Справа — крупный редактор на всю высоту окна: в нём правится то поле (саммари, заметки или пути), в котором стоит фокус; при открытии тега там саммари, у тега знаний — заметки. Правка справа — та же правка поля: «Сохранить» и вопрос о несохранённом работают как обычно. Если страница уже 1200 px, редактора справа нет. Правка саммари руками доживёт до следующего успешного запуска с галочкой: тогда сессия перепишет его, взяв правку за основу.
- **Обновление саммари:** галочка «Обновить саммари тегов после запуска» видна при выбранных тегах и включена по умолчанию; в CLI и скилле её снимает `--no-save-tag`. После запуска со статусом `done` по каждому тегу идёт короткая сессия (haiku, только Read/Grep/Glob, до 15 ходов), по очереди. Она переписывает саммари своего тега целиком: это текущее состояние, а не журнал. Разделы: «Суть», «Где код» (ветка, worktree, MR), «Ключевые решения», «Что осталось», «Где читать подробнее». Саммари длиннее 2500 знаков обрезается с пометкой. Пути в папку запусков, кроме `<id>/artifacts/…`, код заменяет пометкой «недоступен следующим запускам»: выводы этапов (`iter-*/…output.md`) следующим запускам не видны. При любом другом статусе саммари не трогаются. Ошибка сессии не меняет статус запуска: она пишется в `error` этого тега, его старое саммари остаётся. «Остановить» во время саммари прерывает текущую сессию и пропускает оставшиеся, запуск остаётся `done`.
- **Продолжение** запуска наследует теги и галочку; блоки тегов уже в его задаче. Автотег при продолжении не повторяется.
- **Ограничения:** два одновременных запуска с одним тегом — побеждает последний записавший, обновление первого может потеряться. Запись в папки артефактов прошлых запусков guard запрещает только у flow с артефактами; пути тега этапам открыты так же, как доп. директории. Стоимость сессий саммари не ограничена `--max-budget`: лимит проверяется на этапах. Переименования тега нет: заведи новый.

API: `GET /api/tags` (список с `kind`), `POST /api/tags` (`{ slug, title?, kind? }`, по умолчанию `task`), `GET /api/tags/<slug>` (тег и готовый текст `input`: блок у тега задачи, раздел знаний у тега знаний), `PUT /api/tags/<slug>` (`{ title?, summary?, notes?, dirs?, description?, inline? }` — переданные поля заменяются целиком; `description` и `inline` только у тега знаний, иначе 400), `DELETE /api/tags/<slug>`, `POST /api/tags/<slug>/attachments` (`{ name, data }`, base64), `DELETE /api/tags/<slug>/attachments/<имя>`. В `POST /api/runs` — поля `tags` (список слагов), `saveTag` и `autoTag` (`true` — завести новый тег задачи, см. «Автотег»; не булево — 400); в ответе 201 при автотеге — `autoTag: { slug, title? }` или `autoTag: { error }`. Фичи сервера в `GET /api/config` — `tags` и `auto-tag`.

## Анализ flow

Карточка «Анализ flow» на вкладке «Обзор» завершённого запуска (фича сервера `run-analysis`). `POST /api/runs/<id>/analysis` с телом `{ model? }` (по умолчанию sonnet) запускает сессию без инструментов (до 3 ходов) и отвечает готовым результатом; у идущего запуска — 409 `code: live`, при втором анализе того же запуска одновременно — 409 `code: busy`. `GET /api/runs/<id>/analysis` отдаёт сохранённый `runs/<id>/analysis.json` или 404 `code: missing`. Рядом пишется `analysis.prompt.md` — промпт сессии.

Модели отдаются факты из `run.json` и YAML flow (снимок `runs/<id>/flow.yaml`, у старого запуска — восстановленный из отчёта): по блокам — условие, итерации, вердикты с началом замечаний и признаком застоя (`stale`: замечания повторили прошлую итерацию); по этапам — инструменты, пишущий ли, модель, запусков, ходы (среднее, максимум, упирался ли в `max_turns`), стоимость, время, пик контекста и доля окна, отказы guard, размер шаблона промпта, что использует промпт (`{{prev}}`, `{{feedback}}`, `{{phases.*}}`, артефакты), `reads`/`writes`. Системный промпт — приёмщик архитектуры с правилами: граница между этапами оправдана только контекстом; объединять этапы на выходе друг друга с низким пиком контекста (ориентир < 40% окна); разбивать или сужать этап с пиком > 75% окна или упёршийся в лимит ходов; command вместо judge при детерминированной проверке; застой замечаний — менять промпт или условие, не жечь итерации; лишние права сузить; справочное вынести за инструмент; блоков больше одного — только при разных критериях готовности; flow хорош — сказать это и не выдумывать правки.

Ответ `RunAnalysis`: `{ at, model?, costUsd, tokens?, verdict?: keep | improve | rework, summary, suggestions[], facts, error? }`, рекомендация — `{ kind: merge | split | remove | tools | condition | prompt | context | parallel | other, severity: high | medium | low, phases[], title, why, how }` (до 20, мусор отбрасывается). Сбой модели не ошибка запроса: приходит `error` и факты без вердикта. Стоимость анализа в `totalCostUsd` запуска не входит.

## Eval flow

`agentgraph eval <flow|file.yaml> --tasks <tasks.yaml> [--runs N] [--compare <flow2|file.yaml>] [--cwd dir] [--max-budget usd] [--max-iterations n] [--model id] [--json out.json] [-v]` — сквозной прогон набора задач через один или два flow.

Файл задач:

```yaml
tasks:
  - name: fix-tests          # обязательно: латиница, цифры, - и _, уникально
    input: "Почини тесты"    # обязательно: задача ({{input}})
    cwd: ~/code/repo         # необязательно; ~ раскрывается, относительный путь — от папки tasks.yaml; иначе --cwd
    setup: git checkout -- . && git clean -fd   # необязательно: shell перед каждым прогоном; не 0 — прогон не идёт, запись с ошибкой
    check: npm test          # необязательно: shell после прогона со статусом done; 0 = решена. Без check решает статус
    timeout_sec: 600         # необязательно: таймаут setup и check
```

Порядок строго flow → задача → прогон, последовательно. Каждый прогон — обычный запуск в `runs/` (`title` «eval <flow> · <задача> #<n>», видны в UI); `--max-budget`, `--max-iterations` и `--model` действуют на каждый. Исключение одного прогона не валит eval: запись `pass: false` с `error`. SIGINT останавливает после текущего прогона (код выхода 2); завершённый eval даёт 0, даже если задачи не решены: это измерение. `--tag`, `--auto-tag`, `--once`, `-o`, `--input` с eval несовместимы; вопросы агента отклоняются. Команды `setup` и `check` идут через shell, как `command`-условие flow.

Вывод: строка прогресса на прогон, затем таблица «Задача | flow1 | flow2» с ячейками `2/2 100% · $0.40 · 1м 2с · ит. 1.0`, строка «Итого» и при двух flow раздел «Перевернулись»: задачи, у которых доля решённых различается между flow. Результаты — `runs/evals/<YYYY-MM-DD_HH-MM-SS>-<flow>[-vs-<flow2>]/results.json` (перезаписывается после каждого прогона, копия по `--json`): `{ version: 1, startedAt, finishedAt, tasksFile, flows, tasks, runs, cwd, aborted?, records[], cells[], totals[], flipped[] }`, где `records[]` — `{ flow, task, run, runId, status, pass, costUsd, durationMs, iterations, setupExit?, checkExit?, output?, error? }`.

## Стоимость

Каждый этап — новая сессия с полным системным промптом Claude Code (~33K токенов). Первая сессия за час платит за запись кэша, остальные читают его дёшево. Сколько контекста этап получил на старте и до скольких он вырос, видно в `tokens` этапа в `run.json` и на карточке этапа (чип `ctx`). Ограничивай расход через `--max-budget`, `defaults.max_budget_usd` и `max_turns`. Генератор работает без инструментов и с коротким системным промптом, он дешёвый. Сессия саммари тега (по одной на тег, только при статусе `done`) идёт на haiku, её стоимость входит в итог запуска и видна в `tagSummaries[].costUsd`; `--max-budget` её не ограничивает. Сессия подбора автотега (haiku, без инструментов, до старта) тоже входит в `totalCostUsd` с самого начала — `autoTag.costUsd` — и учитывается в `--max-budget` на первом же этапе. Сессия подбора имени запуска (haiku, без инструментов, идёт параллельно этапам после старта) тоже входит в `totalCostUsd`: прибавляется, когда имя готово, и видна в `titleSession.costUsd`. Судья тоже с коротким промптом, но может читать файлы и звать сабагентов, поэтому дороже прежнего.

## Ограничения и что дальше

- Этапы внутри блока можно запускать параллельно группами (`group`). Параллельных блоков и ветвлений нет: блоки идут строго по очереди, а продолжение запуска, `{{prev}}` между блоками и полоска блоков в UI рассчитаны на этот порядок.
- Между этапами передаётся текст выводов (`{{prev}}`, `{{phases.NAME}}`) и артефакты запуска. Артефакт живёт только внутри запуска и его продолжений: файлов, общих для независимых запусков, артефактов вне папки запуска (например, в репозитории проекта), папок с файлом на задачу и двоичных артефактов нет.
- Запись в артефакт через `Bash` не предотвращается, а только помечается автором «неизвестно» с предупреждением. Правки артефактов на ходу в CLI нет, слияния одновременных правок пользователя и этапа тоже: вместо этого правка блокируется на время пишущего шага.
- Flow из одного блока нельзя продолжить с места остановки, в том числе flow с артефактами: правку артефактов остановленного одноблочного запуска некуда применить, поэтому она недоступна.
- Разовый запуск из одного блока (а генератор чаще всего делает один блок) тоже нельзя продолжить, поэтому «Продолжить» у разовых запусков доступна реже. Черновик разового запуска живёт только во вкладке браузера: перезагрузка или закрытие вкладки его теряют (уход спрашивает подтверждение). Страница «Контекст» для черновика не работает: она берёт flow по имени из `flows/`. «Запустить…» из задачи Jira, MR или ветки разовый запуск не предлагает.
- Условие проверяется после полного прохода этапов. Ранний выход внутри итерации можно сделать через `marker` на промежуточном этапе.
