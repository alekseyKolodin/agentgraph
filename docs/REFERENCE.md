# agentgraph: reference

> Overview and demo are in the [README](../README.md). New here? Start with [GETTING_STARTED.md](GETTING_STARTED.md): how it works, installation, first run, deployment and how to share a project. Below is the full reference.

Task → `flow.yaml` → a chain of Claude Code sessions, looped until a condition is met.

The idea:

1. You drop in a task description.
2. The **generator** (a Claude session without tools) turns it into a flow spec: phases (`phases`), phase prompts, the tools of each phase, a stop condition.
3. The **runner** executes the spec: each phase = a fresh Claude Code session with its own prompt, into which the previous phase's output is substituted. After all phases have run, the condition is checked; if it is not met, the next iteration starts, and the condition's feedback goes into the prompts.
4. A flow can consist of several **blocks** in a row: a loop until a condition, then steps in a single pass, then another loop with its own condition (see "Multiple blocks in a row").
5. Besides output text, phases can maintain shared **run artifacts**: named files (plan, checklist, decisions) that survive iterations and blocks, are protected by phase permissions and can be edited by the user in the UI between steps (see "Run artifacts").

Under the hood is `@anthropic-ai/claude-agent-sdk`: the same authorization as your `claude`, the same tools (Read/Edit/Bash…), sessions are visible in `claude --resume`.

## Installation

```bash
npm install
npm run build
```

Run in dev mode without building: `npm run agentgraph -- <arguments>`. To make the `agentgraph` command available globally: `npm link` (after `npm run build`).

## Web UI

```bash
npm run ui            # http://127.0.0.1:4747
```

The UI is a React app from `web/`: `npm run ui` builds it into `dist/web` itself if there is no build or `web/` has changed, and the server serves it at `/`. Screen addresses are plain paths: `/flow/<name>`, `/run/<id>`, `/tags`, `/tags/<slug>`, `/context`, `/draft`; for any of them the server returns `index.html`, and an unknown path leads to Home. Old links keep working: the UI itself translates `/#run/<id>`, `/#flow/<name>`, `/#tags/<slug>`, `/#context` of the previous interface into paths, and the server redirects `/next/…` (the UI address during the move to React) to `/…` with a 308 response.

The interface is in Russian by default; the **EN / RU** button next to the logo in the sidebar switches it to English and back. The choice is stored in the browser (`localStorage` key `agentgraph.lang`) and applied after the page reloads. Only the UI's own text is translated: flow content, agent output and most messages from the server stay as they are. The runner's own condition texts (the loop condition, "marker … as the last line", "Command … exited with code") and artifact edit rules are translated by the UI. Text from the helper models (run name, iteration summaries, the judge's verdict, flow analysis, auto-tag title) is written in the language of the task, not of the UI: an English task gets English summaries.

On the left are the "Home" and "Context" items, the flow list and the run history; on the right is the selected flow. Clicking a flow in the list, a `/flow/<name>` link and "Open flow" on a run page open the "Run" tab; a newly created flow opens in the Builder, a flow with an invalid spec opens on YAML:

- **Home** (the first item on the left, "Home", the "agentgraph" logo or the address `/`): agent questions from all active runs in one list, the ones waiting longest first. You can answer right there without opening the run; a half-written reply is not reset while events from other runs arrive. Below are the active runs: the block strip, the current block, iteration and phase, how long it has been running and how much it costs, and the "Open", "Pause"/"Resume", "Stop" buttons. The number of questions waiting for a reply is shown in the tab title ("(2) agentgraph", on a run page "(2) <run name> · agentgraph") and on the "Home" item on the left, on any screen. "Enable notifications" turns on browser notifications about new questions and about a run's end; the button is there until the browser has asked for permission, and if permission is denied, a "Notifications off" mark stands in its place (the tooltip says why). Notifications arrive when the tab is not visible; if the tab is visible but another run or flow is open, a toast pops up at the bottom right, and clicking it leads to Home. If no open tab will show the notification itself (the UI is closed or browser notifications are not enabled), the server reports the question and the run's end with a system notification — see "Notifications" below. The Home header shows the **Claude subscription limits**: the share of the 5-hour and weekly windows and the reset time, as in Claude Code's `/usage` (`GET /api/limits`; the server gets them through the Agent SDK without calling the model and caches them for a minute, `?force=1` bypasses the cache). The bar turns yellow from 70% and red from 90%; click it to refresh. With an API key, Bedrock or Vertex there are no subscription limits, and the block is not shown. On the right of Home is the **"Events"** panel: a feed of the same things notifications are about (an agent question and the reply to it, a pause at the agent's request and the resume, a run's end with status and cost), newest to oldest, over the last 50 runs and all active ones; the first 20 events are visible, "N more" opens the rest. The feed is built from `run.json` (`GET /api/feed`), so it survives a tab reload and a server restart and sees runs from the CLI; hidden runs do not get into it. Events new since the last "Mark as read" are highlighted, and their count is next to the heading (the mark is stored in the tab's `localStorage`). Clicking an event opens the run; clicking a question that is waiting for a reply opens its card on Home. On a narrow screen the feed comes right after the questions and active runs. Home lives on the shared event stream of all the server's runs (`GET /api/events`, SSE) and fetches its state from `GET /api/home`;
- **Context** (the "Context" item on the left, `/context`): what a session will get before the first message. You choose a project directory (the suggestions are the same recent directories as in the run form: the default directory, projects from "Connections", `cwd` and `addDirs` of runs; projects removed from "Connections" are not shown) and, optionally, a flow, a phase and a model. The page shows memory files with tokens (`~/.claude/CLAUDE.md`, the project's CLAUDE.md and `CLAUDE.local.md`, `.claude/rules/*.md`, CLAUDE.md from the phase's `add_dirs`, auto-memory), skills and subagents with their source and tokens, MCP servers, the system prompt (the standard `claude_code` preset or the phase's `system` as text), tools (the phase's `tools` plus the implicit Agent and Skill; without a phase, all of them) and tokens by category. With a phase, its `add_dirs`, `plugins` (its own and the block's), `tools`, `system` and model (phase → flow `defaults` → selected model) are taken into account. If a directory from `add_dirs` or a folder from `plugins` is missing on disk, the page warns about it and keeps working: such a plugin does not go into the listing. With a phase there is a "Phase prompt by source" section (`prompt` in the response: `parts` with `kind` prompt / handoff / dirs / knowledge-lines / knowledge-inline, characters before substitutions; `vars` — template variables; `chars`): the prompt template, the handoff, the list of additional directories, the lines of on-request knowledge tags as one part and each full-text tag as its own; the artifacts section and attachments are only known during a run and are not included. Warnings: full-text tags take more than half of the prompt (and at least 2000 characters), the prompt is longer than 16000 characters before substitutions, instructions come from four or more sources (memory files, full-text tags, a custom system prompt). Claude Code itself does the counting through the Agent SDK (`getContextUsage` on a session without a prompt, the model is not called), and the session options are built by the same code as the runner's, so what is shown matches a real run. Each listing spins up a Claude Code process (about a second); the server caches it for a minute; "Refresh" asks again. "Open" on CLAUDE.md and rules opens an editor with a markdown preview; "Save" writes the file and recalculates the listing. If the file was changed externally in the meantime, the save is rejected (409), and "Reload" pulls in the version from disk. Only `.md` files from this server's listings are editable (checked by realpath); managed policies and everything from `~/.claude/plugins` and `~/.claude/cache` are view-only; skills, `settings.json` and files not from the listing are neither written nor read. CLAUDE.md files are ordinary files on disk and can contain tokens and internal addresses: the content is shown only on "Open". API: `GET /api/context?cwd=&flow=&phase=&model=&force=1`, `GET /api/context/file?path=`, `PUT /api/context/file` with `{"path", "text", "mtimeMs"}` (the response is the new `mtimeMs`; 403 — the file is not from the listing or is not editable, 404 — a file from the listing has disappeared from disk, 409 — changed externally); for `GET /api/context`, 400 — an invalid flow name or no project directory, 404 — no such flow or phase, a listing taking longer than 30 seconds is cut off with an error;
- **Tasks and code** (on Home): Jira issues (the "My sprint", "All mine" presets, a custom JQL), open MRs (via `glab`, the "Mine" filter) and local project branches. Each list shows the first 5 rows; "N more" opens the rest. "Run…" builds the task (`{{input}}`) from a ticket, MR or branch and opens the "Run" tab of the selected flow; the run does not start by itself. In the run form you can prepare a separate git worktree. The run stores `source` and `worktree` in `run.json`; linked runs are shown under the row. Jira settings and token live in `~/.agentgraph` (`AGENTGRAPH_CONFIG_DIR`). More in [GETTING_STARTED.md](GETTING_STARTED.md#run-from-a-jira-issue-mr-or-branch). API: `GET /api/integrations`, `PUT|DELETE /api/integrations/jira`, `GET /api/jira/issues`, `POST|PUT|DELETE /api/projects`, `GET /api/projects/mrs|branches`, `POST /api/intake`, `POST /api/worktrees`;
- **My MRs: need attention** (on Home, above "Tasks and code"): your open MRs from the projects in "Connections" (GitLab only, via `glab`) that have at least one reason:
  - the branch's latest pipeline failed (only `failed`; `canceled` and running ones don't count);
  - there are unresolved discussions where the last non-system message is not yours (bots count too);
  - there are conflicts (`has_conflicts` or `detailed_merge_status: conflict`).

  Each reason has a link: "CI failed" leads to the pipeline, the others to the MR. An error in one project (for example, `glab` is not authenticated on the host) is shown under the list and does not hide the others. "Run…" works as in "Tasks and code", but a line "Needs attention: …" with the reasons at the time of the run is added to the flow input. After the list loads, the server asks haiku (`claude-haiku-4-5-20251001`, a session without tools) once in the background which flow fits each MR. If there is a suitable one, a "→ <flow>" chip appears in the row (the tooltip says why); clicking it opens "Run" for that flow with the input filled in. If there is no suitable one or the model named a flow not from the list, there is no suggestion. A run never starts by itself. The list is cached for a minute (↻ bypasses the cache) and is refreshed on Home if it is older than 5 minutes. Suggestions are cached by MR, reasons, MR update time and flow list, so the model is asked only about what is new. Each MR takes one or two `glab` requests (discussions only if the MR has comments), no more than 4 at a time; more than 100 discussions in one MR are not read. API: `GET /api/attention[?force=1]` → `{ items, errors, at }`, `POST /api/attention/suggest` with `{"refs": [...]}` → `{ suggestions: { <ref>: { flow, why } } }` (matching only for MRs from the latest `GET /api/attention` response), `POST /api/intake` with `"attention": true` for `type: "mr"`;
- **flow header**: the description takes two lines, "more" opens the rest (it is shown in full on the YAML tab);
- the **Builder** tab: the flow graph from left to right. Nodes are "Task" and the phases (number, name, phase id, overridden model and effort, number of tools, what the phase receives; "receives nothing" is highlighted as an error). Edges are labeled with what the phase passes on (`handoff`, after a group — "group outputs (joined)"). A parallel group is a `∥ name` frame with the members in a column: edges go into each one and come out of each one. The diamond is the block's condition; the dashed arc from it to the first step is "not met ↺ up to N" (for `none` — "↺ exactly N iterations"). In a multi-block flow the blocks go in bands from top to bottom, each in a frame with a header, "↺ up to N iterations" or "single pass" and knowledge tag chips (`knowledge`); the frame is not narrower than its header, and the header is not cut off; the edge to the next block is labeled "met →", with `on_fail: continue` — "met or limit →". A single block gets a frame only if it has a `title` or knowledge tags. For a flow with `artifacts`, there is an artifacts column to the right of the blocks: solid edges are writes (`writes`), dashed ones are reads (`reads` and `{{artifacts.KEY}}`); hovering over an artifact highlights its edges. An edge goes from the right side of a phase along a channel under its block to the bus on the right and does not cross other blocks. Clicking a phase opens it in full in the "Large editor" on the right: name, "Variables" chips, the prompt in large type, "What to pass to the next phase", the artifacts row, tools, id, model, effort, turn limit, permissions, cost limit, parallel group, additional directories, system prompt, output schema and the ↑ ↓ ⧉ ✕ buttons. Meanwhile the left column does not scroll, the selected node stays selected, and the phase card on the left is highlighted. On the right and in the card on the left are the same fields: an edit on one side is immediately visible on the other and on the graph. The same place is reached via "+" on the graph, "Add phase", "⧉", the "What changed" rows of "Edit with AI", a save error in a phase field and a click in any field of the card on the left. On a narrow screen (no wider than 1100 px), where there is no editor on the right, clicking a phase expands its card and puts focus in the prompt. Clicking a block header or the diamond leads to the loop settings. "+" on a node (on hover) adds a phase after the step (for a group member — after the whole group), "+" on a group frame adds one more member. The graph is redrawn on every edit, and the "Edit with AI" highlighting is visible on the nodes too. The "− 100% + Fit" panel (a row above the canvas, the graph does not overlap it) and ⌘/Ctrl+wheel zoom the graph (the zoom is remembered separately for the Builder, the "Run" tab and the run page; until you change it by hand, a wide graph is fitted to the width, but not smaller than 70%), and dragging the background scrolls. Below are the phase cards: name, prompt, the "What to pass to the next phase" field, tool chips and the collapsed "Advanced" section (it holds "Additional directories" and the phase id: its output is referenced as `{{phases.id}}`). The "Variables" chips (a click inserts `{{variable}}` into the prompt, used ones are highlighted) sit in the phase editor on the right, above the prompt, on a wide screen. On the phase card on the left they are present only on a narrow screen. Flow and block fields ("Flow description", "Default task", the judge rubric, the condition command) open on the right on focus the old way: as a mirror of a single field. Phases can be added, duplicated, reordered and deleted; the loop and condition settings are right there. The **Add block** button adds the next stage: each block has its own mode (loop until a condition or a single pass), condition and a choice of what to do if the condition is never met. The graph draws blocks one under another, and ↑/↓ on the outermost phase of a block moves it into the neighboring block (not into a call block). **Add flow call** adds a block that calls another flow, and "After the block" in the settings of each block of a multi-block flow sets the branching (see "Calling another flow and branching"). The block id (the key in YAML) of a multi-block flow is edited in the block settings; `next` targets and `{{phases.<call block>}}` references follow a rename. The "Save" button at the bottom appears when there are unsaved edits; saving validates and writes the YAML; a single-block flow is saved in the short form (`loop` + `phases`);
- **claude.ai connectors** in the phase card, under the tools: which Jira, Confluence and Slack tools the phase is given and what that means. "+ Jira, Confluence, Slack…" shows the list of tools of the account's connected connectors; the first items of each connector are "whole connector" (one entry in `tools`) and "all read-only" (all of its tools that change nothing) (the server asks Claude Code for it, a few seconds; unconnected ones are listed separately), plus a field for entering a name by hand. A writing tool is highlighted: the phase will run it without confirmation. A name that none of the connected connectors has is highlighted as an error; a name of the form `mcp__<uuid>__…` from a desktop session is not accepted. If the phase prompt calls on Jira, Confluence or Slack (a tool name, "Atlassian MCP", a link, "open … in Jira") but the phase has no connectors, the row warns about it. The run form warns if the input contains a Jira or Slack link but no phase of the flow will get connectors.
- **Edit with AI** (above the graph in the Builder): you describe in words what to change, and the agent edits the flow with the Edit tool, like code: whatever is not related to the edit stays byte for byte, and dependent places (`{{phases.X}}` references, neighboring prompts, the judge rubric) the AI adjusts and lists in its reply. It works from what is currently in the Builder, including unsaved edits; the AI will fix a broken flow along the way. The result lands in the Builder unsaved: the AI's reply with the list of edits, the list of changed fields (a click leads to the phase), changed phases and blocks are highlighted, "Undo edit" returns things as they were, "Abort" stops the AI while it is editing. It gets into the file only on "Save". The model is chosen next to the "Change" button (the same choice as in "New flow", remembered in the browser under `agentgraph.flowAiModel`; "default" shows the actual model once a session has named it). While the AI works, a panel shows the step ("editing", "fixing validation errors 1/2" when the result did not pass validation), the session's model, a timer, the last lines of its progress (text, tool calls), a notice when a request to the API is being retried, and a "No news for N" warning after two minutes without a single event; the result shows the model, duration and cost. API: `POST /api/flows/:name/edit` with `{"instruction", "spec"? | "yaml"?, "cwd"?, "model"?}` returns `{ name, spec, summary, changed, costUsd }`; with `Accept: application/x-ndjson` the response is a stream of lines `{"type":"progress", "model"?, "retry"?: {attempt, maxRetries, delayMs}, "stage"?: {kind: edit | repair, attempt?, of?}}`, `{"type":"log","line"}`, then `{"type":"done","body"}` (the same body plus `model` and `durationMs`) or `{"type":"error","error"}`. Closing the connection stops the session;
- the **Run** tab: a collapsible "Scheme" (collapsed by default so that "Run" is visible without scrolling; when expanded, no taller than 60% of the window, then it scrolls) — the same graph, read-only, from the saved version of the flow (without the Builder's unsaved edits); clicking a node opens the Builder at that phase (the phase opens right away in the editor on the right) or block. Below it is the phase plan collapsed into a summary ("2 blocks, 5 phases" or "3 phases, up to 4 iterations, …"; it expands on click, so "Run" stays visible without scrolling), the task (goes into `{{input}}`), the project directory, the iteration limit (for a multi-block flow, the limit of each loop; empty = as in the blocks), the cost limit, the model. In addition:
  - **attachments** to the task: "Add files…", dragging files onto the form or pasting a screenshot into the task field; the "name · size ×" chip removes a file. Images (`png jpg jpeg gif webp`), PDF and text (`txt md csv json log yaml yml xml`) are allowed: up to 10 files, up to 10 MB each and up to 25 MB in total. No `.docx`: Read doesn't parse it. `CLAUDE.md` and `CLAUDE.local.md` (in any case) are saved as `attached-…`: the attachments folder goes to the agents in `additionalDirectories`, and under the original name Claude Code would load the file as agent instructions. Files go into `runs/<id>/attachments/`, their absolute paths are appended to the end of every phase's prompt ("Task attachments (open with the Read tool)"), and the `attachments/` folder is added to all phases in `additionalDirectories`. The agent opens them itself via Read, so phases without Read will not see the attachments; the form warns about this with a list of such phases. The judge (`until.type: judge`) also gets the list of attachments and their folder: they are part of the task. On the run page attachments are shown as links in the header; images and PDFs open in the browser. When a run is continued, the attachments are copied into the new one;
  - **additional directories** for the whole run, one path per line (the "Choose…" button appends a line): like `add_dirs`, but for all phases at once (see "Additional directories for a phase"). If a directory doesn't exist, the run is rejected with a 400 error before the run folder is even created. The list is written to `run.json` (`addDirs`) and carried over into a continuation. If one of the directories no longer exists by the time of the continuation, "Continue" responds with 400, and you can't remove it from the continuation: put the directory back or start a new run;
  - **recent directories**: chips under the project directory and under the additional directories. A click puts the path into the project directory or appends it as a line to the additional ones. The paths are collected from `cwd` and `addDirs` of past runs (newest on top, without worktrees), projects from "Connections" and the default directory; no more than 8 are shown, those missing on disk are not shown. "×" on a chip (visible on hover) removes the path from the recent ones in both rows and in the suggestions of the "Context" page; the path comes back after a new run with it. The project in "Connections" stays, though; remove it there. You can't pin a path by hand.

  API: `POST /api/runs` accepts, besides `flow`, `input`, `cwd` and limits, the fields `attachments: [{ "name", "data" }]` (`data` is the content in base64; request body up to 40 MB) and `addDirs: string[]` (`~` is expanded, relative paths are resolved from `cwd`). An error in attachments or directories is a 400. `GET /api/dirs/recent[?limit=N]` returns the recent directories `[{ path, label, lastUsed?, exists }]`. `DELETE /api/dirs/recent?path=<absolute path>` removes a path from the recent ones: 200 and the new list, 400 for an empty or relative path. Hidden paths and the time they were hidden are stored in `~/.agentgraph/settings.json`, field `hiddenDirs`; a path is shown again if there was a run with it after it was hidden. `GET /api/runs/:id/file?path=attachments/<name>` returns an attachment with a type based on its extension;

  One-off run API: instead of `flow`, `POST /api/runs` accepts `spec` (an object from the Builder) or `yaml` (a string): exactly one of the three; the draft is checked before the run folder is created, and such a run is marked `adhoc`. `POST /api/flows/generate` with `save: false` returns `{ name, spec, yaml, summary, costUsd }` and writes nothing. `POST /api/flows/check` with `{ spec }` or `{ yaml }` checks a draft: `{ name, spec, yaml, summary }` or 400. `POST /api/runs/:id/save-flow` with `{ name?, folder? }` puts the run's snapshot into `flows/` (the `name` field in the YAML is changed to the chosen one), response `{ name, folder }`; a taken `name` is a 409. Feature in `GET /api/config`: `adhoc-runs`.
- the **YAML** tab: the same spec as text, for fine-grained editing;
- the **Delete** button in the flow header: removes the file from `flows/` after confirmation; past runs remain;
- **one-off run** ("New flow" → "One-off run (don't save the flow)"): the flow is generated from the description and opens in the Builder as a draft (address `/draft`, with a "one-off" mark at the title). Editing by hand, "Edit with AI" and the YAML tab work as usual, except that "Save" turns into "Apply": the server checks the draft and writes nothing. A draft has no folder and no "Delete". "Run" starts a run with what is currently in the Builder; no file appears in `flows/`, the only copy of the flow is the snapshot `runs/<id>/flow.yaml`, and `run.json` has `adhoc: true`. The draft lives only in the tab: leaving it and closing the tab ask for confirmation. A one-off run has a "one-off" mark in the list and in the header, and instead of "To flow" there is **"Save as flow"**: a name (empty — a name free from the run's name, `<name>-2` if taken) and a folder; a taken name is a refusal, an existing flow is not overwritten. The run itself stays one-off after that. "Continue from where it stopped" for a one-off run (and for a continuation of a continuation) follows the snapshot, even if `flows/` has a flow with the same name.
- the **New flow** button: generate a flow from a task description or assemble it by hand from a template, right into the folder you need. Generation shows the same progress panel as "Edit with AI" (with "No news" after four minutes: the generator has no tools and thinks silently, sending the whole flow at the end) and the model choice. "Abort" stops the session; "Hide" closes the dialog while the generation keeps going in the tab, and when it is done a notification "Flow X is ready — open it" appears instead of switching screens (unsaved edits stay where they are); the result also waits in the dialog with an "Open" button, so a one-off draft is not lost when the notification goes away. Closing the tab stops the generation: there are no background generations on the server. `POST /api/flows/generate` streams the same way with `Accept: application/x-ndjson` (`stage` — `{kind: generate}`); without the header the body is as before;
- **flow folders**: flows can be arranged into folders (subdirectories `flows/<folder>/`, one level) — the "Folder" field under the flow name (choose an existing one or type a new one; empty means the root) or dragging a flow onto a folder in the list on the left. An emptied folder is deleted. A flow name stays unique across all folders, so `run <name>`, links and runs don't depend on the folder;
- **runs by project**: on the left, runs are grouped by project directory (the label is the folder name, the full path is in the tooltip; projects are ordered by the recency of their latest run, a collapsed one shows the number of active runs ●). The "by project" toggle returns the flat list;
- **run status filter**: above the run list are chips of the statuses currently present in the list, with the number of runs ("waiting for reply", "running", "done", "iteration limit", "error", "interrupted", "aborted"…). A click adds a status to the filter or removes it; if several are selected, all selected ones are shown; "all" resets it. The filter works up to the "N more" limit, the open run stays in the list, and the selection is remembered in the browser. Search works together with it (see "search" below);
- **run name**: a new run (from the UI, CLI or the skill) has a short name, 3–7 words in the task's language. It is made up by a separate haiku session without tools based on the task, the flow name and the run's source. The session runs in parallel with the phases and does not delay `POST /api/runs`. The name appears a few seconds after the start, without a page reload. Until then, and also for old runs and when naming fails (error, 30 s timeout, empty task), the flow name remains the title, and this does not break the run. The name is cleaned the same way as an auto-tag title: one line without control characters and angle brackets, up to 60 characters. It is made up from untrusted text, so the UI shows it only as text. Where it is visible: the title in the run list (the flow comes first in small type in the subline), the run page header (under it a "flow <name>" line linking to the flow, without a link for a one-off run), the active run card on Home, the tab title, system notifications ("name (flow)"), the result in the CLI and the skill's summary. "Continue from where it stopped" takes the name of the original run; the model is not called again. If the original run has no name, the continuation has none either. You can't rename a run by hand. API: `title` in `GET /api/runs`, `GET /api/runs/:id` and `GET /api/home`; the `title` event (`title` or `error`, `totalCostUsd`) in the run stream and in the shared stream `GET /api/events`; the `run-title` feature in `GET /api/config`;
- **search** in the sidebar: a "Find flow…" field above the flow list and "Find run…" above the run list. Every word of the query must be found in at least one field; case doesn't matter. Flows are searched by name, folder and description. Folders with matches expand for the duration of the search, folders without matches are hidden, and the remembered folder collapse state does not change. Runs are searched by name, flow, task, task and knowledge tags, project folder name, id and source key (ticket, MR). Search works together with the status filter (both conditions must hold) and up to the "N more" limit, so it finds old runs too. While the search is not empty, the numbers on the status chips count only the found runs; the set of chips does not change, a status without matches shows 0. The open run stays in the list. In "by project" mode groups with matches are expanded and empty ones hidden. No matches — "Nothing found". The finished data is `phases[].tokens` in `GET /api/runs/:id`.
- **run artifacts** (on the run page, only for flows with `artifacts`; for others there is no panel, and the UI makes no artifact requests at all): the "Artifacts" panel between the pause and question cards and the phase blocks. The collapsed row shows the number of artifacts, which one was changed last and by whom, "✎ phase X is writing" (for a parallel group, all writing members), warnings and "unsaved". During a pause at the agent's request and during an agent question the panel is highlighted but doesn't expand by itself. Clicking a name opens the artifact window: a markdown preview (for `.md`, with "as text") or text, any saved version, "Edit". In edit mode there are "Save", "Save and resume" (only while paused) and "Discard". Closing the window keeps the draft ("unsaved" in the row), and any "Resume" or "Continue from where it stopped" button, including on Home, asks when there is a draft: "Save and resume", "Resume without edit" or "Cancel"; switching to another run and reloading the page ask for confirmation. While a step that writes the artifact is running, editing is blocked with a reason ("phase X is writing"; "phase X is waiting for your reply" if the writing phase asked a question): the editor text stays, and after the step ends "Save" is available again. If the file changed after it was opened, the save is rejected, showing who changed it and when: "Reload", "Overwrite", "Copy my text". If the run was resumed from somewhere else (another tab, the chat or the skill) and the draft remains, the panel and the window say the text is not saved and the running step will not see it. For a run from the CLI there is only read, "Refresh" and the data's time; for a finished one (`done`) and one that can't be continued, read-only with a reason; for a stopped one that can be continued, the edit will go into the continuation, and "Continue from where it stopped" is right next to it. A file larger than 1 MB is read-only in the UI. Warnings (a write without permission, stray files, a vanished artifact) are shown as an icon in the iteration header, on the artifact row and in the "Result"; on the phase card, "changed: …" and "write denials: N". API: `GET /api/runs/:id/artifacts` (`items` — path, author, versions, `lockedBy`, `editable` and reason; `from`, `warnings`, `live`, `continuable`), `GET /api/runs/:id/artifacts/:key[?version=N]` (text, `hash` — the base for a write, versions, `editable`), `PUT /api/runs/:id/artifacts/:key` with `{"text", "base", "resume"?}` → `{ hash, author, readers, resumed }` (`readers` — running phases that already got the previous version). Errors with a `code` field: 400 `bad_request`, 403 `readonly` (+ `reason`), 404 `unknown_key` or `missing`, 409 `conflict` (+ `hash`, `author`, `at`) or `not_paused` (`resume: true` while not paused; nothing is written), 413 `too_big`, 423 `locked` (+ `reason`: `writing` | `asking`, `phases`). The key is only a name from the flow: a path instead of a key (`..%2Frun.json`) gives 404. The `artifacts` event in the run stream (`/api/runs/:id/events`) carries a snapshot of the list and the step's result; it does not go into Home's shared stream. The `artifacts` feature is in `features` of `GET /api/config`;
- **run chat** (a dock on the right edge of the run page, visible on every tab — Overview, Graph, Log, Artifacts; on a narrow screen it is a sheet at the bottom): a conversation with an agent about this run — ask what is going on, why it failed, what the agent has already changed in the code, or ask it to do something with the run. The dock is open by default for a running run; the "Collapse" button in its header or Esc anywhere in the dock collapses it into a thin "Chat" strip at the edge (a click on the strip opens it again), and the choice is kept until the page is reloaded (an opened dock is remembered in the browser and opens for finished runs too). Its width (height on a narrow screen) is set by dragging the edge or with the arrow keys on it and is remembered in the browser. The agent is a Claude Code session in the run's project directory: it reads the run folder and the repository (Read, Grep, Glob, Bash), edits files in the project directory when directly asked to (Edit, Write; it cannot write to the run folder), and controls the run through the same server functions as the buttons. It gets fresh state with the `run_status` and `run_log` tools (the tail of the live log), reads artifacts (`artifacts`) and the flow (`flow_read`: the run's `flow.yaml` snapshot and the current file in `flows/`), and the server puts a status line at the start of each message.
  - **What it does by itself and what only by a button.** Safe things — pause, resume, the iteration limit, an answer to an agent question in the user's words — the agent does right away when asked. Dangerous and shared things — stopping the run, writing an artifact, answering a pause (into the decisions artifact), saving the flow to `flows/`, continuing from where it stopped (with a model and a cost limit), running the same flow again with the same task — it only offers as buttons under the reply. A click asks for confirmation with what exactly will happen (for saving the flow: that `flows/<name>.yaml` is a shared file for all following runs), then the server checks the state again and runs the action once: the button turns into "✓ done", "✕ failed" with the reason, or "expired" — when the state it was offered for is gone (the artifact or the flow file changed after it was read, the run is no longer on that pause or is no longer running). While the agent is replying, the buttons wait. An artifact written from the chat is signed "user (chat)" (`via: "chat"` in the version author and in `pauses[].answer`). Fix and continue from the chat: an instruction to the next step or to the rest of the run (`run_note`) goes right away, like the field on the phase card; on a pause the agent offers buttons to apply an edited flow to this run only ("apply flow", with an optional "also save to flows/"), to take `flows/<name>.yaml` into this run ("reload flow") or to restart the iteration with an instruction ("restart iteration"; the run stays paused until resumed). An incompatible edit is rejected with the reasons, and the run goes on with its old flow. "Apply flow" is offered only after the agent has read the flow in the same reply; if the snapshot was edited after that (on the same pause, from the pause card or another button), the button expires instead of undoing that edit; so does a "reload flow" button offered before such an edit. The result lists what changed ("no changes" when nothing did) and the reason when writing to `flows/` failed; a one-off run has no "also save to flows/" checkbox. Restarting an iteration is not offered when the block has not started an iteration or its limit is already 50. A rerun from the chat takes the current `flows/<name>.yaml` (a one-off run — its snapshot): a live edit stays in its own run and its continuations, and the rerun confirmation says so when there is such an edit. A continuation takes `flows/` too, or the run's snapshot when its last live edit wasn't saved there; `flow_read` says which, and in that case the "save flow" button warns that continuing this run stays on its snapshot.
  - **Reading the reply.** The reply is markdown (lists, tables, code, links, clickable paths). Above it is a collapsed "N actions" line with a tick per step; expanded, it lists what the agent did in plain words ("Reads iter-02/01-code.output.md", "Paused the run", a command), files of the run open in the file window, other paths are revealed in Finder; failed steps are red. While the agent is replying, the dock shows its latest steps and text live. Under the reply are widgets the agent sends as data, not HTML: a table, links (a run file, an artifact — opens the artifact window, a phase — leads to its card in Overview, a project path), action buttons, and reply chips (a click sends the text as your message; only under the latest reply). Old `chat.json` files without steps and widgets are shown as before.

The reply runs on the server: you can go to another run and come back — the reply's progress and result will be pulled in; "Abort" stops the reply. The model is chosen in the chat header. The history is stored in `runs/<id>/chat.json`, with each reply's `steps` and `widgets` (button results included). API: `GET|POST|DELETE /api/runs/:id/chat` (POST `{"message", "model"?}` responds with an NDJSON stream: `saved`, `step` (`index`, `step` — a new step or the same one with an error), `text`, `widget`, `effect` (`kind`: `artifacts` | `flow` | `run`, `runId`? — the page reloads artifacts, the flow or the run list), `done` or `error`; `GET` of a reply in progress has `busy` and `live` with its steps, text and widgets), `POST /api/runs/:id/chat/stop`, `POST /api/runs/:id/chat/action` with `{"msgIndex", "actionId"}` → `{ action, chat, effects }` (409 `busy` while the agent is replying, 409 `used` for a second click, 404 `not_found`, 423 `locked` when a phase is writing the artifact — the button stays).

### Agent questions

**Pause** is soft: the running session (a phase or a condition check) finishes its work, and the next step won't start until you press "Resume". The run gets the "paused" status and keeps its context in the UI server's memory; if the server is restarted, the paused run is lost, like any live run. Such a run (`run.json` still says `running`, but the runner process from the `pid` field is gone) is shown with the "interrupted" status: it can't be resumed, but it can be continued from the first unfinished block (see "Continuing a finished run"). **Stop run** interrupts the current session immediately, including a paused run and a condition check command: its processes are killed as a whole group. API: `POST /api/runs/:id/pause`, `/resume`, `/abort`. The run also stops at a pause requested during the last iteration of a block: there you can repeat the iteration (below) before the block ends.

**Fix and continue.** If you see the run going wrong, you fix it in the same run, without "stop → continue":
- **Instruction**: a field on the card of the running phase (or condition check) and on the pause card. The text is appended as a "User instruction" tail to the prompt of the next step: of the next phase, of every member of a parallel group, or of the judge, whichever comes first. It works in any flow, without `{{feedback}}`, while the run is running and on pause. With "for the rest of the run" checked, every following step gets it. The card of the step shows the instructions it received; the ones still pending are listed under the field. `run.json` keeps them in `notes` (`id`, `text`, `scope`: `next` | `run`, `at`, `via`: `ui` | `skill` | `chat`, `applied`: where it went — `block`, `iteration`, `phase`, the judge is `#cond`), the stream sends a `note` event when an instruction is added and when it is applied (with only the new `applied` entries). An instruction given during the very last step is never applied and stays pending.
- **Edit the run's flow** (pause card): the `runs/<id>/flow.yaml` snapshot opens in the YAML editor; "Apply to the run" makes the next steps follow the edit, in the same run and under the same id. The edit stays in this run; "Also save to flows/<name>.yaml" (off by default) writes it to the saved flow too, with the flow's own `input` instead of the run's task. **Take the flow from flows/** — the same with the current version of `flows/<name>.yaml` (you fixed the flow in Claude Code); not available for a one-off run. Anything that is still ahead can change: prompts, models, phases of the running block (the next step is the first one whose phases haven't run in this iteration yet), its condition and limit, future blocks, `defaults`. Not allowed: the name, the task (give an instruction instead), artifact declarations, switching between one block and several, finished blocks, moving the running block; the limit of the running block can't drop below the started iteration. Additional directories, plugins and knowledge tags of the running and future blocks are checked again, as at start. An edit that doesn't fit is rejected with a list of reasons, and the run goes on as before. With the checkbox, `flows/<name>.yaml` is written only if its content (the task aside) hasn't changed since the run took it (at start, after "Take the flow from flows/" or after the previous save) and the run started from that very file; reformatting or new comments don't count. The edit is laid over the file, so its comments and most of the formatting stay (a file with YAML anchors is written as the edit text). If the file's content was changed elsewhere (the builder, another run) or the run started from a different flow (a continuation from an edited snapshot), it isn't overwritten: the edit applies to the run only, and `saveError` says why — carry it over to `flows/` by hand. The file is written before the run switches to the edit, so the `flow` event already carries `savedToFlows`; an edit that doesn't fit doesn't touch `flows/`. If the write fails, the run still follows the edit and the reason is in `saveError`. If the snapshot was changed by someone else after the dialog read it (another tab, the skill), the edit is rejected as stale instead of silently undoing that change. The previous snapshot is kept as `flow.N.yaml` (the original is `flow.0.yaml`), `run.json` gets `flowEdits` (`version`, `at`, `source`: `edit` | `reload`, `via`, `changed` — what changed, `savedToFlows`, `saveError`), the stream sends a `flow` event (with the block reports and the limit after the edit, so a reconnect replays it in order), and the header shows "flow edited mid-run: N". An edit without changes writes nothing. A phase inserted in the middle of an iteration gets a number after the phases that already ran, so the result and the history follow the order of execution.
- **Repeat iteration** (pause card): the remaining steps of the current iteration are dropped and iteration N+1 of the running block starts; the block limit goes up by one, for a block without a loop too. The instruction from the field goes into `{{feedback}}` of the new iteration (after the judge's feedback, if any) and as a tail to its first step. A cut iteration gets a condition entry "restarted by the user" instead of a check. The run resumes right away.

Edits and repeats happen only while the runner stands at a checkpoint (between steps) on pause, never in the middle of a parallel group. API: `POST /api/runs/:id/note` `{ text, scope?: "next" | "run", via? }` → `{ note }` (the run is running or paused); `PUT /api/runs/:id/flow` `{ yaml, saveToFlows?, base?, via? }` → `{ edit }` (`base` — the `flowEdits.length` of the snapshot that was edited); `POST /api/runs/:id/flow/reload` `{ via? }` → `{ edit }`; `POST /api/runs/:id/restart-iteration` `{ note?, via? }` → `{ block, iteration }` (the run stays paused: then `/resume`). Errors: 409 `not_paused`, 400 `incompatible` with `problems: string[]`, 409 `not_started` (the block hasn't started an iteration), 400 `limit` (the limit is already 50), 409 `restarted` (already repeated on this pause), 409 `stale` (the snapshot changed after it was read), 409 `adhoc` (a one-off run has no `flows/` file to reload from or save to), 400 `bad_request`. The `/agentgraph` skill: `note <id> --text T [--all]`, `flow-reload <id>`.

If a phase has the `AskUserQuestion` tool enabled, the agent can stop and ask the user. In the UI the run gets the "waiting for reply" status, and a card with options and a "Your own reply" field appears on the run page. If the agent wrote something before the question (a feedback table, a list of options), that text appears on the card above the question, and collapsed in the history: what counts is what the main agent wrote last (consecutive text blocks, without subagents) (the question's `preface` field in `run.json`; the `/agentgraph` skill and the run chat get it too). The question text and option descriptions are shown as markdown (lists, code, links), and the question's header as a badge above it; the reply itself goes to the agent as is, keyed by the original question text; after the reply the session continues, and the question with its reply stays in the run history: the question as a block, the reply under it. In the CLI the question is printed to the terminal, and the reply is entered as an option number or text. Example: `flows/example/example-ask.yaml`.

A flow where questions inside a session are forbidden (the agent works on its own and writes decisions to files) can still hit something only the user can resolve: a test environment, access, an external answer. For this the loop has `loop.pause_marker`. The phase writes its questions and ends its output with the marker line. The marker counts only if it is the last non-empty line of the output: a quote in the middle of the text does not pause. If the loop condition is not met, the run pauses after the iteration: iterations are not wasted, and the reason is visible on the run page (the agent's text above the marker is markdown), in `pauseReason` of `GET /api/runs/:id`, in a system notification and in the "Events" feed on Home (all pauses of a run with the request and resume times are in `pauses` in `run.json`). After you reply and press "Resume", the run goes on with the next iteration of the same block. In the CLI there is no pause, and the block ends with an error containing the questions. Example: `flows/example/example-pause.yaml`.

**Replying to a pause into an artifact.** If the flow has an artifact with `decisions: true` (see "Run artifacts"), there is a "Reply" field under the card of a pause at the agent's request, and the "Resume" button in the header is called "Resume with reply" when the field has text. The reply is appended to the end of that artifact as an entry: time, block, iteration, phase, the phase's questions as a quote, and the reply. The same reply goes into `run.json` in `pauses[].answer` (`text`, `via`: `ui` | `skill`, `at`): this is the authoritative list of replies, since phases can also write to the decisions artifact. The run resumes only after a successful write; on error it stays paused, the reason is visible, and the text stays in the field. An empty field means a regular "Resume" without a write. If there is an edit in the artifact window, "Save and resume" first saves it, then resumes with the reply. The reply field is only on the run page: on Home such a run has a "Reply on the run page" button. If there is no `decisions` artifact but there are artifacts, the pause card offers "Open artifacts" instead of "write it where the agent asks"; for flows without artifacts the card is unchanged. The `/agentgraph` skill replies the same way: `resume <id> --answer-file F`. API: `POST /api/runs/:id/resume` with `{"answer"}`. An empty `answer` or a body without it means the previous resume. Errors: 409 `not_paused` (the run is not paused), 400 `no_decisions` (nowhere to write the reply), 413 (reply larger than 64 KB).

**Continuing a finished run.** A run that ended other than `done` (`max_iterations`, error, stop, "interrupted") can be continued with the current version of the flow (if the run's flow was last edited mid-run only in the run — the last `flowEdits` entry is a snapshot edit without "also save to flows/" — with the run's snapshot, and so are the continuations of such a run; the "Continue" button's tooltip says so): with the "Continue from where it stopped" button on the run page, `POST /api/runs/:id/continue` or `agentgraph.mjs continue <id>` from the skill. The new run skips the unbroken leading run of blocks that finished `done` in the old one, and substitutes their last outputs into `{{phases.*}}`, `{{prev}}` and `{{history}}`. The block where the old run stopped starts from the first iteration and without its old outputs: they may contain outdated instructions. A continuation of a continuation takes outputs from the run where the block was executed. The iteration limit for a continuation is taken from the flow: `--max-iterations` would override all loops, so it is not accepted. If the output of a skipped phase is missing, the continuation is rejected rather than running with an empty `{{phases.*}}`. There is nothing to continue if the first block is not finished; the exception is a block that hit the iteration limit (`max_iterations`): then the continuation restarts from it with a new limit, without its old outputs, but with the code in the project directory and the artifacts. A single-block flow is continued the same way. Whether a run can be continued, the server reports in `GET /api/runs/:id` with the `continuable` and `continueReason` fields; the "Continue from where it stopped" button takes them from there.

For a flow with artifacts, a continuation gets a copy of the current artifact files of the previous run, including edits made after it stopped, but without the version history. The last author is carried over with the mark "from run X", so the first phase knows the last edit was made by the user. The new run's page and its `run.json` (`artifacts.from`) show where the artifacts were taken from. If the flow has changed: a new artifact is created from `initial`, a removed one is not copied, when `file` changes for the same key the content is carried over, and a renamed key counts as removed plus new. The stopped block starts from the first iteration without its old outputs, but with the artifacts: an artifact is exactly the state the user may have fixed.

The server listens only on `127.0.0.1`, and there is no authentication. To keep a foreign page in the browser from controlling it (CSRF, DNS rebinding), it accepts only a `Host` of 127.0.0.1, localhost or [::1] with any port (otherwise 421), for requests other than GET and HEAD only an `Origin` of the same address or no `Origin` (otherwise 403), and as a body only `Content-Type: application/json` (otherwise 415). The UI, the skill helper and curl fit this. `--cwd` of the `ui` command sets the default project directory for the run form, `--port` changes the port, `--no-notify` turns off system notifications.

### Notifications

When an agent asks a question or a run ends (except when stopped by hand), the server shows a system notification — if no open UI tab will show its own: the UI is closed or "Enable notifications" hasn't been pressed in it. A tab with browser notifications enabled tells the server so when it connects to `/api/events` (`?notify=1`), and then the server stays silent to avoid duplicates. A server started by the `/agentgraph` skill (`AG ensure`) sends notifications too.

- macOS: if `terminal-notifier` is installed (`brew install terminal-notifier`), clicking a notification opens Home or the run page; without it the notification goes through `osascript`, and a click opens Script Editor. If you don't see notifications, allow them in "System Settings → Notifications" for Script Editor (or terminal-notifier).
- Linux: `notify-send`.
- `--no-notify` of the `ui` command turns them off completely; `AGENTGRAPH_NOTIFY=log` writes a line to the server log instead of a notification (for checks), `AGENTGRAPH_NOTIFY=off` stays silent.

## Quick start

```bash
# generate a flow and run it right away in the given repository
npm run agentgraph -- "Fix the failing tests in the project without touching the tests themselves" --cwd ~/code/my-repo

# one-off run: generate and run, don't save the flow to flows/
npm run agentgraph -- "Rename the utils module to shared and fix the imports" --cwd ~/code/my-repo --once

# only generate, review it and edit it by hand if you like
npm run agentgraph -- gen "Add a /health endpoint and cover it with tests" --cwd ~/code/my-repo
npm run agentgraph -- show flows/add-health-endpoint.yaml

# edit an existing flow from a description (AI edits the file in place, comments are kept)
npm run agentgraph -- edit add-health-endpoint "after the implementation, add a review phase with a judge"

# run an existing flow
npm run agentgraph -- run flows/add-health-endpoint.yaml --cwd ~/code/my-repo -v

# keep working on a feature: the tag summaries, notes and paths go into the task, after done the summaries are updated
npm run agentgraph -- run add-feature --cwd ~/code/my-repo --tag loyalty-card --tag frontend-rules --input "Add a loyalty card to the profile screen"
npm run agentgraph -- tags
```

CLI options: `--cwd` (project directory), `--max-iterations` (for every block with a loop), `--max-budget` (cost limit, USD, total per run), `--model`, `--input` (replace the task of an existing flow), `--once` (one-off run: only with the `agentgraph "<task>"` form, without `-o`; the flow isn't written to `flows/`, its copy is `runs/<id>/flow.yaml`), `--tag <slug>` (task tag, can be repeated), `--no-save-tag` and `--auto-tag` (a new task tag from the task text; see "Tags"), `-v` (stream session progress to the console). `agentgraph tags` lists the tags.

## Examples in `flows/example/`

- `example-blocks.yaml` — three blocks: a slogan until the judge approves → a translation and a short version in a single pass → a check with a marker. No tools, costs cents; handy as a smoke test: `npm run agentgraph -- run example-blocks`.
- `example-ask.yaml` — a phase with `AskUserQuestion`: the agent asks the user a question, the answer comes from the UI or the terminal.
- `example-pause.yaml` — `loop.pause_marker`: the phase asks for the user's decision, the run pauses (UI only).
- `example-parallel.yaml` — a parallel group (`group`): three phases look at an idea at the same time, the fourth combines their outputs from `{{prev}}`. No tools, costs cents: `npm run agentgraph -- run example-parallel -v`.
- `example-compose.yaml` — connecting flows: a phase decides what to do and ends with a marker, `next` leads to a call of `example-parallel` or of `example-blocks`, the latter repeated until the judge approves (see "Calling another flow and branching").

## flow.yaml format

Phases go in the `phases` field, the block's stop condition goes in `loop.until` (types: a `command`, a `judge`, a `marker`, `none` — no condition, exactly `max_iterations` iterations). The example below shows all fields at once and is therefore multi-phase; a typical flow is a single phase with all the tools it needs plus an acceptance condition. Each phase is a fresh session that sees only the text passed to it, so an unnecessary boundary between phases means lost context. A separate phase is justified when the contexts really must not mix: a read-only review after a writing phase, a parallel group of independent tasks, a step with a huge context that needs to be compressed before the next one. The generator and "Edit with AI" follow this rule; the "Analyze flow" button on the run page checks it against the facts (see "Flow analysis").

```yaml
name: fix-tests                 # slug
description: ...
input: "task text"              # available as {{input}}
defaults:                       # optional, applies to all phases
  model: claude-opus-5-5
  effort: high
  max_turns: 40
  max_budget_usd: 5
loop:
  max_iterations: 4
  until:                        # one of:
    type: command               #   shell command, exit 0 = done; output -> {{feedback}}
    run: npm test
    # type: judge               #   judge with a rubric (Read/Grep/Glob + subagents)
    # prompt: "..."
    # type: marker              #   the last line of the phase output is exactly this literal
    # marker: "<DONE>"
    # phase: verify
    # type: none                #   exactly max_iterations iterations
  pause_marker: "<NEEDS_USER>"  # optional: the phase ended its output with this line -> the run pauses until the user decides
phases:
  - name: analyze
    title: Analysis
    tools: [Read, Grep, Glob]   # required field; [] = no tools; Agent (subagents) and Skill (skills) are always added; AskUserQuestion = can ask the user
    prompt: |
      Task: {{input}}
      Feedback from the previous iteration: {{feedback}}
      ...
    handoff: 'a "## Result" section: what you found, files and lines, the edit plan'   # how to end the answer; appended to the prompt
  - name: implement
    tools: [Read, Edit, Write, Grep, Glob, Bash]
    prompt: |
      Task: {{input}}
      Plan: {{prev}}
  - name: qa
    tools: [Read, Grep, Glob, Bash]
    add_dirs: [~/projects/qa-rules]   # where the phase may go besides the project directory (like --add-dir)
    plugins: [~/plugins/qa-tools]     # Claude Code plugins for this phase only (like --plugin-dir), see "Block and phase plugins"
# a block (full form, blocks[]) can have knowledge: [qa] — knowledge tags from the "Tags" page: all phases of the block get their notes, paths and attachments;
# and plugins: [...] — Claude Code plugins for all phases of the block
    group: checks               # adjacent phases with the same group run at the same time (see "Parallel phases")
    prompt: |
      Check the changes against the QA rules.
  - name: security
    tools: [Read, Grep, Glob]
    group: checks
    prompt: |
      Check the changes for vulnerabilities. Changes: {{prev}}
    # model, effort, max_turns, permission_mode, max_budget_usd, system, output_schema — optional
```

### Template variables

| Variable | What is substituted |
|---|---|
| `{{input}}` | the original task |
| `{{prev}}` | the output of the previous phase (for the first phase on iteration 2+ it's the output of the last phase of the previous iteration; for the first phase of the next block, the output of the last phase of the previous block). Members of a parallel group get the output from before the group; the phase after the group gets the members' outputs joined together |
| `{{phases.NAME}}` | the latest output of phase `NAME`; for a call block (`flow:`), `NAME` is the block name and the value is the call result |
| `{{feedback}}` | the condition's feedback after the previous iteration (output of the failed command, the judge's feedback); empty on the first iteration of each block |
| `{{iteration}}`, `{{max_iterations}}` | the iteration number and the limit of the current block |
| `{{outputs}}` | all outputs of the block's current iteration in the order the phases are declared, each under a `### name` heading (mainly for the judge prompt) |
| `{{history}}` | all previous outputs, each entry truncated to 6000 characters |
| `{{artifacts.KEY}}` | the contents of artifact `KEY` at the start of the step: up to 32 KB in full, larger — a map of its sections (see "Run artifacts"), an empty file — an empty string. Works in the prompt, `handoff` and the judge's rubric; the substitution gives the phase read access to the artifact |
| `{{artifacts.KEY.path}}` | the absolute path to the artifact file; also gives read access |

Variables are not substituted in `system`, in an artifact's `initial` or in condition commands.

### Several blocks in a row

The form above is a single block. When a task consists of parts, each of which has to be finished before moving on, write `blocks` instead of `loop` + `phases`:

```yaml
name: spec-and-implement
input: "..."
blocks:
  - name: spec                  # loop: until the judge accepts the spec
    title: Spec
    loop:
      max_iterations: 3
      until: { type: judge, prompt: "..." }
    phases: [...]
  - name: split                 # no loop = a single pass, the condition isn't checked
    phases: [...]
  - name: implement             # a loop again: until the tests are green
    loop:
      max_iterations: 5
      until: { type: command, run: npm test }
    on_fail: continue           # stop by default
    phases: [...]
```

- Blocks run strictly one after another: only phases inside a block can run in parallel (see "Parallel phases"). If a block's loop has used up `max_iterations` and the condition isn't met, the run stops with status `max_iterations` (`error` says which block). With `on_fail: continue` the runner moves on to the next block.
- The `until.marker` marker counts only if the phase ended its output with it: the last non-empty line is exactly the marker, as with `pause_marker`. A phrase like "I'm not outputting the <DONE> marker" doesn't end the loop.
- A phase whose session ended with an error (API, computer sleep, turn or cost limit) stops the run with status `failed`: the error text isn't passed to the next phase as if it were a result. To continue, use "Continue from where it stopped".
- `{{prev}}`, `{{phases.NAME}}` and `{{history}}` carry over from block to block: the first phase of a block gets the output of the last phase of the previous block in `{{prev}}`. `{{feedback}}`, `{{outputs}}`, `{{iteration}}` and `{{max_iterations}}` belong to each block and are reset at the start of the block.
- Run artifacts are shared by all blocks: the next block sees them as the last step of the previous block left them.
- Phase names are unique across the whole flow. `{{phases.NAME}}` can refer to a phase of this or an earlier block, but not a later one: that one hasn't run yet. `marker.phase` is a phase of the same block, the last one by default.
- `--max-iterations` overrides the limit of every block with a loop; a block without a loop always runs once.

### Calling another flow and branching

A block can call another flow instead of having phases, and any block can choose where to go next. Together they cover "flow 1 → flow 2 → flow 3", "flow 1 → flow 2 or flow 3 depending on the result" and "repeat flow 2 until X". Example: `flows/example/example-compose.yaml`.

```yaml
name: bug-or-feature
blocks:
  - name: triage
    flow: triage                  # call block: a flow from flows/ by name instead of phases
    next:                         # branching after the block: rules in order
      - if: { type: marker, marker: "<BUG>" }
        goto: fix
      - goto: build               # no if = otherwise
  - name: fix
    flow: fix-bug
    input: |                      # the called flow's task; the default is below
      {{input}}

      Triage: {{phases.triage}}
      Review feedback (empty on the first iteration): {{feedback}}
    loop:                         # repeat the call until the judge approves
      max_iterations: 3
      until: { type: judge, prompt: "..." }
    next: end                     # don't go on to build
  - name: build
    flow: implement-feature
```

**Call block** (`flow: <name>`):

- Each iteration of the block is a child run of that flow: its own folder in `runs/`, its own page and a link to the parent. The parent waits for it to end. The called flow runs exactly as it does on its own: its `defaults`, artifacts, agent questions and pause.
- `input` is the called flow's task (its `{{input}}`): a template with the same variables as a phase prompt. Without `input` the task is the run task, then `## Результат предыдущего шага` with `{{prev}}` and `## Замечания проверки` with `{{feedback}}`, each only if it isn't empty.
- The call result is the output of the child's last step, as in its "Result" card (for a parallel group, the members' outputs joined). It goes to `{{prev}}` of the next block and to `{{phases.<block name>}}`: the call block's name is also the name of its result, so it can't match a phase name. The called flow's phases aren't visible to the parent: a call is a context boundary.
- The block succeeds if the child run ended `done`; any other status stops the parent with that status, like a failed phase.
- `loop`, `until` and `on_fail` work as for a block of phases: one iteration is one child run. The judge sees the call result in `{{outputs}}`, `marker` checks the last line of the result (without `phase`), `command` runs in the project directory. Child N gets the artifacts of child N−1, like a continuation.
- The project directory, worktree, additional directories, attachments and knowledge tags of the run go to the child; task tags and their summary stay with the parent. A call block has no `knowledge`, `plugins` or `loop.pause_marker`: they belong to the called flow.
- Only text goes between parent and child: the task in, the result out. Artifacts aren't shared.

**Branching** (`next`):

- A string means "always go there" (`next: end`). A list holds rules checked in order after the block ended (`done`, or the iteration limit with `on_fail: continue`): the first rule that holds decides. A rule without `if` always holds and must be the last one. If no rule holds, the next block in order runs.
- `if` is a condition like `until` without `none`: `marker` (the last line of the output of `phase` or of the block's last phase; for a call block, of the call result), `command` (exit code 0), `judge` (`done=true` means "go"). A judge that returns no verdict (an API error) fails the run instead of counting as "no", and a run stopped during a check records no decision: in both cases "Continue" decides the branch again.
- `goto` is a block below or `end` (the run ends `done`). Jumps go only forward: repeating is a block's `loop`, and repeating several flows is a call, inside a `loop`, of a wrapper flow that calls them.
- Blocks that were jumped over don't run. With branching, `{{prev}}` of a block is the output of the block that actually ran before it, and `{{phases.X}}` of a skipped block is empty; the Builder's variable hints say so.
- A block can't be named `end` in a flow with `next`.

**Checks** (when saving in the Builder or the YAML tab, for a one-off draft, before a run): the called flow is in `flows/` (any folder) and is valid, calls don't form a cycle (A → B → A), the chain is at most 3 calls deep, a `next` target exists and is below the block, `{{phases.X}}` in a `next` judge rubric refers to this or an earlier block. A flow that other flows call can't be deleted: `DELETE /api/flows/:name` answers 409 with `callers`.

**Running:**

- A child run is a run like any other: its own page, chat, agent questions, pause and artifacts. Its header says "called from flow X" with a link to the parent; in the sidebar it sits under the parent, indented. On the parent's page the call card and the call node in the "Graph" inspector link to the child run of each iteration. In the CLI the child's progress is printed under the block's line, indented with `│ `. `eval` runs children silently.
- `run.json` of the parent: the call phase has `call: { runId, flow, status }`, a block with `next` has `next: { to, rule?, checks }` (what each rule's check said; command logs and judge prompts are in `NN-<block>/next-K.*`), and a block jumped over has `bypassed: true`. The child has `parent: { runId, flow, block, iteration }`. On the run page a block jumped over reads "not chosen by the branch", and the header of a block with `next` says where the run went.
- Cost: the parent's total includes its children. A child gets what is left of the parent's `--max-budget`; a child stopped by the budget stops the parent with `budget_exceeded`.
- Pause, resume, stop: pausing the parent while a call runs pauses the child after its current step, and the parent pauses after the call; resuming the parent resumes both, and stopping the parent stops the child (and releases it from a pause or a question). The child's own buttons and chat control only the child: pausing it doesn't pause the parent, and stopping it stops the chain — the parent ends `aborted`.
- Instructions and flow edits (see "Fix and continue") go to the run they are given in. An instruction to the parent while a call runs reaches the parent's next step: the next iteration's call task or the next block. To steer the running child, give it on the child's page. The parent's flow can be edited only while the parent itself stands on a pause, not while it waits for a child (the edit is refused with a hint to edit the child on its page); calls are checked again on such an edit.
- "Continue from where it stopped" is on the parent only. Blocks jumped over aren't repeated, a branch that wasn't decided is decided by the continuation, and a stopped call block continues its last child run from where that one stopped. If the child can't be continued (or the block now calls another flow), the call starts anew; in the first case it still gets the last child's artifacts, and those artifacts can be edited on the child's page before continuing the parent. A child run can't be continued on its own: it would break off from the chain. Calls are checked at the start of every run, including a continuation and a child.

**Builder:** "Add flow call" adds a call block. Its settings have the flow picker with "Open ↗" and the called flow's composition, the task with variable chips (empty means the default) and the repeat mode with its condition. Each block of a multi-block flow has "After the block": rules "condition → block" and the "otherwise" rule. The graph draws a call as one stacked `↪` node with the called flow's composition, branch edges with condition labels, jumps over blocks on their own lane on the left, and an "End" node when a rule leads to `end`. `show` prints calls and branching. The generator doesn't write calls or `next`: its schema hasn't changed.

### Parallel phases (group)

The runner starts adjacent phases of one block that have the same `group` field at the same time, and the next phase and the block's condition wait until all members finish. This suits independent work: reviews from different angles, researching separate questions, mostly reading. Example: `flows/example/example-parallel.yaml`.

- All members see one context, captured before the group starts: a shared `{{prev}}` (the output from before the group) and `{{phases.*}}`. You can't refer to a fellow group member via `{{phases.<member>}}`: it's a validation error, otherwise on iteration 2+ the member's output from the previous iteration would be silently substituted there.
- The phase after the group gets the members' outputs joined in declaration order in `{{prev}}`: `### name` and the output, as in `{{outputs}}`. Each member's output is also available separately in `{{phases.<name>}}`.
- A group has at least two phases, the group name isn't reused elsewhere in the flow, and a group has at most one phase with `Edit` or `Write`. `Bash` doesn't count as writing, but parallel builds or tests in the same directory can interfere with each other, for example through a shared build cache: better not to put such phases in a group.
- At most one member of a group writes a given artifact, and a member doesn't read (via `reads` or a substitution) an artifact that another member writes: they run at the same time. A phase that writes only artifacts (`writes` without `Edit` and `Write` in `tools`) doesn't count as writing in the sense of the previous item. All members get artifact substitutions as of the moment the group starts.
- `AskUserQuestion` is not allowed in a group: the UI, the CLI and the skill can't show two questions at once yet.
- A pause takes effect at the boundary between steps: the group members finish their work, and the next step doesn't start until "Resume".
- "Stop" aborts the sessions of all members at once.
- If a member fails, the runner waits for the others and stops the run with status `failed` and the error of the first failed member in declaration order. The cost limit (`--max-budget`) is checked after the group, so the overspend can reach the cost of the whole group.
- If a block with a `marker` condition ends with a group, `until.phase` is required: "the last phase of the block" isn't defined for a group.
- A group of N phases uses up the 5-hour subscription limit N times faster.
- Phase files are numbered by their position in the block, as usual; in `run.json` the members have a `group` field, and the reports come in order of completion.

If a phase has an `output_schema`, its result is JSON matching that schema, and that JSON is what goes into `{{prev}}`. The `handoff` field describes how the answer should end so that the next phase can use it: the runner appends it to the prompt, and the Builder shows it as the label of the edge between phases.

### Additional directories of a phase

`add_dirs` gives a phase access to directories besides the project directory, like `--add-dir` in Claude Code. Paths and attachments of the block's knowledge tags (`knowledge`, see "Tags") are added to phases the same way. Example: a separate project with QA rules connected only to the testing phase. Paths are absolute, start with `~`, or are relative to the project directory.

- `CLAUDE.md` and skills from `.claude/skills` are picked up from these directories.
- What a phase gets from `add_dirs` is shown on the "Context" page: pick a flow and a phase.
- The runner appends the list of them to the end of the phase prompt so the agent knows where to look.
- If a directory doesn't exist, the run fails before the first phase: silently working without the rules is worse.
- The judge (`until.type: judge`) doesn't get them. If it needs the same rules, move the check into a phase. The judge does get the run artifacts, though: the "Run artifacts" section, substitutions in the rubric and the read tools.
- The runner also passes the artifacts folder to the session as an additional directory, but only to a phase with access to artifacts and not in this list: a phase learns about its artifacts from the "Run artifacts" section.
- Run-level directories (the "Additional directories" field in the run form, `addDirs` in `POST /api/runs`) are added to all phases together with their `add_dirs`, without duplicates, and are appended to the same list at the end of the prompt. The judge doesn't get them either. The "Context" page doesn't know about them and shows only the phase's `add_dirs`.

### Block and phase plugins

`plugins` connects local Claude Code plugins, like `--plugin-dir`: the plugin's skills, agents, commands, hooks and MCP servers exist only in the sessions it's connected to. Usually the field is set on a block: all phases of the block get the plugin. Example: a testing block with a QA plugin, while the coding blocks and regular Claude Code sessions don't know about it unless the plugin is installed globally. A phase has this field too: its plugins are added to the block's plugins, without duplicates. Paths are absolute, start with `~`, or are relative to the project directory.

- `add_dirs` doesn't connect a plugin: only `CLAUDE.md` and `.claude/skills` are picked up from a directory, while a plugin's skills live in its `skills/` and, along with its agents, hooks and MCP, don't get in that way.
- If the folder doesn't exist, the run fails before the first phase, as with `add_dirs`. The "Context" page warns about the same thing and shows the plugin's skills, agents and MCP as part of the phase. A folder that exists but isn't a plugin (for example, a folder one level up) silently connects nothing: check on the "Context" page that the plugin's skills have appeared.
- The "Context" listing for such a phase starts a session with the plugin: the plugin's SessionStart hooks and MCP servers are started in the process.
- The judge doesn't get plugins.
- Plugin hooks run inside the phase session. If a hook asks for confirmation, there's no one to confirm in headless mode, and it's a denial, like any permission question. Quiet mode for such a plugin is turned on through its own settings.
- A plugin with MCP tools: server `<server>` of plugin `<plugin>` is called `plugin:<plugin>:<server>` in the session, its tools are `mcp__plugin_<plugin>_<server>__<tool>`, the whole server is `mcp__plugin_<plugin>_<server>`. For a phase to call them without confirmation, add the names to `tools` in the YAML: the Builder accepts only claude.ai connectors manually. An MCP server with OAuth must first be authorized once in a regular `claude --plugin-dir <folder>` session via `/mcp`; until then its status is `needs-auth` and it has no tools.
- A plugin is trusted code: its hooks run shell commands, and the artifact guard doesn't see MCP tools and hooks, just as it doesn't see Bash. Connect only plugins you trust as much as your own `~/.claude`.
- The plugin path is a path on your machine: a colleague with the same flow may have the folder somewhere else.
- In the Builder the field is "Claude Code plugins": in the block panel (for every phase of the block) and under "More options" on a phase card, one folder per line; the folder button picks a path.

### Run artifacts

An artifact is a named text file of a run, declared in the flow: a plan, a checklist, decisions. The runner creates it before the first phase in `runs/<id>/artifacts/`, and the file lives for the whole run: it survives iterations and blocks, carries over when you continue, and the user edits it in the UI or with the `/agentgraph` skill between steps. `{{prev}}` lives until the next phase, and each phase retells the state anew; an artifact keeps one current copy.

```yaml
artifacts:                      # at the top level, in both flow forms
  plan:                         # key: Latin letters, digits, - and _
    title: Plan                 # the key by default
    file: plan.md               # a name without directories: md, txt, json, yaml, yml; <key>.md by default
    initial: |                  # initial text as is, without substitutions; without it the file is empty
      # Plan
  progress:
    title: Check items
  decisions:
    title: Decisions
    decisions: true             # answers to pauses are appended here; at most one per flow
phases:
  - name: analyze
    tools: [Read, Grep, Glob]
    writes: [plan]              # edits only its own artifacts, Edit and Write in tools aren't needed for that
    prompt: ...
  - name: verify
    tools: [Read, Grep, Glob, Bash]   # no Edit: the phase doesn't edit code
    reads: [decisions]
    writes: [progress]
    prompt: |
      Plan: {{artifacts.plan}}  # a substitution also gives read access
      Mark the completed items in {{artifacts.progress.path}}.
```

- **Permissions.** A phase reads the artifacts from `reads`, `writes` and the `{{artifacts.KEY}}` / `{{artifacts.KEY.path}}` substitutions in the prompt and `handoff`, and writes only the artifacts from `writes`. The runner itself allows the phase any missing `Read`, `Edit` and `Write`, but only for its artifacts: editing any other file still requires `Edit` or `Write` in `tools`. A phase with `Read` in `tools` still reads any files, as before, but learns only about its own artifacts. The judge reads all artifacts.
- **Protection.** Editing another phase's artifact, creating an undeclared file in the artifacts folder and writing to the `runs/` folder (except your own artifacts, including with tools from `tools`) are rejected, and the agent gets an explanation. The same applies in the phase's subagents; a subagent with `isolation` isn't started for a phase with implicit permissions. Writing via `Bash` isn't prevented: after the step the runner flags such a change and writes a warning, but doesn't roll back the contents. Before each step, everything foreign in the artifacts folder (directories, including `.claude`, dotfiles, symlinks, `CLAUDE.md`) is moved to `artifacts-quarantine/<time>/` with a warning: Claude Code loads such files as instructions. A foreign regular file with an allowed extension stays, with a single warning; an artifact that disappeared is recreated empty. The names `CLAUDE.md` and `CLAUDE.local.md` are not allowed for artifacts.
- **What the phase sees.** At the end of the prompt (after `handoff` and the list of additional directories, before attachments) there's a "Run artifacts" section: the title, path, access and last author of each of its artifacts, and two rules — "write only to artifacts with 'write' access" and "take artifact paths only from here". Artifacts whose text is fully substituted into the prompt are listed in the line "the text is already above: no need to read the file for its contents" — otherwise phases reread the file before every edit. Writable artifacts (except the `decisions` log) are listed in the line "current state, not a log": update them so the file describes how things are now; add to and refine lists, but without a history of attempts per iteration. If the last edit was made by the user via the UI or the skill, the line says "take it into account and don't revert it". A change to the file between steps that wasn't made via the UI is marked "changed outside the phases, source unknown", without such an instruction.
- **Large artifact.** The substitution is captured at the start of the step. A file up to 32 KB goes in full; a larger one as a map of up to 8 KB: markdown sections by headings outside code blocks, top-level JSON and YAML keys, otherwise chunks of 200 lines. Each section has a line range, a size and its first meaningful line. The file itself doesn't change. The phase can read the rest of a section with the `artifact_read` (a section by its key from the map), `artifact_map` (the full map) and `artifact_search` (line search) tools, or with `Read` with `offset` and `limit`. The tools are read-only and available to every phase and to the judge with access to artifacts. For a writing phase that got a map, the section tells it to reread the file after its own edits.
- **Authorship and versions.** After each step the runner records who changed the artifact: a phase (with block and iteration), the user (UI or skill), "outside" (between steps, not via the UI), "unknown" (during a phase that doesn't write this artifact, for example via `Bash`; with a warning) or the condition (the `until` command). Each change is a version in `artifacts-history/<key>/`. A version stores a copy of the contents for a file up to 1 MB, as long as the run's history is under 200 MB; otherwise the version is recorded without a copy, with a warning. Any version with a copy can be opened in the artifact window.
- **Checklist items.** For a markdown artifact (`.md`) the server counts checklist lines outside code blocks (``` and ~~~): `- [ ]` are open, `- [x]` and `- [X]` are done; the marker is `-`, `*` or `+`, any indentation. The count is updated with each new version and is stored in the `tasks: { open, done }` field: in the artifact list (`GET /api/runs/<id>/artifacts`), in the `artifacts` event, in `run.json` (`artifacts.items[]`) and when reading the current version of the artifact. Reading version `?version=N` doesn't include the field. If the file was changed after the last recorded version (`unrecorded`), the read counts from the current text, while the list shows the old number until the next version. No items, a file that isn't `.md`, or larger than 8 MB — no field. In the UI it's an "N of M open" badge in the artifact row and in the header of its window, for example for the `progress` artifact ("Check items"): you can see how many problems are left without opening the file.
- **Editing on the fly.** While a step that writes the artifact is running, editing in the UI is blocked. An edit is picked up by every step that started after it was saved: a phase, a group or a condition check. A phase that's already running got the previous version. It's safer to edit while paused: "Pause" → the step finishes → edit → "Save and resume".
- **Refer to the artifact, not to the phase's retelling.** A user edit reaches the phases that read the artifact, but not those that take `{{phases.<phase>}}`: the phase output has already been written. Give the implementation phase `{{artifacts.plan}}`, not `{{phases.analyze}}`.
- **State, not a log.** An artifact describes how things are now: an open item is one line (`- [ ] … (open since iteration N)`), a confirmed fix is `- [x]` in one line. Don't ask phases to append "iteration N: still not fixed": the history is kept by the versions in `artifacts-history/`, and a log bloats the prompt of every later phase that gets the artifact as text. The exception is the `decisions` artifact: answers to pauses are appended to it.
- **Text or path.** Give `{{artifacts.KEY}}` to a phase that always needs the artifact; `{{artifacts.KEY.path}}` to one that reads it only occasionally, and for things that grow: patches, logs, long lists. Keep bulky things (for example, a ready patch for manual application) as a separate artifact so that phases that need the summary don't carry it.
- **When you need an artifact.** A plan that the implementation follows over several iterations; a checklist of what's done and what's open; the user's decisions. A linear flow and a loop where a phase needs only the previous output are fine with `{{prev}}`. Give a check phase that marks items `writes: [progress]` instead of `Edit`: it won't be able to edit code. In the judge's rubric, ask it to check the result against the project files and commands, not against what's marked in the artifact. Don't set `max_turns` to 1–3 for a phase with access to artifacts: even with `tools: []` the model often opens the file with a tool first and hits the turn limit.
- **Validation** (blocks saving in the UI, `show` and running): key and file names, `file` duplicates ignoring case, `reads`, `writes` and `{{artifacts.KEY}}` references to an undeclared artifact (with the location), more than one `decisions: true`, the group rules (see "Parallel phases"). An artifact that's declared but not used by anyone isn't an error: the judge reads it or the user edits it.
- **CLI.** `show` prints the flow's artifacts, `run` prints the path to the artifacts folder at the end. There's no editing on the fly in the CLI: the steps run back to back, but a file edited by hand during a run is attributed according to the authorship rules.
- A flow without `artifacts`, `reads` and `writes` works byte for byte as before: no section in the prompt, no folders, no artifact fields in `run.json`.

### Tools and permissions

Tools listed in `tools` are **allowed without confirmation**: in headless mode any confirmation request automatically turns into a denial, so otherwise the agent simply couldn't edit files or run commands. Hence the principle of least privilege: give `Bash` only to the phases that really need it. `permission_mode: bypassPermissions` removes all checks entirely; use it deliberately. Artifact permissions (`reads`, `writes`) don't extend access to project files: they apply only to the phase's own artifacts.

**claude.ai connectors** — Jira and Confluence (Atlassian), Slack, Docs, connected in your account. A phase gets them only if it lists the tools it needs in `tools` by their exact names, for example `mcp__claude_ai_Atlassian_Rovo__getJiraIssue`, or the whole connector as one entry, `mcp__claude_ai_Atlassian_Rovo`: then all its tools are allowed without confirmation, including those that change data, and the phase gets new tools of the connector automatically. The runner doesn't connect connectors to other phases or the judge (`ENABLE_CLAUDEAI_MCP_SERVERS=false`). A phase can't call a tool that isn't in the list anyway, while connected connectors, after the first call of any tool, put the definitions of all their tools into the context — about 45K tokens on every subsequent request. The exception is `permission_mode: bypassPermissions` or `auto`: there the connectors stay. This doesn't affect local MCP servers (Figma desktop and the like). The easiest way to give connectors to a phase is in the Builder — the "claude.ai connectors" row (see "Web interface").

Phases and the judge have no background tasks: `Bash` and subagents run synchronously. A command without `timeout` runs for up to 30 minutes, with `timeout` up to an hour; if it doesn't finish, it's killed. The session ends together with the agent's answer, and a background task would die with it: the agent would write "waiting for a notification", and the push or the subagent would be cut off. Start a process that has to outlive the phase (an emulator, a dev server) detached from the session: `nohup <command> > <log> 2>&1 &`.

## What a run leaves behind

`runs/<time>-<name>/`:

- `flow.yaml` — the spec the run used; for a one-off run it's the only copy of the flow, and continuing the run uses it too
- `run.json` — status, cost, turns, the `sessionId` of each phase (you can open it with `claude --resume <id>`), the `pid` of the runner process, `final` — the result: the phases of the last step (`block`, `iteration`, `phase`, `title`, `ok`, `output` — the output path relative to the run folder). For runs from before this field existed, `GET /api/runs/:id` computes it
- in `run.json` of a one-off run: `adhoc: true` (regular runs don't have this field)
- in `run.json` for each phase: `model` — the actual model from the Agent SDK's `system/init`, or, if init didn't arrive (the session failed before it started), the configured one (phase → `defaults` → `--model` or the "Model" field of the form); `effort` — the configured one (phase → `defaults`), because the SDK doesn't report the actual effort. The key is absent if the value is unknown: that's the case for runs from before this change and for phases where the model and effort aren't set anywhere and init didn't arrive;
- in `run.json` for each phase: `tokens` — the tokens of its session: `contextStart` and `contextPeak` — the context of the first and the largest request of the main loop (input + cache reads and writes; subagents not included), `requests` — the number of requests to the model, `contextWindow` — the main loop model's window from the result's `modelUsage` (absent if the window is unknown: the SDK sent 0 or the main model's entry wasn't recognized among several), `input`, `output`, `cacheRead`, `cacheCreation` — totals across all models of the session, including subagents; if the session was cut off without a result, there are no totals and no `contextWindow`, only the context. There's no `tokens` field if the SDK didn't send usage (the session failed before the first request), or for runs from before this change
- `iter-01/01-analyze.prompt.md` — the rendered phase prompt
- `iter-01/01-analyze.transcript.md` — the text of the answers and the tool calls
- `iter-01/01-analyze.output.md` — the final output of the phase (what went into `{{prev}}`)
- `iter-01/condition.json` (+ `.command.log` / `.judge.prompt.md`) — how the condition was checked
- `chat.json` — the run's chat history and its session id (appears after the first chat message)
- `attachments/` — task attachments from the run form (or copied from the run being continued); their paths relative to the run folder are in `run.json` in the `attachments` field, and run-level directories are in `addDirs`
- `artifacts/` — the run artifact files (only for flows with `artifacts`); open to phases with access and to the judge
- `artifacts-history/<key>/0001.md`, `0002.md`, … — artifact versions after each change; they live outside `artifacts/` and aren't visible to agents
- `artifacts-quarantine/<time>/` — what the runner removed from the artifacts folder before a step (appears only when something is found); `.tmp/` — temporary files for atomic writes
- in `run.json` for a flow with artifacts: `artifacts` — the artifacts with their last author and versions, `from` (which run they were taken from when continuing) and run-level warnings; for a phase and a condition — `artifacts.changed` and `artifacts.warnings`, for a phase also `denials` (write denials); for a pause — `answer`

For a flow of several blocks, iterations are in the block's folder: `01-spec/iter-01/…`, `02-split/iter-01/…`. `run.json` has `blocks` (the status and iterations of each block), and phases and conditions have a `block` field.

A run with tags has `tags` (slugs), `saveTag` (the checkbox) and `tagSummaries` in `run.json` — the result of the summary session for each tag: `tag`, `ok`, `costUsd`, `tokens`, and, if the summary wasn't updated, `skipped` (why there was no session) or `error`. The run folder has `tag-summary.<slug>.prompt.md`, the session prompt for each tag. A run with the auto-tag checkbox also has `autoTag`: the `slug` and `title` of the created tag (it's also in `tags`) or `error`, plus the `costUsd` and `tokens` of the picking session. Runs without tags have neither the fields nor the files.

The run name (see "run name" in the "Web interface" section) is in the `title` field of `run.json`. The `titleSession` field describes the naming session: `costUsd`, `tokens` and `error` if naming failed. The naming session doesn't write its prompt to the run folder. A continuation with an inherited name has `title` but no `titleSession`. Old runs have none of these fields.

## Tags: tasks and knowledge areas

A tag comes in two kinds (`kind` in `tag.json`; old tags without the field are task tags; the kind doesn't change after creation):

| Kind | What it is | Where it goes |
|---|---|---|
| `task` — task tag | a feature summary across runs (implementation → bug fixes → review → conflicts), notes, paths, attachments | a `<!-- tag:<slug> -->…<!-- /tag -->` block at the start of the task; after `done` — a summary session |
| `knowledge` — knowledge tag | what the phases should know (frontend, backend, QA): a "when it's needed" description, notes as instructions, paths, attachments; no summary | a line "- <slug> — <title>: <description>" under the "Knowledge areas …" header at the end of the prompts of the phases of a block with the `knowledge: [qa]` field in flow.yaml (or of all blocks if the tag is chosen in the run form), plus the `knowledge_read` tool the phase uses to read the whole tag; a tag with `inline` — the old full "Knowledge area <slug>" section; the tag's paths go into the additional directories of phases and the judge in either mode |

A feature is often refined over several runs. To avoid describing it from scratch every time, give the run a **task tag** — for example, `loyalty-card`: a short summary that the model maintains, plus your notes, paths and attachments. A run can have several tags (up to 10): the feature and, for example, a knowledge tag with the platform rules.

A **knowledge tag** is created on the "Tags" page with the "knowledge area" kind and attached to a block with the `knowledge` field (Builder: the "Knowledge tags" field on the block). A non-existent tag or a task tag in `knowledge` is an error before the phases start (in the UI — 400 with the block name). Tag notes are limited to 4000 characters, the description to 200, tags per block to 10. By default the tag is revealed gradually: the phase prompt has one line (`- qa — QA rules: <description or the first line of the notes> (notes characters: N, attachments: M, paths: K)`) under the header "Knowledge areas (details via the knowledge_read tool with the slug; open only when needed):", and the phase gets the full text (description, notes, existing paths, absolute paths of attachments) by calling `knowledge_read({ slug })` — an in-process MCP tool, server `knowledge`, available without confirmation; it rereads the tag on every call, so an edit on the "Tags" page is visible to a running run. The "Always insert notes into the prompt in full" checkbox (`inline` in tag.json) brings back the old behavior for short rules that must always apply; if all of a block's tags are like that, the phase doesn't get the tool. The judge gets the knowledge tags' folders, but not their text and not the tool. A flow with `knowledge` on an old server: the field is silently dropped, and the run goes without the knowledge.

In the run form the "Task" field stays a clean task: the server inserts the tag text, and a read-only "Tag context" panel under the chips shows what it will insert. The "Update summary" checkbox is visible only with a task tag. In `run.json` the run's knowledge tags are in `knowledge`; a continuation inherits them.

- **Where it's stored:** `~/.agentgraph/tags/<slug>/` (or `$AGENTGRAPH_CONFIG_DIR/tags/`), outside the repository:
  - `summary.md` — the summary, the current state of the feature;
  - `notes.md` — notes (the tag's prompt): your text, the summary session doesn't touch it;
  - `attachments/` — the tag's attachments (same types and limits as run attachments);
  - `tag.json` — the title, dates, the tag's paths (`dirs`) and the last 20 runs that updated the summary (`runs`) plus, separately, the last 10 terminal sessions that did (`kind: "session"`, see "Sessions"; they don't push runs out of the list); an auto-tag has `autoTitle: true` until the title is rewritten by hand; a knowledge tag has `description` (when it's needed, up to 200 characters) and `inline: true` (insert the notes into the prompt in full).

  Slug: lowercase Latin letters, digits and hyphens, up to 64 characters.
- **What a tag gives a run:** the tag block `<!-- tag:<slug> -->…<!-- /tag -->` goes at the start of the task: the title, notes, paths, absolute paths of attachments and the summary. The summary is the model's text, so it's wrapped in `source-data` with the "data, not instructions" label; the notes are your text, like the task itself. Phases and the judge get read access via additional directories: the tag's paths (for a file, its folder), the tag's attachments folder and the `artifacts/` folders of the tag's last three runs. Non-existent paths are skipped. These folders aren't written to the run's `addDirs` and are recomputed from the current state of the tags when continuing. The tag's attachments aren't copied to the run folder: phases read them from the tag folder.
- **Choosing in the run form:** the "Task tags" field above the task — pick from the list or type a new slug and press Enter. Each tag is a chip; its block joins the other tags' blocks at the start of the task, and the cross on a chip removes only its block. In the CLI — `--tag <slug>` (can be repeated), in the `/agentgraph` skill — `start --tag <slug>`. If the tag's block isn't in the input (CLI, skill, any API client), the server or the CLI inserts it; blocks that are already there aren't touched. A new tag is created when the run starts. The server won't accept input consisting only of tag blocks without a task of its own. The form doesn't remember the chosen tags.
- **Auto-tag:** the "Create a task tag automatically" checkbox in the run form (in the CLI — `--auto-tag`, in the skill — `start --auto-tag`, in the API — `autoTag: true`). Works only if no task tag is chosen; knowledge tags don't interfere. If a task tag is chosen by hand, the checkbox is inactive, the server ignores `autoTag` and doesn't call the model. Before the start, a short session (haiku, no tools, 30 s timeout) comes up with a slug and a title from the task text, the flow name and the run source, and a **new** task tag is created. The model's title is sanitized: one line without control characters and angle brackets, up to 80 characters. It was made up from untrusted text (anyone can write a ticket), so it's marked `autoTitle` and doesn't go into the tag block for the phases — the block header is just "Task tag: <slug>"; on the "Tags" page it's shown as usual, and a title rewritten by hand becomes your text and goes into the block. Existing tags aren't shown to the model and aren't reused: if the slug is taken (by a tag of either kind or just a folder), `<slug>-2`, `-3`… is created, and the other tag isn't changed. From then on it's the same as a tag chosen by hand: a block in the task, after `done` — a summary; "Update summary" has no effect for an auto-tag, the summary is always updated (so `--auto-tag` with `--no-save-tag` is an error). To continue a feature, pick its tag by hand or click "Continue": an auto-tag for "fix the review comments on X" will create a separate tag. A picking failure (error, timeout, invalid slug) isn't a run error: the run goes without a tag, and the reason is in the `POST /api/runs` response, in the UI notification and in `run.json` → `autoTag.error`. A continuation of the run inherits its tag and doesn't create a new one. The checkbox is remembered in the browser and is off by default. The tag is created at the start, so a failed run leaves a tag without a summary.
- **The "Tags" page** (`/tags` in the UI): the list of tags, creating a new one, the editor — title, summary, notes, paths (absolute, one per line), attachments, runs with the tag, deleting the tag; a knowledge tag also has the "Description — when this tag is needed" field and the "Always insert notes into the prompt in full" checkbox, and in the list the description is shown instead of the beginning of the notes. On the right is a large editor the full height of the window: it edits whichever field (summary, notes or paths) has the focus; when a tag is opened it shows the summary, for a knowledge tag — the notes. Editing on the right is the same as editing the field: "Save" and the unsaved-changes prompt work as usual. If the page is narrower than 1200 px, there's no editor on the right. A summary edited by hand lasts until the next successful run with the checkbox: then the session rewrites it, taking the edit as the basis.
- **Updating the summary:** the "Update tag summaries after the run" checkbox is visible when tags are chosen and is on by default; in the CLI and the skill `--no-save-tag` clears it. After a run with status `done`, a short session (haiku, only Read/Grep/Glob, up to 15 turns) runs for each tag, one at a time. It rewrites its tag's summary in full: it's the current state, not a log. Sections: "Gist", "Where the code is" (branch, worktree, MR), "Key decisions", "What's left", "Where to read more". A summary longer than 2500 characters is truncated with a note. Paths into the runs folder, except `<id>/artifacts/…`, are replaced by the code with a "not available to later runs" note: phase outputs (`iter-*/…output.md`) aren't visible to later runs. With any other status the summaries aren't touched. A session error doesn't change the run status: it's written to this tag's `error`, and its old summary stays. "Stop" during the summary aborts the current session and skips the remaining ones; the run stays `done`.
- **Continuing** a run inherits the tags and the checkbox; the tag blocks are already in its task. The auto-tag isn't repeated when continuing.
- **Limitations:** two concurrent runs with the same tag — the last writer wins, and the first one's update may be lost. The guard forbids writing to the artifacts folders of past runs only for flows with artifacts; the tag's paths are open to phases the same way as additional directories. The cost of summary sessions isn't limited by `--max-budget`: the limit is checked on phases. Tags can't be renamed: create a new one.

API: `GET /api/tags` (list with `kind`), `POST /api/tags` (`{ slug, title?, kind? }`, `task` by default), `GET /api/tags/<slug>` (the tag and the ready `input` text: a block for a task tag, a knowledge section for a knowledge tag), `PUT /api/tags/<slug>` (`{ title?, summary?, notes?, dirs?, description?, inline? }` — the fields passed are replaced entirely; `description` and `inline` only for a knowledge tag, otherwise 400), `DELETE /api/tags/<slug>`, `POST /api/tags/<slug>/attachments` (`{ name, data }`, base64), `DELETE /api/tags/<slug>/attachments/<name>`. In `POST /api/runs` — the fields `tags` (a list of slugs), `saveTag` and `autoTag` (`true` — create a new task tag, see "Auto-tag"; not a boolean — 400); with an auto-tag the 201 response has `autoTag: { slug, title? }` or `autoTag: { error }`. Server features in `GET /api/config` — `tags` and `auto-tag`.

## Sessions: Claude Code in a terminal with tags

The "Sessions" tab (`/sessions`, server feature `sessions`) opens a regular interactive Claude Code session — the real `claude` TUI with slash commands, its own permission prompts, `/resume` and `/clear` — in a terminal inside agentgraph, with the context of agentgraph tags. It works both in the desktop app and in `agentgraph ui` in a browser. The terminal is `node-pty` 1.1.0 on the server (an optional native dependency: if it doesn't load, e.g. on Linux without a build, the feature is off and there is no tab) and xterm.js in the window, connected by a WebSocket; a headless mirror of the screen (`@xterm/headless`) gives a reloaded page the current screen, so reloading or closing the tab doesn't stop the session. Up to 6 live sessions at a time (each `claude` takes about 300 MB).

**Starting.** The form: folder (with recent folders), tags (task and knowledge, up to 10, a new slug becomes a task tag), and under "Advanced" the name (by default the tag slugs or the folder name), the model and the permission mode (by default neither flag is passed and claude takes its own from the user's settings; `bypassPermissions` and `dontAsk` aren't offered), and "Update task tag summaries on exit". The server finds `claude` on `PATH`, otherwise the CLI from the Agent SDK platform package (in the packaged app — from `app.asar.unpacked`), otherwise the form shows an error; the claude version is shown under the terminal. Runs use the SDK's CLI (or `AGENTGRAPH_CLAUDE_EXECUTABLE`), so a session and a run can be on different claude versions. claude starts without a shell, as an argument array:

```
claude --session-id <uuid> --name=<name>
  --settings '<hooks and permissions.deny>'
  --mcp-config '{"mcpServers":{"agentgraph":{"type":"http","url":"http://127.0.0.1:<port>/api/sessions/<id>/mcp","headers":{…},"alwaysLoad":true}}}'
  --allowedTools mcp__agentgraph__knowledge_read,mcp__agentgraph__tag_read
  --add-dir <tag folders>… --add-dir <session files folder>
  [--model M] [--permission-mode P]
```

No `--append-system-prompt` (it freezes on the first request), `--strict-mcp-config` or `--bare`: the user's own hooks and MCP servers stay. The environment is the server's minus host and session markers (`CLAUDECODE`, `CLAUDE_CODE_SESSION_ID`, `CLAUDE_CODE_ENTRYPOINT`, `CLAUDE_CODE_MESSAGING_*`, `CLAUDE_AGENT_SDK_*`, `CLAUDE_PID`, `CLAUDE_EFFORT`, `CLAUDE_PREVIEW_*` and a few more) — the user's login, provider and Bedrock/Vertex settings stay — plus `NO_PROXY=127.0.0.1,localhost`, `TERM=xterm-256color`, `COLORTERM=truecolor`.

**How the tags get in.** Only through standard Claude Code mechanisms:
- `SessionStart` (start, `/clear`, `/resume`, compact) — a command hook (`curl -sSf … || true`; Claude Code skips HTTP hooks on SessionStart) answers with the full tag context in `additionalContext`: a task tag block (title, notes, paths, attachments, the summary as `source-data`) without the run markers, and a line per knowledge tag (inline ones in full).
- A hook's `additionalContext` is cut after 10,000 characters, so the context has a budget of 8,500: if it doesn't fit, task tags go as one line each, and the model reads the full text with the `tag_read` tool, like knowledge tags with `knowledge_read`.
- A tag added or removed during the session reaches the model with its next step (`PostToolBatch`) or your next message (`UserPromptSubmit`): only the change — blocks of the added tags and "tag X removed" lines. Until then the chip is dashed with a clock. The `knowledge_read` and `tag_read` tools (an HTTP MCP server on the agentgraph server itself) read the current tags at call time.
- `--add-dir` of a running claude doesn't change, so a `PermissionRequest` hook allows a read (`Read`, `Grep`, `Glob`) inside the folders of the current tags — a tag path that is a file allows only that file, `Glob` only with a relative pattern, all checked by realpath. Only that call is allowed: the folder isn't added to the session (`addDirectories` would make it a working folder, writable in `acceptEdits`), so the next read asks the hook again. Anything else is decided in the TUI.
- `--add-dir` also grants write access, so `--settings` denies `Edit` (which covers writing) on the folder itself and everything in it: the whole tags folder (`~/.agentgraph/tags`) and the artifacts folders of past runs — even inside the project — and the other opened folders. Tag paths inside the project or containing it are neither added nor denied; a folder with glob characters or brackets in its name is skipped (the rule wouldn't match it).

**Status.** "Working" — from `UserPromptSubmit` to `Stop`; "Waiting for you" — after `Stop`, `StopFailure` or a `Notification` about a permission prompt, idle prompt or MCP form; a session with no hooks for a while is checked against `claude agents --json`. "Ended" comes only from the claude process exiting: `SessionEnd` with reason `clear` or `resume` only switches the conversation. An exit without a single `SessionStart` while the trust dialog was on screen is a separate outcome, "Folder not trusted". If there's no `SessionStart` for 15 seconds, the tag row says the tags weren't delivered (possible causes: a proxy, `disableAllHooks`, `allowedHttpHookUrls`); while the trust dialog is on screen, it says so instead.

**Keyboard and files.** Shift+Enter is a new line in claude's input (it sends what Option+Enter does), Option works as Meta, Cmd+C / Cmd+V copy and paste. A file dragged onto the terminal is inserted as a path escaped like Terminal.app does; the browser doesn't give the file's path, so the server saves a copy into the session's `files/` folder (it's among `--add-dir`; same types and limits as attachments) and inserts that path.

**Quitting.** "End" sends SIGHUP: claude sends `SessionEnd` and exits (code 129). Stopping the server (Cmd+Q, Ctrl-C in `agentgraph ui`) closes the WebSockets, sends SIGHUP to every claude and waits up to 5 seconds. In the desktop app, Cmd+Q with live sessions asks first ("Close agentgraph?").

**Task tag summaries.** The hooks keep a turn log, `turns.jsonl`: the user's message from `UserPromptSubmit` and the model's final answer (`last_assistant_message`) from `Stop`; the raw Claude transcript isn't parsed. When claude exits and the "Update task tag summaries on exit" checkbox is on (the default), a short session (haiku, only Read/Grep/Glob in the session's folder, up to 15 turns, not persisted) runs for each task tag attached at that moment, one at a time: the previous summary and the turns since the last summary go in as `source-data`, the new summary is written like after a run, and the tag's run list gets `{ kind: "session", id, title }`. "Update summary" (in the header, on the ended-session card, in the list for a session marked below) does the same at any time, only for the turns since the last summary; with no new turns or no task tag the button is inactive. Knowledge tags have no summary. Writes to one tag are queued inside the process; if a run rewrote the tag's summary while the session's summary was being written, the session recomputes once from the new one. A tag whose session failed keeps its old summary, and the turns stay unaccounted until all tags succeed. Quitting the app or stopping the server doesn't write summaries (a session would cost money with nobody watching): the session is marked "summary not updated: the app was closed" until the button is used.

**Continue and restart.** "Continue" on an ended session starts claude again in the same folder with the current tags (folders and write bans recomputed, a new hook token) at the same `/sessions/<id>`: `--resume` of the last conversation if its transcript exists, otherwise — no message was ever sent — a new conversation with a new `--session-id`. "Restart with tags" (the `⋯` menu of a live session) does the same without leaving the page: SIGHUP to the running claude, then `--resume` with recomputed `--add-dir`, so the folders of tags added on the fly become readable without asking; no summary is written on that exit. The open terminal switches to the new process by itself. "Delete session…" (an ended one only) removes `sessions/<id>/`; the Claude transcript stays.

**Storage.** `<AGENTGRAPH_HOME>/sessions/<id>/`: `session.json` — name, folder, tags, model, mode, the claude conversation ids (`claudeSessionIds`, a new one after `/clear` or `/resume`; only UUIDs are accepted), the transcript path from the hook, dates, exit code, turns, `summarizedTurns`, the last `summary` (`at`, `tags`, `errors`, `costUsd`) and `summaryPending`; `turns.jsonl` — the turn log; `screen.json` — the last screen, shown under the card of an ended session; `files/` — dragged files. Sessions survive a server restart as ended; one that was running when the server stopped or crashed is ended with the `summaryPending` mark. The Claude transcript stays in `~/.claude/projects`.

**Tag page.** In the list of runs that updated a task tag's summary, a session is shown as "session · <name>" and leads to `/sessions/<id>`. "Open a session with this tag" opens the new-session form with the tag filled in (`/sessions?tags=<slug>`).

**Security.** A terminal is a shell. The WebSocket upgrade bypasses the usual request guard, so it checks `Host` like the rest of the API and requires `Origin` to be exactly `http://<Host>`; without `Origin` it's refused (WebSockets aren't covered by CORS). Hooks and MCP come from the child claude without `Origin`: they need the session's random token in the `X-Agentgraph-Session` header (constant-time comparison); a wrong token is 404, not 401, so the MCP client doesn't start OAuth. The token is visible in the claude argv to the same user's `ps` — the same trust boundary as the whole API on 127.0.0.1 without auth. The Vite dev proxy forwards WebSockets (`ws: true`) only for a local `Host` (Vite doesn't check it on upgrade, and a DNS-rebinding page would otherwise pass) and rewrites `Origin` only for its own page. Links in the terminal open only for `http(s)`.

API: `GET /api/sessions` (`{ sessions, max }`, live first), `POST /api/sessions` (`{ cwd, tags?, name?, model?, permissionMode?, saveTag?, cols?, rows? }` → 201 session; 409 `code: limit`, 400 `code: no_claude`, 501 `code: no_pty`), `GET /api/sessions/<id>`, `PUT /api/sessions/<id>/tags` (`{ tags }`), `PUT /api/sessions/<id>/name` (`{ name }`), `POST /api/sessions/<id>/end`, `POST /api/sessions/<id>/continue` (`{ cols?, rows? }`; a live session — 409), `POST /api/sessions/<id>/restart` (a live one only), `POST /api/sessions/<id>/summary` (202, the summary is written in the background, `summarizing: true` until it ends; nothing new or no task tag — 409), `DELETE /api/sessions/<id>` (an ended one only), `POST /api/sessions/<id>/files` (`{ name, data }`, base64 → `{ path }`), WebSocket `/api/sessions/<id>/ws` (server → `{t:'snap'|'o'|'s'|'x'}`, client → `{t:'i', d}` input and `{t:'r', cols, rows}` size). From the child claude only: `POST /api/sessions/<id>/hook` and `POST /api/sessions/<id>/mcp` (JSON-RPC: `initialize`, `ping`, `tools/list`, `tools/call`; `GET` — 405).

## Flow analysis

The "Analyze flow" card on the "Overview" tab of a finished run (server feature `run-analysis`). `POST /api/runs/<id>/analysis` with the body `{ model? }` (sonnet by default) starts a session without tools (up to 3 turns) and responds with the finished result; for a running run — 409 `code: live`, for a second concurrent analysis of the same run — 409 `code: busy`. `GET /api/runs/<id>/analysis` returns the saved `runs/<id>/analysis.json` or 404 `code: missing`. Next to it, `analysis.prompt.md` is written — the session prompt.

The model is given facts from `run.json` and the flow YAML (the snapshot `runs/<id>/flow.yaml`, for an old run — restored from the report): per block — the condition, iterations, verdicts with the beginning of the feedback and a stagnation flag (`stale`: the feedback repeated the previous iteration); per phase — tools, whether it writes, model, number of runs, turns (average, maximum, whether it hit `max_turns`), cost, time, peak context and its share of the window, guard denials, the size of the prompt template, what the prompt uses (`{{prev}}`, `{{feedback}}`, `{{phases.*}}`, artifacts), `reads`/`writes`. The system prompt is an architecture reviewer with rules: a boundary between phases is justified only by context; merge phases that feed into each other and have a low peak context (rule of thumb < 40% of the window); split or narrow a phase with a peak > 75% of the window or one that hit the turn limit; command instead of judge for a deterministic check; stagnating feedback — change the prompt or the condition, don't burn iterations; narrow excess permissions; move reference material behind a tool; more than one block only with different completion criteria; if the flow is good, say so and don't invent edits.

The `RunAnalysis` response: `{ at, model?, costUsd, tokens?, verdict?: keep | improve | rework, summary, suggestions[], facts, error? }`, a suggestion is `{ kind: merge | split | remove | tools | condition | prompt | context | parallel | other, severity: high | medium | low, phases[], title, why, how }` (up to 20, junk is discarded). A model failure isn't a request error: you get `error` and the facts without a verdict. The cost of the analysis isn't included in the run's `totalCostUsd`.

## Flow eval

`agentgraph eval <flow|file.yaml> --tasks <tasks.yaml> [--runs N] [--compare <flow2|file.yaml>] [--cwd dir] [--max-budget usd] [--max-iterations n] [--model id] [--json out.json] [-v]` — an end-to-end run of a set of tasks through one or two flows.

The tasks file:

```yaml
tasks:
  - name: fix-tests          # required: Latin letters, digits, - and _, unique
    input: "Fix the tests"   # required: the task ({{input}})
    cwd: ~/code/repo         # optional; ~ is expanded, a relative path is relative to the tasks.yaml folder; otherwise --cwd
    setup: git checkout -- . && git clean -fd   # optional: shell before each run; non-zero — the run doesn't happen, a record with an error
    check: npm test          # optional: shell after a run with status done; 0 = solved. Without check, the status decides
    timeout_sec: 600         # optional: timeout for setup and check
```

The order is strictly flow → task → run, sequentially. Each run is a regular run in `runs/` (`title` "eval <flow> · <task> #<n>", visible in the UI); `--max-budget`, `--max-iterations` and `--model` apply to each one. An exception in one run doesn't bring down the eval: a record with `pass: false` and `error`. SIGINT stops after the current run (exit code 2); a finished eval returns 0 even if tasks weren't solved: it's a measurement. `--tag`, `--auto-tag`, `--once`, `-o`, `--input` are incompatible with eval; agent questions are rejected. The `setup` and `check` commands go through the shell, like a flow's `command` condition.

Output: a progress line per run, then a "Task | flow1 | flow2" table with cells like `2/2 100% · $0.40 · 1m 2s · it. 1.0`, a "Total" row and, with two flows, a "Flipped" section: tasks whose share of solved runs differs between the flows. Results — `runs/evals/<YYYY-MM-DD_HH-MM-SS>-<flow>[-vs-<flow2>]/results.json` (overwritten after each run, a copy with `--json`): `{ version: 1, startedAt, finishedAt, tasksFile, flows, tasks, runs, cwd, aborted?, records[], cells[], totals[], flipped[] }`, where `records[]` is `{ flow, task, run, runId, status, pass, costUsd, durationMs, iterations, setupExit?, checkExit?, output?, error? }`.

## Cost

Each phase is a new session with the full Claude Code system prompt (~33K tokens). The first session in an hour pays for the cache write, the rest read it cheaply. How much context a phase got at the start and how far it grew is shown in the phase's `tokens` in `run.json` and on the phase card (the `ctx` chip). Limit spending with `--max-budget`, `defaults.max_budget_usd` and `max_turns`. The generator works without tools and with a short system prompt, so it's cheap. The tag summary session (one per tag, only with status `done`) runs on haiku; its cost is included in the run total and shown in `tagSummaries[].costUsd`; `--max-budget` doesn't limit it. The auto-tag picking session (haiku, no tools, before the start) is also included in `totalCostUsd` from the very beginning — `autoTag.costUsd` — and counts toward `--max-budget` on the very first phase. The run naming session (haiku, no tools, runs in parallel with the phases after the start) is also included in `totalCostUsd`: it's added when the name is ready and shown in `titleSession.costUsd`. The judge also has a short prompt, but it can read files and call subagents, so it costs more than it used to.

## Limitations and what's next

- Phases inside a block can run in parallel in groups (`group`). There are no parallel blocks or parallel calls of flows. Branching (`next`) only jumps forward (see "Calling another flow and branching"); continuing a run, `{{prev}}` between blocks and the block strip in the UI are designed around the order of blocks.
- Between phases, the output text (`{{prev}}`, `{{phases.NAME}}`) and the run artifacts are passed. An artifact lives only within a run and its continuations: a called flow (`flow:`) runs as a child run with its own artifacts, and only text goes between the parent and the child (the task in, the result out); there are no files shared between independent runs, no artifacts outside the run folder (for example, in the project repository), no folders with a file per task and no binary artifacts.
- Writing to an artifact via `Bash` isn't prevented, only marked with the author "unknown" and a warning. There's no editing artifacts on the fly in the CLI, and no merging of concurrent edits by the user and a phase either: instead, editing is blocked while a writing step is running.
- A single-block flow can't be continued from where it stopped, including a flow with artifacts: there's nowhere to apply artifact edits for a stopped single-block run, so they're unavailable.
- A single-block one-off run (and the generator usually makes one block) can't be continued either, so "Continue" is available less often for one-off runs. A one-off run draft lives only in the browser tab: reloading or closing the tab loses it (leaving asks for confirmation). The "Context" page doesn't work for a draft: it takes the flow by name from `flows/`. "Run…" from a Jira issue, MR or branch doesn't offer a one-off run.
- The condition is checked after a full pass through the phases. You can exit early within an iteration with a `marker` on an intermediate phase.
